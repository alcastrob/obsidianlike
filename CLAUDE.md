# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A VS Code extension (`.vsix`) that acts as a local Obsidian-like markdown editor. It operates entirely offline — no marketplace, no external servers. Installed locally into the VS Code profile named **"Obsidian like"**.

The core feature is a `CustomTextEditorProvider` that opens `.md` files in a webview powered by **CodeMirror 6** (CM6). The editor provides live-preview (WYSIWYG-like): markdown syntax markers are hidden on non-active lines, and block elements like tables are rendered visually. The underlying document is always plain markdown text.

## Deploy workflow (mandatory after every code change)

```bash
npm run package
code --profile "Obsidian like" --uninstall-extension angelCastro.obsidian-like
code --profile "Obsidian like" --install-extension obsidian-like-0.0.1.vsix
```

Then reload the VS Code window (Ctrl+Shift+P → "Developer: Reload Window").

`npm run package` = `npm run compile && npm run build-webview && vsce package --allow-missing-repository`

- `compile` → tsc compiles `src/extension.ts` → `out/extension.js`
- `build-webview` → esbuild bundles `webview-src/editor.js` → `out/editor.bundle.js`

## Architecture: extension host (`src/extension.ts`)

### Helpers

- `getAttachmentRoots(docUri)` — returns `vscode.Uri[]` for `localResourceRoots` (vault root, doc dir, configured subfolder). Vault root is always included, so any nested path under it is webview-accessible.
- `findImageFiles(dir)` — recursive image-file walker (extensions: png/jpg/jpeg/gif/svg/webp/bmp), skipping dotfiles and `node_modules`. Falls back to `fs.statSync` when `Dirent.isDirectory()/isFile()` are both false, because cloud-sync placeholder folders (Dropbox Smart Sync, OneDrive Files On-Demand) use NTFS reparse points that Node's `readdirSync` dirent type can misreport on Windows.
- `getImageMap(webview, docUri)` — returns `{ filename → webviewUri }` map. Resolution order: (1) the configured attachments dir (`getSaveDir`) — priority location; (2) a recursive `findImageFiles` scan of the whole vault root for any filename not already found. First match wins per basename. If a `![[file]]` reference isn't in the map at all, `imgPlugin` leaves the raw markdown text untouched instead of rendering a broken image.
- `getThemeCss()` — reads `.obsidian/themes/{name}/theme.css` from vault root (config: `obsidianLike.obsidianTheme`). Tries the exact-case path first, then falls back to a case-insensitive scan of `.obsidian/themes/`, matched by **name only** — deliberately not gated on `Dirent.isDirectory()`. A first version of this fallback did gate on it and still failed on a real macOS vault where the theme folder was visibly present: `readdirSync`'s `Dirent` type can misreport for reparse points / cloud-sync placeholders (iCloud Drive, Dropbox, OneDrive) / network or FUSE mounts — the same class of bug `findImageFiles` already works around elsewhere in this file, and not actually Windows-exclusive, just more commonly hit there. Since all that matters is whether `theme.css` is readable at the expected path, the fallback just tries reading it for every name-matching candidate instead of trusting the dirent type at all. If the theme still isn't found after both attempts, `showWarningMessage` includes the exact resolved `.obsidian/themes` path plus whatever folder names *were* found there (or a note that the directory itself couldn't be read) — richer than a bare "not found," since that's the only diagnostic signal available without a live debugging session on the machine where it fails.
- `computeBreadcrumb(docUri)` — returns `[{ name, fsPath }]` array for the clickable path bar
- `splitTarget(raw)` — splits a wiki-link/transclusion target into `{ notePart, section }` on the first `#`. `section` is a heading's raw text and may be from **any** level (`#`–`######`) — `note#section` does not imply the target heading is `# section`; it's matched against whatever level it's actually written at in the target file (see `parseHeadings`).
- `splitDirHint(notePart)` — splits `notePart` into `{ noteName, dirHint }` on `/`; only the immediate parent segment is kept as the disambiguation hint (mirrors the wiki-link directory-hint rule below).
- `resolveNoteUri(notePart, currentDir)` — the shared note-lookup used by `open-note`, `open-transclusion`, `get-transclusion` and `get-headings`. See "`open-note` resolution rules" below — this function *is* those rules, factored out so all four callers agree on where a bare/disambiguated note name resolves to.
- `parseHeadings(text)` — regex ATX-heading scanner (`# `.. `###### `), returns `[{ level, text, line }]` in document order (`line` is 0-based). Skips lines inside ``` ``` ```/`~~~` fences so a `#` in a code sample isn't mistaken for a heading. Setext headings (`===`/`---` underlines) are **not** recognized — only ATX, matching what `livePreviewPlugin`'s `ATXHeading[1-6]` handling already assumes webview-side.
- `navigateToTarget(raw, currentDocUri, sourcePanel, createIfMissing)` — resolves `raw` (via `splitTarget` + `resolveNoteUri`), optionally creates the note when missing (`open-note` passes `true`; `open-transclusion` passes `false` — a transclusion pointing nowhere should surface "not found", not silently create a blank note), opens it with `vscode.openWith` in `sourcePanel`'s column, and — if `raw` carried a `#section` that resolves to a real heading in the target — looks up that target's panel in `panelsByPath` and posts `scroll-to-line` to it ~350ms later (giving the freshly-opened webview time to mount). Disposes `sourcePanel` afterward, same as the original `open-note`-only behavior.

### Module-level state

- `noteIndex: NoteIndexEntry[]` (`{ name, dir, fsPath }`) — every `.md` file in the vault; `dir` is the vault-relative parent directory (`''` for root-level notes), `fsPath` is host-only (used to match note-history entries back to a name/dir pair, never sent to the webview as its own field). Built at activation, updated by `FileSystemWatcher` on create/delete, broadcast to all open panels as `note-index` (webview only receives `name`/`dir`).
- `activePanels: vscode.WebviewPanel[]` — tracks open panels to push `note-index`/`note-history` updates.
- `panelsByPath: Map<string, vscode.WebviewPanel>` — the panel currently showing each document path (set/cleared alongside `activePanels`, keyed by `document.uri.fsPath`). Exists solely so `navigateToTarget` can find the just-opened (or already-open) target panel to send `scroll-to-line` to — `vscode.openWith` doesn't hand back a panel reference, and `supportsMultipleEditorsPerDocument: false` means there's at most one panel per path to track.
- `extensionContext: vscode.ExtensionContext` — stashed at `activate()` purely to reach `context.globalState` from `recordNoteOpened`/`getNoteHistory` (see "`vaultTool.openNoteQuickPick`" below), which live outside `activate()`'s own closure. `recentNoteEntries()` maps `getNoteHistory()`'s fsPaths onto current `noteIndex` entries (dropping any that no longer exist) and `broadcastRecentNotes()` pushes that as `note-history` to every open panel — called from `resolveCustomTextEditor` right after `recordNoteOpened`, and from `buildNoteIndex` (a rename/delete can change which history entries still resolve).

### `resolveCustomTextEditor`

- Sets `webviewPanel.webview.options` with `localResourceRoots` covering `out/` and all attachment dirs.
- Calls `getThemeCss()`, `getImageMap()`, `computeBreadcrumb()` and passes all to `buildHtml()`.
- After 300ms: sends `{ type: 'note-index', notes }` and `{ type: 'theme-css', css }` (theme CSS is **not** inlined in HTML — see below).
- Handles `onWillSaveTextDocument`: sends `get-content` to webview, awaits `content-for-save` response (5s timeout).
- Handles `onDidChangeTextDocument`: sends `external-update` to webview when the file changes outside the webview.

### Autosave (`obsidianLike.autoSaveDelay`) and the sync/save race it replaced

The webview's own `sync` message (400ms debounce after the last keystroke, unchanged — see `EditorView.updateListener` in `editor.js`) always applies to the `vscode.TextDocument` model via `WorkspaceEdit`, keeping the in-memory document current for other consumers (Git decorations, `get-transclusion`'s "unsaved edits in another open tab are reflected" read via `openTextDocument`, etc.). That alone does **not** write to disk. Historically this repo relied on VS Code's own `files.autoSave` to do that part, but on macOS the two raced: `applySync`'s `vscode.workspace.applyEdit` (fired by the regular 400ms sync) and the `onWillSaveTextDocument` participant's own edit (fetched async from the webview via `get-content`/`content-for-save`, then applied as a `TextEdit` returned to `e.waitUntil`) were **two independent full-document-replace operations**, each going through a different VS Code internal pipeline (`workspace.applyEdit` vs. the save-participant `e.waitUntil` edit-application), with no ordering guarantee between them. If a `sync` carrying newer content happened to land *before* a still-in-flight, now-stale `content-for-save` reply got applied, the stale reply's edit landed last and silently overwrote the newer keystrokes — visible as text disappearing right as autosave fired mid-typing. Not reliably reproduced on Windows, consistent with a genuine race rather than a deterministic bug.

Fix: both paths now go through the exact same primitive, in the exact order their content was requested.
- `queueReplace(content)` — a promise chain (`pendingApply`) that serializes every full-document `WorkspaceEdit.replace` behind whichever one was queued before it. `fullRange()` (`document.positionAt(0)` .. `document.positionAt(document.getText().length)`) is computed **inside** the queued callback, i.e. once it's actually this replace's turn — not up front — so it always targets the document's real current length regardless of how many other queued replaces already landed ahead of it.
- `applySync(content)` calls `queueReplace(content)` (fire-and-forget, same as the old direct `applyEdit` call it replaced) and then `scheduleAutoSave()`.
- `onWillSaveTextDocument`'s `pendingSaveResolve` callback also calls `queueReplace(content)` instead of returning a `TextEdit[]` to `e.waitUntil` directly — `e.waitUntil` still gets a promise (resolving to `[]`, since the edit was already applied through the queue), just now only used to *delay the disk write* until that queued replace has actually landed. Because both the regular `sync` path and the save-participant path push onto the *same* `pendingApply` chain, whichever one's content was requested from the webview later is guaranteed to apply later too — arrival order at the host (a single postMessage channel, FIFO) now fully determines final content, eliminating the cross-pipeline race.
- **Autosave itself**: `getAutoSaveDelay()` reads `obsidianLike.autoSaveDelay` (default 3000ms). `scheduleAutoSave()` (called at the end of every `applySync`) resets a per-panel `autoSaveTimer`; when it fires with no further edits, `document.save()` is called if `document.isDirty` — this is the extension's own idle-based autosave, independent of `files.autoSave`. `document.save()` still goes through the now-race-free `onWillSaveTextDocument` above, so it also picks up any last few hundred ms of typing the 400ms `sync` debounce hasn't flushed yet.
- **Flush on tab close**: `webviewPanel.onDidDispose` clears `autoSaveTimer` and calls `document.save()` immediately if `document.isDirty`, rather than waiting for the idle delay to have already elapsed. By this point the webview itself is gone, so this can only persist whatever the last `sync` already applied to the document model — content typed in the last instant before close, not yet flushed by that 400ms debounce, is a residual gap this can't close (there is no "about to dispose, please flush" hook for a `CustomTextEditorProvider`'s webview).
- **Flush on VS Code closing**: `deactivate()` (`src/extension.ts`, end of file) saves every document under `panelsByPath` that's still `isDirty`, returning the combined promise so VS Code waits for it (up to its own shutdown timeout) before tearing down the extension host. Same residual gap as above if the webviews are already gone by the time this runs — `onWillSaveTextDocument`'s `get-content` round-trip just times out after 5s and falls back to whatever was already in the model.

**Follow-up bug: the last word or two typed disappeared, with the cursor jumping back to wherever it was when the save started.** `queueReplace`'s FIFO ordering (above) guarantees the *edits* apply in the right order, but a second, narrower race lived in `onDidChangeTextDocument`'s "is this my own edit landing, or a real external change?" check, which compared the just-changed text against `lastOwnContent`. That variable used to be written **synchronously**, the instant a `sync`/`content-for-save` message was *received* — not when the `WorkspaceEdit` it describes actually *landed*. Sequence that broke it: `content-for-save(C1)` arrives, `lastOwnContent = C1`, `queueReplace(C1)` queued (not yet applied); before `applyEdit(C1)` actually resolves, the user resumes typing and a later `sync(C2)` arrives, `lastOwnContent = C2` (overwritten already), `queueReplace(C2)` queued behind C1. When `applyEdit(C1)` *then* finally lands, `onDidChangeTextDocument` fires with `newText = C1`, compares against `lastOwnContent`, which is already `C2` — mismatch → treated as an "external" change → `external-update` sent to the webview with the stale `C1`, reverting whatever the user had already typed past that point and re-anchoring the cursor (via the line/col fix above) to where it was in `C1`. `queueReplace`'s own FIFO ordering still applied `C2` correctly to the document a moment later, but by then the webview had already been told to throw its live buffer away and go back to `C1`.
- Fixed by moving `lastOwnContent = content` out of the two call sites (`applySync`, `pendingSaveResolve`) and into `queueReplace` itself, set only **after** `vscode.workspace.applyEdit` resolves — i.e. in the same serialized order edits actually land, never describing one that hasn't yet.
- Additionally hardened with `applyingOwnEdit` (boolean, set for the duration of `queueReplace`'s own `applyEdit` call): `onDidChangeTextDocument` checks it *first* and, if true, always treats the change as its own (no content comparison at all) — structurally correct regardless of any remaining bookkeeping timing, rather than re-derived from a string comparison that can itself be mid-flight. Edits made **outside** `queueReplace` (e.g. `toggle-task`'s own direct `applyEdit`, used precisely so a checkbox click's resulting document change flows back to the webview as a real `external-update`) are deliberately untouched by this flag and continue to trigger it as before.

**Earlier follow-up bug from this feature: cursor jumping to line 1, column 1 on every autosave.** Every `document.save()` — including this new idle-triggered one — commonly ends up producing text that differs very slightly from what the webview last sent, regardless of anything this extension controls: VS Code's own save participants (`files.insertFinalNewline`, `files.trimTrailingWhitespace`, formatters, etc., whichever the user has enabled) can touch the buffer as part of the save. That legitimately differing content correctly triggers `onDidChangeTextDocument` → `external-update` (see `resolveCustomTextEditor` above) — but `editor.js`'s handler for it used to unconditionally do `view.dispatch({ changes: { from: 0, to: doc.length, insert: msg.content } })`, i.e. delete-and-reinsert the *entire* document on every such update, even when only a trailing newline had changed. CM6 maps the cursor through a dispatched change automatically, but a position that sat inside a range being *entirely* replaced has no well-defined mapped location, so it collapsed to `0` — visible as the cursor jumping to line 1, column 1 mid-typing, exactly in sync with the new autosave.

- **First fix, incomplete**: `minimalReplaceRange(oldStr, newStr)` (`editor.js`, just above the message-handling `switch`) — a plain common-prefix/common-suffix diff finding the smallest `{ from, to, insert }` span actually needed, instead of always replacing the whole document. Fixes the case where the changed span is small (e.g. a trailing newline appended at the very end) and the cursor sits outside it, since CM6's default selection-mapping leaves an unaffected position untouched. Didn't fully fix the reported bug: `files.trimTrailingWhitespace` strips trailing spaces from *every* line that has them, and markdown commonly uses a trailing double-space as an explicit line break — so on a real note, the diff between pre- and post-trim content can be scattered across many lines, which widens `minimalReplaceRange`'s span to cover most of the document. If the cursor happens to fall inside that (now large) span — likely, since it's wherever the user was actively typing — CM6 still has nothing better to map it to than the edge of the span, which can still land far from where it was.
- **Actual fix**: the `external-update` handler now also captures the cursor's (line, column) *before* dispatching, via `view.state.doc.lineAt(oldPos)` — `col = oldPos - oldLine.from` — and explicitly re-anchors the selection afterward with `posFromLineCol(msg.content, oldLine.number, col)` (also just above the `switch`), rather than trusting CM6's automatic change-mapping at all. This is correct independent of how large or scattered the diff is: a save participant like trim-trailing-whitespace never adds or removes *lines*, only trims characters off individual line ends, so "same line number, same column, clamped to whatever that line now contains" reliably lands back where the user actually was — something raw character-offset mapping through a wide diff can't guarantee. `minimalReplaceRange` is still used for the `changes` themselves (keeps the edit small for CM6's own bookkeeping — undo history, decorations, etc. — even though correctness no longer depends on it).

**Suppressing VS Code's "Do you want to save the changes...?" prompt on close.** Once the sync/save races above were actually fixed, the remaining friction was VS Code's own confirmation dialog: closing a dirty tab (or closing the window with dirty tabs still open) normally prompts Save/Don't Save/Cancel before the editor is even allowed to close — checked by VS Code's workbench layer *before* `onDidDispose` fires, so there's no `CustomTextEditorProvider` hook that can intercept or answer it on the extension's behalf. The one *sanctioned* lever is `files.autoSave`: VS Code's own documented behavior is that whenever it's not `"off"`, dirty editors are saved automatically on close instead of being prompted about — for a single tab and, empirically, for whole-window close too.
- `syncMarkdownAutoSaveSettings()` (`src/extension.ts`, just above `activate()`) sets `files.autoSave: "afterDelay"` as a **`[markdown]`-language-scoped** override (`vscode.workspace.getConfiguration('files', { languageId: 'markdown' })`, `.update(section, value, ConfigurationTarget.Global, /* overrideInLanguage */ true)`) — written to the user-settings.json of the current VS Code profile, and scoped so it only changes behavior for markdown files, leaving whatever the user has configured for every other language untouched. Called once from `activate()`.
- Both writes are guarded by a `.get()` check first, so `activate()` doesn't rewrite the user's settings.json (and fire a redundant `onDidChangeConfiguration`) every single time VS Code starts if the values already match.
- The `onDidDispose` tab-close flush and `deactivate()` whole-window flush (both described above) are kept as-is on top of this — belt-and-suspenders, in case a dirty tab somehow closes without VS Code's own autoSave-driven save having already covered it.

**Follow-up: this reintroduced overlapping-save concurrency, in a different shape than the original macOS race.** The first version of this synced `files.autoSaveDelay` (VS Code's own idle delay for `afterDelay` mode) to match `obsidianLike.autoSaveDelay`. Since both are debounced off the *same* underlying signal — the document going idle after an edit — syncing the two numbers meant VS Code's native timer and this extension's own `scheduleAutoSave` timer would tend to elapse at nearly the same instant on every single pause in typing, each independently calling `document.save()` and each triggering its own `onWillSaveTextDocument` firing. `pendingSaveResolve` was a single shared variable, not built to handle two overlapping firings: the second firing's assignment silently clobbered the first firing's callback, so the webview's eventual `content-for-save` reply — correlated only by "whatever `pendingSaveResolve` currently points to", not by which firing actually asked for it — resolved the *wrong* firing's promise. Worse, the first firing's own 5s timeout (`if (pendingSaveResolve) { pendingSaveResolve = undefined; ... }`) would then null out the second firing's callback too, out from under it, if it hadn't resolved yet. (This same overlap is also reachable without any of this — a manual Ctrl+S landing while this extension's own idle autosave is already mid-flight hits the identical bug.)
- Fixed two ways. First, `files.autoSaveDelay` is no longer synced to `obsidianLike.autoSaveDelay` at all — it's set to a fixed, deliberately huge constant (`NATIVE_AUTOSAVE_DELAY_MS`, 24h) instead, so VS Code's own timer practically never fires on its own; it's enabled purely for the close-prompt suppression above (which only depends on `files.autoSave` *not being* `"off"`, not on the timer ever actually having fired), not to compete with this extension's own idle timer as a second real save driver.
- Second — real defense-in-depth, since a manual Ctrl+S can still land squarely inside our own autosave's in-flight round trip regardless of the above — `onWillSaveTextDocument` now coalesces overlapping firings onto a single shared `pendingFlush: Promise<void>`: if a firing arrives while one is already in progress, it just awaits *that same* in-flight flush instead of starting a second `get-content` round trip and clobbering `pendingSaveResolve`. Every firing's `e.waitUntil` resolves once the shared flush lands, each still gets its own actual disk write from VS Code's save machinery, but there's only ever one webview round trip and one `queueReplace` call backing however many overlapping firings triggered it.
- **Not addressed, and deliberately left to the user**: whether `files.trimTrailingWhitespace` silently discarding a markdown line-break's trailing double-space constitutes *content* loss (as opposed to the cursor-position bug above) is a separate, real concern — this extension does not currently touch that VS Code setting (scoping it off for markdown would be a `[markdown]`-language settings override, not attempted here since it means writing to the user's settings.json on their behalf).

**Cross-window save conflict: opening the same note in two VS Code *windows* (two independent extension-host processes) let one silently clobber the other's newer save.** Everything above fixes ordering *within* one window's own document/webview pair — it has nothing to say about a second window, with its own completely independent `vscode.TextDocument` snapshot of the same file, whose idle autosave timer fires after the first window has already written newer content to disk. Reported directly: "solo estoy escribiendo en una, pero el autosave hace que haya conflictos de escritura con contenido desactualizado."
- `lastKnownMtime: Map<string, number>` (`src/extension.ts`, module-level, keyed by `fsPath`) tracks the on-disk mtime as of the last time each document is *known* to have matched disk — refreshed via `refreshKnownMtime(uri)` right after this window's own successful save, and after an external-change auto-reload (`onDidChangeTextDocument`'s branch that already sends `external-update`). Module-level rather than a per-panel closure variable specifically so `deactivate()`'s whole-window-closing flush — which has no panel/webview reference at all — can consult the exact same guard.
- `isDiskNewerThanKnown(uri)` stats the real file and compares against that map; no recorded mtime at all (a brand-new, never-saved document) returns `false` rather than blocking the first save.
- All three of this extension's own disk-write paths check it *before* writing: `scheduleAutoSave`'s idle timer, the tab-close flush in `onDidDispose`, and `deactivate()`'s whole-window-shutdown flush. Each skips its save when the disk is newer than what this window last saw, rather than blindly overwriting — `scheduleAutoSave` additionally shows a one-time `showWarningMessage` (`warnedStaleOnDisk`, panel-local, reset once the conflict resolves) so the silent skip is at least visible: *"...se modificó en otra ventana. El autoguardado se ha saltado... guarda manualmente (Ctrl+S) para forzar tu versión, o cierra esta pestaña sin guardar para conservar la de disco."*
- **`onDidDispose`'s flush needed the exact same guard for a subtler reason**: the warning above tells the user closing the tab without saving is a safe way to keep the disk version, but the tab-close flush (`document.save()` if `document.isDirty`, meant to persist the last few hundred ms of typing the 400ms `sync` debounce hasn't flushed yet) used to run *unconditionally* — so "close without saving" would still silently trigger a save on the way out, overwriting the newer disk content anyway. Fixed by gating it behind `isDiskNewerThanKnown` too, so the escape hatch the warning describes is actually true.
- Deliberately scoped to just these three *automatic* flush paths — a manual Ctrl+S (going through the ordinary `onWillSaveTextDocument`/`pendingFlush` pipeline documented above) is left alone, since blocking an explicit user action without any UI to resolve it would be worse than the automatic-clobber bug this exists to fix. **Known limitation, stated directly to the user rather than solved**: this closes the "silent overwrite with no warning" failure mode, but doesn't attempt any real merge of genuinely concurrent edits made in both windows at once — if that happens, the user still has to pick a winner by hand (save one side, discard the other).

### Why theme CSS is sent via postMessage, not inlined in HTML

Obsidian themes (e.g. Border) embed SVG data URLs in CSS properties like `-webkit-mask-image`. Those SVGs contain `<style>...</style>` tags, which prematurely close the `<style id="__obsidian-theme">` HTML element. The fix: leave the style element empty in HTML, send CSS via `postMessage({ type: 'theme-css', css })`, apply with `element.textContent = css` (bypasses the HTML parser entirely).

### Message handlers (webview → host)

| Message | Action |
|---|---|
| `sync` | Apply `content` to VS Code document via the serialized `queueReplace` (see "Autosave" above), then reset the `obsidianLike.autoSaveDelay` idle timer |
| `content-for-save` | Resolves the pending `onWillSave` promise |
| `rename` | Validates new name, calls `WorkspaceEdit.renameFile()` — link fixup happens via the `onDidRenameFiles` listener that fires from this, see below, not from this handler directly |
| `open-note` | `navigateToTarget(name, ..., createIfMissing: true)` — resolves the wiki-link target (optionally `note#section`) and opens it with `vscode.openWith` in the same column, scrolling to the heading if a section was given (see below for resolution/creation rules) |
| `open-external-file` | `{ name, basePath? }` — a `[[file.docx]]`/`[[file.xlsx]]`/`[[file.pdf]]` wiki-link or `![[...]]` embed of one (see `EXTERNAL_FILE_EXT`/`isExternalFileTarget`/`ExternalFileWidget` in `editor.js`). Resolves `name` via `resolveExternalFileUri` (same shape as `resolveNoteUri`, but the glob pattern searches for the name *as-is*, no `.md` appended) and hands the result straight to `vscode.env.openExternal`, opening it with whatever the OS has registered as the default application — never routed through `vscode.openWith`/the markdown editor, since these aren't notes. A vault-wide miss shows a warning instead of creating anything (unlike `open-note`, there's no sensible "create a blank .docx" fallback) |
| `open-transclusion` | Same as `open-note` but `createIfMissing: false` — clicking a transclusion's "open source" button navigates to it like a link, but a missing target just shows a warning instead of creating an empty note |
| `get-transclusion` | Resolves `msg.target` (`note`, `dir/note`, or `...#section`), reads the target's text via `vscode.workspace.openTextDocument` (so unsaved edits in another open tab are reflected), slices out the section if one was given, and replies `transclusion-result` — see "Transclusions" below |
| `get-headings` | Resolves `msg.note`, returns `parseHeadings(text)` (level/text only, no line) as `headings-result` — powers the `#`-section step of `WikiSuggestView`'s suggestion popup |
| `open-url` | `vscode.env.openExternal(vscode.Uri.parse(url))` |
| `reveal-path` | `vscode.commands.executeCommand('revealInExplorer', vscode.Uri.file(fsPath))` |
| `paste-image` | Saves base64 buffer as `Pasted image YYYYMMDDHHMMSS.png` to configured attachments dir, sends back `image-pasted` with webview URI |
| `drop-files` | `{ files: [{ name, data }] }` — one or more OS files dropped onto the webview. Saves each into the configured attachments dir *keeping the original filename* (unlike `paste-image`'s timestamp naming, since a real filename is available here), disambiguating only on an actual collision (`"name N.ext"`), and replies `files-dropped` |
| `toggle-task` | Toggles the task checkbox line at `msg.line` (0-based). See "Task checkboxes" below. |
| `toggle-task-at-location` / `edit-task-at-location` | `{ path, line }` variants of `toggle-task`/(no inline equivalent — see below) for a task that may live in a *different* file than the one this panel is showing — used by ```tasks``` query rows' checkbox and edit button. See "Task checkboxes" and "```tasks``` query blocks" below. |
| `cursor-position` | `{ line }` (0-based) — sent on every CM6 selection change, cached in `panelCursorLine`. Powers the `vaultTool.editTaskAtCursor` keybinding; see "Keyboard shortcut for 'edit task at cursor'" below. |
| `scroll-position` / `restore-scroll` | `{ scrollTop }` — `scroll-position` sent (rAF-throttled) on every `view.scrollDOM` scroll, cached in `panelScrollTop`; `restore-scroll` sent back after the Tasks extension's "Create or edit Task" dialog closes, to undo the scroll-to-top that dialog's focus steal was observed to cause. See "Restoring scroll after the task-edit dialog closes" below. |
| `run-dataview-query` | `{ lang, query }` (`lang` is `dataview`/`dql`/`dataviewjs`) — runs the query against the sibling Dataview extension's vault index and replies `{ type: 'dataview-query-result', lang, query, result: { ok, html } }`. See "Dataview query blocks" below. |

### Task checkboxes — soft dependency on `angelCastro.obsidian-like-tasks`

Clicking a `.cm-task-checkbox` widget in the CM6 editor (see `TaskCheckboxWidget` below) posts `{ type: 'toggle-task', line }` (0-based doc line number). The handler in `resolveCustomTextEditor`'s `onDidReceiveMessage`:

1. Reads the current line text with `document.lineAt(line).text`.
2. Calls `getTasksApi()`, which lazily does `vscode.extensions.getExtension('angelCastro.obsidian-like-tasks')?.activate()` and caches the resulting promise in the module-level `tasksApiPromise` — but **only caches success**: if `getExtension()` returns `undefined` or `activate()` throws, `tasksApiPromise` is reset to `undefined` so the *next* call retries from scratch, rather than being stuck with a permanently-failed lookup for the rest of the session (a real, if narrow, cold-start race: this extension's own activation can occasionally be requested before `angelCastro.obsidian-like-tasks` is registered in VS Code's extension list). Extension id note: the "Obsidian-Like Tasks" extension's `package.json` `name` is `obsidian-like-tasks` (repo folder: `c:\git\obsidianlike_tasks`) — if that ever changes again, update this id here too.
3. If the Tasks extension is installed and its API exposes `toggleTaskLine`, calls `tasksApi.toggleTaskLine(lineText)` — this is the "Obsidian-like Tasks" extension's own recurrence-aware state machine (`src/api/TasksApi.ts` in that repo), returning either `[toggledLine]` or, for a just-completed recurring task, `[nextOccurrenceLine, toggledLine]`.
4. Otherwise falls back to `naiveToggleTaskLine(lineText)` — a local helper that does a plain `[ ]` ↔ `[x]`/`[X]` regex flip with no recurrence handling.
5. Applies the result via a `WorkspaceEdit` that replaces only `document.lineAt(line).range` (not the whole document — unlike `applySync`), joining multiple returned lines with the document's actual EOL (`document.eol === vscode.EndOfLine.CRLF ? '\r\n' : '\n'`).

This is a **soft dependency**: `package.json` has no `extensionDependencies` entry, so Obsidian-like works standalone without the Tasks extension installed — `getTasksApi()` resolves to `undefined` (via `getExtension()` returning `undefined`, or a rejected `activate()` caught internally) and the naive fallback runs instead. Two extensions' webviews cannot call into each other directly, which is why this call happens host-to-host (Obsidian-like's `extension.ts` calling into the Tasks extension's exported API), not webview-to-webview.

The `TasksExtensionApi` shape Obsidian-like expects (declared locally in `src/extension.ts`, not imported from the other repo — kept intentionally minimal/optional-heavy so an older build of the Tasks extension degrades gracefully instead of throwing):
```ts
interface TasksExtensionApi {
  isTaskLine(lineText: string): boolean;      // not currently called from Obsidian-like
  toggleTaskLine(lineText: string): string[]; // returns replacement line(s), no trailing newline
  renderTasksQuery?(queryText: string): TasksQueryResultDTO;
  toggleTaskAtLocation?(path: string, line: number): Promise<void>;
  editTaskAtLocation?(path: string, line: number): Promise<void>; // opens that extension's own edit dialog; called by both the ```tasks``` query row edit button and `vaultTool.editTaskAtCursor` (see "```tasks``` query blocks" and "Keyboard shortcut for 'edit task at cursor'" below)
  onDidChangeTasks?: vscode.Event<void>;
}
```

#### Editing a task — why there's no click target for it anymore

There is no cursor-based "edit task" command on this side — this editor is a `CustomTextEditorProvider`, so VS Code doesn't expose anything like `activeTextEditor.selection` for it, and the Tasks extension can't read cursor position out of our webview either (same isolation as everywhere else in this integration). Concretely: before any of this existed, the Tasks extension's own cursor-based command (`tasksManager.createOrEditTask`, since removed from that extension entirely — see below) silently created a *new*, blank task appended to the end of the document instead of editing the one the user meant while a note was open here, because that extension genuinely had no way to know which line was "current."

**First fix — a pencil button (removed)**: a small `.cm-task-edit-btn` button (rendered next to every checkbox by `TaskCheckboxWidget` and every `renderTaskRow`) posted `{ type: 'edit-task', line }` (current document) or `{ type: 'edit-task-at-location', path, line }` (a ```tasks``` query row, possibly a different file), giving the Tasks extension the exact location up front instead of asking it to infer one. This worked, but became redundant once `vaultTool.editTaskAtCursor` (below) shipped a real keyboard shortcut covering the same case with less visual clutter next to every checkbox, so the button and its two message types (`edit-task`/`edit-task-at-location`) were deleted from both `editor.js` and the host's `onDidReceiveMessage`. `editTaskAtLocation` on `TasksExtensionApi` itself stayed — it's still the call `vaultTool.editTaskAtCursor` makes, just triggered from a keybinding instead of a button click.

#### Keyboard shortcut for "edit task at cursor" (`vaultTool.editTaskAtCursor`, `Shift+Alt+E`)

The Tasks extension (`obsidianlike_tasks`) used to also contribute its own `Shift+Alt+E` keybinding for a cursor-based `tasksManager.createOrEditTask` command, but its `when` clause (`editorTextFocus && editorLangId == markdown`) never matched while this extension's custom editor held focus — same reason `activeTextEditor` doesn't exist for it, and that command had no way to ask this webview "what line is the cursor on" either (no cross-extension API for querying another extension's live cursor position, only for calling exported commands with explicit arguments like `editTaskAtLocation(path, line)` above). Since `vaultTool.editTaskAtCursor` here fully covers that case — and does so for *every* markdown file, not just ones opened with this custom editor — that command and its keybinding (along with the equally-dead-in-this-context `tasksManager.toggleTaskLine`/`Ctrl+Enter`) were removed from `obsidianlike_tasks` entirely, rather than left around unused.

**First version — a pure CM6 keymap, no VS Code involvement at all**: `Shift-Alt-e` bound directly in `createEditor`'s `keymap.of([...])`, reading `view.state.selection.main.head` locally and posting the same `edit-task` message the pencil button sends. This worked, but turned out to be a dead end: since it was never registered through `contributes.keybindings`, VS Code's Keyboard Shortcuts UI had no idea it existed — it didn't show up in the list, and there was no way for the user to rebind it to a different chord. A shortcut a user can't see or remap in the standard UI isn't acceptable for something this central, so it was replaced with the design below and removed from `editor.js` entirely.

**Current version — a real command + a cursor-position cache**: `vaultTool.editTaskAtCursor` (`src/extension.ts`) is a normal `vscode.commands.registerCommand`, bound in `package.json`'s `contributes.keybindings` with `"when": "activeCustomEditorId == 'vaultTool.markdownEditor'"` — the exact same pattern `vaultTool.openNoteQuickPick`'s `Ctrl+O` already uses. Being a real keybinding contribution means it shows up in the Keyboard Shortcuts UI (`Source: Obsidian-like`) and the user can rebind it like any other command. The one thing this pattern still doesn't give a host-side command is the cursor's line — `activeTextEditor` remains unavailable — so that gap is closed separately:
- `editor.js`'s `EditorView.updateListener` posts `{ type: 'cursor-position', line }` (0-based) on every `selectionSet`, not just on `docChanged` — cheap enough (a single int) to need no debounce, unlike `sync`'s full-document payload.
- The host caches the latest value per panel in `panelCursorLine: Map<vscode.WebviewPanel, number>` (module-level, alongside `activePanels`/`panelsByPath`), set in the `cursor-position` message handler and cleared in `onDidDispose`.
- `vaultTool.editTaskAtCursor`'s handler resolves "the currently active panel" with the same `activePanels.find(p => p.active) ?? ... ?? (activePanels.length === 1 ? activePanels[0] : undefined)` fallback chain `vaultTool.insertAttachment` already uses, reverse-looks-up its path via `[...panelsByPath.entries()].find(([, p]) => p === panel)?.[0]` (same trick `insertAttachmentCmd` uses), reads the line from `panelCursorLine`, and calls `tasksApi.editTaskAtLocation(path, line)` directly — no `postMessage` round-trip needed, since this command runs on the host side already (unlike the now-removed pencil button, which had to send a message up from the webview).

This is the "publish cursor position via an exported API" design floated early in `obsidianlike_tasks/CLAUDE.md` and initially discarded as overkill — it turned out to be exactly what was needed once "reassignable in the Keyboard Shortcuts UI" became a real requirement, just scoped down to an in-process message/cache instead of a whole new cross-extension API surface (no other extension needs this cursor position, so there was no reason to export it).

#### Restoring scroll after the task-edit dialog closes

The Tasks extension's "Create or edit Task" dialog (`showTaskEditDialog`, `obsidianlike_tasks/src/TaskEditWebview.ts`) opens as its own `WebviewPanel` tab, `ViewColumn.Beside` + `preserveFocus: false` — it steals focus from whichever panel here triggered it (via `vaultTool.editTaskAtCursor` or a ```tasks``` query row's edit button) for as long as it stays open. On a long note, that panel was observed to come back scrolled to the very top once the dialog closed — on both Apply *and* Cancel, which rules out the edit itself as the cause (Cancel never touches the document) and points at the focus/visibility round trip instead, whatever its exact internal mechanism.

Fixed the same defensive way `panelCursorLine` sidesteps not having a real `TextEditor` for this webview: `panelScrollTop: Map<vscode.WebviewPanel, number>` (module-level, alongside `panelCursorLine`, same lifecycle — set on `scroll-position`, deleted on `onDidDispose`) tracks each panel's last-known `view.scrollDOM.scrollTop`, kept current by a `scroll` listener on `view.scrollDOM` in `editor.js` (throttled to one `postMessage` per animation frame, mirroring how `sync` throttles its own full-document payload). Both call sites that can open the dialog — `vaultTool.editTaskAtCursor`'s handler and the `edit-task-at-location` message handler — read `panelScrollTop.get(panel)` *before* calling `tasksApi.editTaskAtLocation(...)`, then `postMessage({ type: 'restore-scroll', scrollTop })` back to that same panel in a `finally` block, so it fires whether the call threw, the user cancelled, or they applied changes. `editor.js`'s `restore-scroll` handler sets `view.scrollDOM.scrollTop` inside a double `requestAnimationFrame` rather than immediately — a single frame wasn't reliably enough to land *after* whatever was resetting it in the first place, since that reset was itself tied to the panel regaining focus/visibility, which happens asynchronously relative to when the message arrives.

The native VS Code editor path (`obsidianlike_tasks`' own `tasksManager.editTaskAtLine` CodeLens, for a note opened with "Open With → Text Editor" instead of this extension) needed the same fix independently — see the equivalent section in `obsidianlike_tasks/CLAUDE.md` (`editor.visibleRanges`/`revealRange` around `showTaskEditDialog` in `createOrEditTaskOnLine`), since it has a real `vscode.TextEditor` there instead of a webview.

**Why `Shift+Alt+E`, after two earlier chords failed** (this part of the investigation predates the redesign above and still applies — it's about the *chord*, not which mechanism dispatches it):
1. The first chord tried was `Ctrl+Shift+Enter`, which turned out to be VS Code's own default binding for "Insert Line Above" (`editor.action.insertLineBefore`). In a normal text editor that's harmless (an extension's keybinding for the same `when` wins over the built-in default), but for this `CustomTextEditorProvider` the symptom was that the key did *nothing at all* — not even reaching the webview's own JS — consistent with VS Code intercepting the keydown at the webview boundary just because *some* keybinding is registered for that chord, independent of whether its `when` clause actually applies (see `microsoft/vscode#165777` and `#241801`).
2. The second chord tried was `Ctrl+Alt+E` — no VS Code/extension conflict — but on any keyboard layout with an AltGr key (Spanish, German, French, and most other European layouts), the browser reports AltGr as `ctrlKey` and `altKey` both `true` simultaneously, the exact same signature as a literal Ctrl+Alt chord. On a Spanish keyboard, AltGr+E composes `€`, so pressing this "shortcut" just typed a euro sign into the document instead of firing the binding.
3. `Shift+Alt+E` has no default VS Code binding and no known extension conflict (checked against the official default-keybindings reference and every `package.json` under `~/.vscode/extensions/`), and Shift+Alt never collides with AltGr composition, which specifically requires Ctrl+Alt. Lesson for any future shortcut meant to fire while this custom editor has focus: besides checking for keybinding conflicts, avoid the `Ctrl+Alt+<letter>` pattern altogether — prefer `Ctrl+Shift+<letter>` or `Shift+Alt+<letter>` instead.

### Dataview query blocks — soft dependency on `angelCastro.obsidianlike-dataview`

A ` ```dataview ` / ` ```dql ` / ` ```dataviewjs ` fenced block (repo: `c:\git\obsidianlike_dataview`) is rendered the same way a ` ```tasks ` block is: the webview can't compute a vault-wide query result from the current document's AST alone, so it's an async round-trip through the host. Unlike the Tasks integration, the sibling extension doesn't hand back a structured DTO for this codebase to render itself — it hands back **ready-to-embed HTML**, because Dataview result shapes (`LIST`/`TABLE`/`TASK`/`CALENDAR`, with arbitrary user-chosen column expressions) are far more varied than the Tasks extension's fixed `TaskDTO`, and re-deriving a DOM renderer for all of them here wasn't worth it.

1. `getDataviewApi()` — same lazy/cache-on-success-only pattern as `getTasksApi()` above, targeting `vscode.extensions.getExtension('angelCastro.obsidianlike-dataview')`. Extension id note: that extension's `package.json` `name` is `obsidianlike-dataview` (repo folder: `c:\git\obsidianlike_dataview`).
2. `renderDataviewBlock(lang, query, currentFilePath)`: for `dataviewjs`, calls `api.runDataviewJs(query, currentFilePath)` (async — the sibling extension's sandbox supports top-level `await`) then `api.renderDataviewJsOutputHtml(result.output, result.error)`; for `dataview`/`dql`, calls `api.renderQueryResultHtml(api.runQuery(query))`. `api.runQuery` can throw synchronously (a DQL *parse* error, as opposed to a runtime error, which that extension already catches and returns as an `{ type: 'ERROR' }` result) — wrapped in a `try/catch` here that falls back to a `<div class="dv-error">` message, since an uncaught throw here would silently drop the reply and leave the widget stuck on "Cargando…" forever.
3. If the extension isn't installed/active at all, returns a fixed `<div class="dv-error">...no está instalada o activa.</div>` message instead of failing silently — same reasoning as `naiveToggleTaskLine` degrading gracefully, but there's no equivalent "naive" fallback for a query engine, so the degradation is a visible message rather than a silent no-op.
4. `DataviewExtensionApi` (declared locally, not imported from the other repo — same reasoning as `TasksExtensionApi`) only types the four methods and the one event actually called: `runQuery`, `runDataviewJs`, `renderQueryResultHtml`, `renderDataviewJsOutputHtml`, `onDidChangeIndex`. The real exported API (`obsidianlike_dataview/src/extension.ts`) is wider (`getAllPages`, `getPage`, `reindexWorkspace`, `findDataviewBlocks`) — unused here, so not declared.
5. `ensureSubscribedToDataviewChanges()` mirrors `ensureSubscribedToTasksChanges()` exactly (module-level single-flight flag, 5 retries 1.5s apart, called from the top of `resolveCustomTextEditor`): subscribes to the sibling extension's `onDidChangeIndex` (fires whenever any file anywhere in the vault is re-indexed — created/edited/deleted) and broadcasts `{ type: 'dataview-changed' }` to every panel in `activePanels`.

The returned HTML's navigable cells (`renderQueryResultHtml`'s `linkHtml()`) use `<a class="dv-link" href="#" data-wiki="...">`, not a `command:` URI — a plain `CustomTextEditorProvider` webview has no built-in handling for `command:` links (that only works in VS Code's own built-in Markdown preview). `data-wiki` is the same attribute `linkClickHandler` (below) already understands generically for table-cell wiki-links and ```tasks``` query backlinks, so clicking a dataview result link works with zero extra wiring on this side — the sibling extension's HTML plugs directly into an existing convention rather than this codebase adding a new one. If `obsidianlike_dataview`'s link markup ever changes away from `data-wiki`, this integration breaks silently (links render but don't navigate) — there's no compile-time coupling between the two repos.

### `dv.view(...)` — interactive DataviewJS scripts with a real DOM (`DataviewJsWidget`)

A ` ```dataviewjs ` block whose code contains a literal `dv.view(` call is **not** routed to `obsidianlike-dataview` above — that extension's `dv` (`src/dataviewjs/api.ts`) is a Node `vm` sandbox with no window at all: no `dv.container`, no `dv.view`, no `app`. It only supports one-shot report scripts (`dv.table`/`dv.list`/`dv.header`/...) that push into an output array later flattened to static HTML. `dv.view(name, input)` is Obsidian's mechanism for loading and running *another* script from the vault (e.g. a hand-written `tasks-timeline.js` Kanban) against a live DOM container and real vault I/O — structurally impossible for a headless Node sandbox to provide, so this codebase implements that case itself instead of extending the sibling extension.

`DV_VIEW_CALL_RE = /\bdv\s*\.\s*view\s*\(/` is tested against the block's raw `CodeText` in the same `FencedCode` branch that handles `dataview`/`dql`/`dataviewjs` (`livePreviewPlugin`, just above the existing branch): a match short-circuits to `DataviewJsWidget` and `return false`; no match falls through to the pre-existing `DataviewQueryWidget`/`obsidianlike-dataview` path completely unchanged. This is a deliberate coarse heuristic, not a parse — a script that merely mentions the string `dv.view(` in a comment would also be routed here, but a real dataviewjs script calling it in a comment is not a realistic case worth guarding against.

**Why `eq()` only compares raw source text, never loaded state (unlike `TasksQueryWidget`/`DataviewQueryWidget`)**: those two are stateless — every rebuild can safely re-render a table/list from scratch off a fresh data blob. A script loaded via `dv.view()` is the opposite: it typically constructs a class instance (drag & drop handlers, open dropdowns, a zoom slider, in-memory filter state) that must survive completely untouched across `livePreviewPlugin` rebuilds triggered by unrelated cursor moves, scrolling, or edits elsewhere in the document. `DataviewJsWidget.eq(other)` is therefore just `this.code === other.code` — as long as the block's own text is unchanged, CM6 never calls `toDOM()` again, so the running script instance (and its DOM) is left alone by construction, with no cache/rebuild-effect plumbing needed at all for this part.

**`toDOM()`'s nested `innerHost`, not `wrap` itself, is passed as `dv.container`**: `tasks-timeline.js` (and scripts following the same Dataview-block-recycling convention) build their own "persistent container" as a *sibling* of the container they're handed — `dvContainer.parentNode.insertBefore(persistentContainer, dvContainer.nextSibling)` — then hide the original. If `dv.container` were `wrap` (the exact node CM6's decoration owns), that sibling would be inserted *outside* CM6's managed subtree via raw DOM surgery, and would survive as an orphan the day the block reverts to raw source (cursor entering it) and the widget is torn down — CM6 only knows to detach/clean up `wrap`, not an unrelated sibling glued on next to it. Nesting one extra `innerHost` div inside `wrap`, and handing that (not `wrap`) to the script as `dv.container`, means any such sibling still lands *inside* `wrap` either way, so CM6's attach/detach lifecycle correctly covers the whole thing.

**`ignoreEvent()` returns `true` unconditionally** — unlike `TasksQueryWidget` (which only needs to shield one filter `<input>`, see above), the entire contents of this widget are script-owned and arbitrarily interactive (drag&drop, dropdowns, search boxes, checkboxes...). Any click here that CM6 treats as a normal document click would move the selection into the block's range, which the block-wide `isActive` gate (computed once per rebuild, same mechanism as `Table`/```` ```tasks ````) would read as "cursor inside" on the very next rebuild — reverting the whole block to raw source mid-interaction and destroying the running instance.

**The `app`/`Notice` shim** (`buildDataviewApp()`, module-level, built fresh once per `toDOM()` call): covers exactly the Obsidian API surface a script like `tasks-timeline.js` touches, nothing more —
- `vault.getMarkdownFiles()`/`getAbstractFileByPath(path)` — synchronous, built from the client-side `noteIndex` array (already kept live by the `note-index` message, see `NoteIndexEntry` above) via a `noteStub(entry)` helper (`{path, basename, extension: 'md'}`), matching real Obsidian's own synchronous signature for these two calls.
- `vault.read(file)`/`vault.modify(file, content)` — async, id-correlated round trips to the host (`dataview-read-file`/`dataview-write-file`, resolved via `pendingDataviewFileRequests: Map<id, {resolve, reject}>`, same shape as `pendingHeadingRequests`). **Deliberately never caches file content** on this side — real `app.vault.read()` always returns current content, and `tasks-timeline.js`'s own "🔄 Refrescar" button (already built into the unmodified script) depends on that staying true without any extra invalidation plumbing here.
- `workspace.getLeaf().openFile(file)` — fires `dataview-open-note` (no reply awaited) and returns a stub leaf with `view: undefined`; a script's `if (view && view.editor) view.editor.setCursor(...)`-style cursor positioning after opening harmlessly no-ops, since VS Code's custom editor doesn't expose a CM6 instance to the extension host the way Obsidian exposes `view.editor`.
- `metadataCache.getFirstLinkpathDest(linkpath)` — synchronous, resolved against `noteIndex` by filename (first match wins). Real Obsidian's own version is itself a synchronous lookup against an already-built index, so this matches both the required signature and the actual semantics closely enough.
- `class DataviewNotice` — a floating toast built and appended inside the webview itself (`.cm-dataviewjs-notice-container`, fixed bottom-right), not a `vscode.window.showInformationMessage` — closer to Obsidian's actual `Notice` look, and needs no host round trip.

**`dvView(name, input, parentContainer, appAdapter)`** implements `dv.view` itself: resolves the named script via `requestDataviewScript(name)` (a `Map<name, Array<resolve>>` waiter list — `dataviewScriptCache` never expires once populated, same "never proactively invalidated" precedent as `tasksQueryCache`; concurrent `dv.view()` calls for the same name dedupe onto one host round trip), creates a fresh child container per call (so sibling `dv.view()` calls never share one DOM subtree), and executes the fetched source via `new Function('dv','app','input','Notice', 'return (async()=>{...})()')(...)` — `input` is bound here (unlike the outer block, which receives none, matching Obsidian: only a script *loaded via* `dv.view()` gets an `input`). The returned `dv` object's own `.view` closes back over `dvView` with the *new* child container, so a loaded script calling `dv.view()` again recurses correctly with no extra code.

Host side (`resolveCustomTextEditor`'s `onDidReceiveMessage`, right after `run-dataview-query`): `dataview-resolve-script` resolves `**/${name}.js` vault-wide via `vscode.workspace.findFiles` (first match wins, same criterion as `resolveNoteUri`) and replies with the raw file content; `dataview-read-file`/`dataview-write-file` mirror the read/modify round trips above (write applies a whole-document `WorkspaceEdit` + `document.save()`, matching `applySync`'s pattern); `dataview-open-note` opens via `vscode.openWith`/`MarkdownDocumentProvider.viewType` **without** disposing `webviewPanel` — unlike `navigateToTarget` (used for wikilinks in the note's own prose, which *does* dispose the source panel), the note containing the dataviewjs block must stay open.

**CSP**: `buildHtml()`'s `script-src` needed `'unsafe-eval'` added (alongside the pre-existing `'unsafe-inline'`) — `new Function(...)` is a CSP-gated eval variant, and there's no way to run an arbitrary loaded script's text without it. Same trust level as Obsidian itself already grants that exact content (it's the user's own vault script, already executed with full privileges inside Obsidian), not a new exposure.

**Obsidian `HTMLElement.prototype` polyfill** (installed once, guarded by `if (HTMLElement.prototype.createEl) return;`): `createDiv`/`createEl`/`createSpan` (string-or-`DomElementInfo`-object dual signature, matching Obsidian's real API — `cls`, `text`, `attr`, `value`, `type`, `href`, `placeholder`, `prepend`), `empty`, `setText`, `appendText`, `addClass`/`removeClass`/`toggleClass`/`hasClass`. **`appendText` was missing from the first version of this polyfill** — found live (not by re-reading `tasks-timeline.js`'s source closely enough up front) via a real vault: the Kanban opened and its day columns rendered correctly (column/container creation doesn't touch task text), but zero tasks ever appeared despite dozens existing, and "🔄 Refrescar" didn't help either. Root cause: `TasksTimeline`'s constructor calls `this.init()` without `await`, and `init()` internally `await`s `render()` — so any exception inside the render chain becomes a silently-swallowed unhandled promise rejection, invisible in the widget itself. Only visible via the webview's own DevTools console (`Developer: Open Webview Developer Tools`), which showed `TypeError: container.appendText is not a function` thrown from `renderMarkdownText` on the very first task it tried to render, aborting the rest of that `render()` call (and therefore every column) silently. Fixed by adding the one missing method; grepped the rest of `tasks-timeline.js` for other non-standard Obsidian DOM calls (`createSvg`/`matchParent`/`setCssStyles`/etc.) and found none, so no further gaps are currently known — but the same silent-failure shape (constructor-time fire-and-forget `init()`) means any *future* missing shim method would fail the exact same invisible way, only diagnosable via the webview console.

### `open-note` / transclusion target resolution rules (`resolveNoteUri`)

A wiki-link or transclusion target may optionally carry one directory segment to disambiguate same-named notes, e.g. `[[folder/Note]]` or `![[folder/Note]]`. Only the immediate parent directory name is used as a hint — the rest of any longer path is ignored. It may also optionally carry a `#section` suffix (stripped by `splitTarget` before this resolution runs) pointing at an ATX heading of **any** level in the target file.

- **Resolution is vault-wide first, always** — `resolveNoteUri` runs a single `findFiles('**/Note.md')` across the *entire* workspace unconditionally; `currentDir`/the directory hint are never used to *narrow* that search, only to break a tie when it comes back with more than one match (see below). A note living in some third, unrelated directory — neither the linking note's own directory nor any hint — still resolves correctly. **This wasn't always true**: an earlier version checked `currentDir` first via `fs.existsSync` and only fell back to a vault-wide search when that missed, which sounds equivalent but wasn't quite — reported as a task-listing wikilink (which resolves relative to the *task's* directory via `baseDirOverride`/`data-wiki-base`, see below) still failing to find a target that existed in a *third* directory (neither the query note's dir nor the task's own dir) and silently creating a blank file next to the query block instead. Doing the vault-wide search unconditionally, with directory info used only as a tie-break, removes that whole class of bug rather than patching the specific case reported.
- **Exactly one vault-wide match**: that's the target, full stop — no directory hint or `currentDir` involved at all.
- **Multiple vault-wide matches** (two or more notes share the same name somewhere in the vault): resolved in this order — (1) an explicit directory hint (`[[folder/Note]]`, filtered to results whose immediate parent directory is named `folder`, case-insensitive) if one was given and matches; (2) a note in the same directory as the link, if the hint didn't match or wasn't given; (3) otherwise just the first result `findFiles` returned (an inherent, pre-existing ambiguity — see the "known limitation" note on the rename-fixup below).
- **No match anywhere**: `open-note` creates it — target directory is the hinted subfolder inside the *current* note's directory (created if missing), or the current note's directory itself if no hint was given; the new file is written empty. `open-transclusion`/`get-transclusion`/`get-headings` do **not** create anything — they report "not found" instead, since silently creating a blank note just to embed it makes no sense.
- **Glob-special characters in a note name are escaped** (`escapeGlob`, just `[`/`]`/`{`/`}` — the only characters bare-glob syntax treats specially without a preceding extglob prefix) before being interpolated into the `findFiles` pattern, so a literal note name like "Proyecto [2024]" is matched as plain text instead of the brackets being parsed as a glob character class and silently matching nothing (or something else). `(`/`)`/`*`/`?` are deliberately left un-escaped — not glob-special on their own, and a real `*`/`?` in a note name is rare enough not to be worth guarding against.
- **"The current note" isn't always the open document** — `navigateToTarget`'s `baseDirOverride` parameter lets a caller say "resolve this link as if it were written in *this other* file instead," which only matters now as the tie-break basis described above (never as a search scope). Needed for a `[[wikilink]]` inside a tasks-query row's description (`renderTaskRow`/`renderCell` in `editor.js`): the open document is the note holding the ```tasks``` block, but the link's text came from a *task*, which can live in any other file/directory in the vault. `renderCell(raw, basePath)` stamps `data-wiki-base="<workspace-relative path>"` onto every `[[wikilink]]` span it renders on behalf of another file; the generic `[data-wiki]` click handler forwards it as `open-note`'s `basePath` field; the host resolves that to an absolute directory (`path.dirname(path.join(vaultRoot, basePath))`) and passes it through as `baseDirOverride`. Absent (e.g. a wikilink typed directly into the open document, or inside a table cell authored in it) → falls back to the open document's own directory, unchanged from before.
- **Section resolution**: once the target file is found, `parseHeadings(text)` is scanned for a heading whose `text` matches `section` case-insensitively (exact match, not substring). No match → `open-note`/`open-transclusion` just skip the scroll (link still opens the note); `get-transclusion` replies with `error: 'section-not-found'`.

### `[[#section]]` — a link to a heading in the *current* document, not a note lookup at all

Reported: writing `[[#cabecera]]` (no note name, just a `#section`) rendered as a broken/missing link, and clicking it created a nameless `.md` file (just an extension, no basename). Root cause: `splitTarget('#cabecera')` correctly produces `notePart: '', section: 'cabecera'` — but every caller (`navigateToTarget`, `get-transclusion`) fed that empty `notePart` straight into `resolveNoteUri`/`resolveExternalFileUri`-style vault-wide lookups, which searched for a note literally named `''`. That never matches, so `open-note`'s create-if-missing path ran and wrote an empty file at `path.join(targetDir, '' + '.md')` — a file whose name is just `.md`.

- `navigateToTarget` (`src/extension.ts`) now special-cases `!notePart.trim()` **before** any `resolveNoteUri` call: the target is `selfUri` (defaults to `currentDocUri` — the document the link was typed into) rather than a vault-wide search result. It resolves the section the same way as any other target (`parseHeadings` + case-insensitive match) and either scrolls the *current* panel in place (no `vscode.openWith`, no disposing `sourcePanel` — the link's own document is already open right there) or, when `selfUri` differs from `currentDocUri` (see below), opens that other file and scrolls it, same as a normal cross-note link.
- `selfUri` exists specifically for a `[[#section]]` written inside a task's own description and rendered on behalf of that task inside a different note's ```tasks``` query row (`renderCell`'s `basePath`/`data-wiki-base` mechanism, same idea as `baseDirOverride` above but the *full* file, not just its directory) — the `open-note` handler now computes it from `basePath` alongside `baseDirOverride` and passes it through. Absent (the common case: a link typed directly into the open note) it falls back to `currentDocUri`.
- `get-transclusion` (for `![[#section]]`, a self-embed of one of the current note's own sections) mirrors this: `notePart.trim() ? await resolveNoteUri(...) : document.uri` — skipping the vault-wide lookup entirely when there's no note name to look up.
- Webview side: `noteTargetExists(rawTarget, state)` (`editor.js`) gained an optional `state` parameter (the CM6 state of the currently open document) used *only* for this case — when `notePart` is empty, existence is checked against `currentDocHeadings(state)` (a small ATX-heading scanner over the syntax tree, mirroring the host's `parseHeadings`) instead of `noteIndex` (which only ever tracks note *names*, so "" never matched anything there regardless of whether the section genuinely existed). `wikiLinkPlugin._build` passes `state` through at its one call site.
- `WikiSuggestView.recompute()`'s heading-search mode used to bail out entirely on an empty `notePart` (`if (!notePart) { this.close(); return; }`) — bare `[[#` closed the popup instead of offering anything, since the existing `requestHeadings`/`get-headings` round-trip has nothing to look up for an empty note name either. Now it special-cases the same way: `currentDocHeadings(this.view.state)` (the same function `noteTargetExists` uses) filtered by the typed query, no host round-trip needed at all since the current document's own text is already right here. `accept()` needed no changes — it already builds `[[${this.notePart}#${it.text}]]`, which naturally comes out as `[[#Heading]]` when `notePart` is `''`.

### Fixing up wiki-links after a note is renamed or moved (`onDidRenameFiles`)

Registered once in `activate()`: `vscode.workspace.onDidRenameFiles(e => { void handleWorkspaceRename(e.files); })`. This single listener covers **both** rename sources — the in-app title-edit (`rename` message handler calls `WorkspaceEdit.renameFile()`) and anything done in VS Code's own file explorer (drag, cut/paste, F2, moving an entire folder) — because both ultimately go through the same real filesystem rename that this event fires for. The webview's `rename` handler no longer fixes up links itself; there's a comment there pointing here instead.

- `handleWorkspaceRename(files)` — `onDidRenameFiles` gives one `{oldUri, newUri}` pair per renamed/moved *item*, which for a folder move is the folder itself, not each file inside it. If `newUri` is now a directory, `findMarkdownFiles(newUri.fsPath)` walks it and each found file's pre-move path is reconstructed by rebasing it onto `oldUri` (`path.relative(newUri.fsPath, newFilePath)` re-joined onto `oldUri.fsPath` — the subtree's internal structure doesn't change in a move, only the path prefix does). Non-`.md` files/folders containing none are skipped entirely — image links resolve by basename only (`getImageMap`), so moving an image never breaks a `![[file.png]]` reference and doesn't need this.
- `fixUpLinksForMovedNote(oldUri, newUri)` — unlike a blind name replace, a move can also change which directory a link needs to disambiguate against, so this must actually *resolve* each candidate link (against the vault as it was just before the move) rather than pattern-match on the old name alone:
  - Builds `oldFileList`: the current (post-move) vault-wide `.md` list with `newUri`'s path swapped back to `oldUri`'s — i.e. a snapshot of "the vault one moment before this specific move", since every other file's location is unaffected by it.
  - For every `[[...]]`/`![[...]]` in every *other* vault note (`WIKI_TARGET_RE = /(!?)\[\[([^\]]+)\]\]/g`), splits out any `|alias`/`#section` suffix (left untouched) and calls `resolvesToOldTarget(notePart, linkingDir, oldFileList, oldUri.fsPath)`, which replays `resolveNoteUri`'s exact vault-wide-first / dirHint-then-same-dir-tiebreak rules against `oldFileList` to check whether *this specific* link — not just any link sharing the old name — actually pointed at the file that moved. (Two different notes can share a basename in different folders; only a link that genuinely resolved to the moved file should be touched.)
  - A confirmed match is rewritten using the *new* location: no directory hint if the linking note and the moved note now share a directory, otherwise `path.basename(newDir)` — consistent with `splitDirHint`'s "only the immediate parent segment is ever used as a hint" rule, so the rewritten link resolves the exact same way any other hinted link would.
  - Only *incoming* links (from other notes) are fixed up — the moved note's own outgoing links aren't touched, even though its own "prefer a file in the same directory" resolution basis has also shifted. Out of scope for now; not requested.
- **Known limitation, shared with `open-note`'s existing "first match wins" ambiguity**: when a moved note has no directory hint pointing at it and multiple same-named notes exist elsewhere in the vault, `resolvesToOldTarget`'s "which one does this link actually mean" tie-break (a sorted list, for determinism) isn't guaranteed to match whatever order VS Code's real `findFiles` would have picked at `open-note` resolution time — this only matters when such a naming collision exists at all.

### `buildHtml(content, font, fontSize, noteIndex, cspSource, scriptUri, title, imageMap, breadcrumb)`

Generates the full webview HTML. Key points:
- CSP: `script-src ${cspSource} 'unsafe-inline'` (inline scripts are needed).
- `<style id="__obsidian-theme"></style>` — **empty** in HTML; filled via `theme-css` postMessage.
- `window.__vaultInitial = { content, font, fontSize, noteIndex, title, imageMap, breadcrumb }` — all initial data.
- The theme class sync script (`theme-dark`/`theme-light` on body) runs **after** `<body>` (at end of body, not in head) so `document.body` is never null.
- `#doc-breadcrumb` — clickable path segments above the title. Always visible (even for root-level files). Last segment (filename) is non-clickable. Directory segments send `reveal-path`.
- `#doc-title` — editable H1 that triggers rename on blur (800ms debounce).
- `#editor` — the CM6 mount point. Has `class="is-live-preview markdown-source-view mod-cm6"` so Obsidian theme selectors activate.

### `vsTheme` / `mdHighlight`

- `vsTheme`: `EditorView.theme({})` with CSS vars from VS Code (`--vscode-editor-*`) for all CM6 UI elements. Also defines `.cm-wiki-link`, `.cm-md-link`, `.cm-fold-indicator`, `.cm-fold-hidden`, `.cm-table-row-hidden`, table styles, **`.cm-header-1` through `.cm-header-6`** heading styles, and **`.cm-inline-code`/`.cm-code-block*`** code styles (see below).
- `mdHighlight`: `HighlightStyle` for bold, italic, strikethrough, links, code. Heading levels and `tags.monospace` (inline code + fenced code content) use **`class` only** (e.g. `{ tag: tags.heading1, class: 'cm-header cm-header-1' }`, `{ tag: tags.monospace, class: 'cm-inline-code' }`) — **critical**: when `class` is set in a HighlightStyle spec, CM6 ignores all CSS properties in that spec and uses the class name as-is. Their actual visual styles (fontSize, background, etc., via CSS vars) must therefore live in `vsTheme`, not in `mdHighlight`.

### Heading styling architecture (important)

Heading spans receive stable class names (`cm-header cm-header-1`…`cm-header-6`) via `mdHighlight`'s `class` property. The CSS for those classes lives in `vsTheme` and references Obsidian theme vars (`--h1-size`, `--h1-weight`, `--h1-color`, etc.) with fallback defaults. The `#editor` div has `class="is-live-preview markdown-source-view mod-cm6"` so Obsidian theme selectors like `.is-live-preview .HyperMD-header-1::before` work. The `cm-line` div for each heading gets `HyperMD-header HyperMD-header-N` via `Decoration.line()` in `livePreviewPlugin` (added before the active-line check, so it applies to all heading lines).

#### The `::before` color bar — width, height, and gutter placement (`vsTheme`)

The Border theme's own `.HyperMD-header-N::before` rule renders the colored vertical bar (`background-color: var(--h1-accent-color)` etc.) but gets width/height/spacing wrong for this port, so `vsTheme` overrides those specific properties with `!important` (color/radius/background stay theme-driven — only sizing and placement are ours):

- **Width**: `4px` (theme default is `3px`; tuned by eye, not tied to any theme var).
- **Height**: the theme sizes the bar off `calc(1.2em - 8px)` with a `translateY(4px)` nudge, which assumes the `::before`'s font-size context is the heading's own big rendered size — true in Obsidian's DOM (the pseudo lives directly on the `<h1>`), but not here, since the actual big font-size only lives on the child `.cm-header-N` span, not on the `.cm-line` the `::before` is attached to. `1.2em` there resolves against the small base editor font-size instead, coming out visibly shorter than the heading text. Fixed by giving `.HyperMD-header` `position: relative` and the bar `position: absolute; top:0; bottom:0` (no explicit height) — this stretches it to the line's real rendered height regardless of what `1.2em` would have resolved to.
- **Spacing to text**: since the bar is now absolutely positioned (out of normal flow), it no longer pushes the heading text via its own `margin-right` — `.HyperMD-header` instead gets `paddingLeft: 7px` (bar width + a 3px gap) so the text starts right after where the bar visually ends.

#### Fold indicator (H1/H2/H3 badge) — hover-only, empty SVG, positioned left of the bar

The Border theme reskins the fold triangle's `<svg class="svg-icon right-triangle">` into an "H1"/"H2"/"H3"-shaped glyph via `-webkit-mask-image` (see `foldPlugin`/`FoldToggle` below), matching Obsidian's own hover-only heading-level indicator. Getting this to look right took three changes in `vsTheme`, all scoped under `.HyperMD-header` so they only affect heading lines:

- **Hidden by default, revealed on hover**: `.cm-fold-indicator` defaults to `opacity: 0` (not a dim always-visible `0.35` like an earlier version had) and only reaches `opacity: 0.85` via `.cm-line:hover .cm-fold-indicator` — hovering anywhere on the heading line (the bar or the text; both are part of the same `.cm-line` box) reveals it, matching Obsidian's real behavior. The rule also keeps `.cm-fold-indicator:hover` itself for when the pointer is directly over the (now-visible) icon.
- **Positioned to the left of the bar, not after it**: a `::before` pseudo-element always paints before any of its element's real children, so as long as the fold-indicator widget is a normal in-flow child of `.HyperMD-header-N`, it can only ever render *after* the bar, never before it — there's no flow-order trick that puts a real child ahead of its own parent's `::before`. Fixed by taking the fold-indicator out of flow entirely: `.HyperMD-header .cm-fold-indicator` gets `position: absolute; left: -18px; top: 50%; transform: translateY(-50%)`, landing it in the gutter carved out by `.cm-content`'s own 28px left padding, to the left of the bar. The Border theme's own `transform: translateX(-8px)` on the inner `.collapse-indicator.collapse-icon` (tuned for Obsidian's own DOM/spacing) is cancelled with `transform: none !important` so it doesn't compound with this outer offset.
- **The SVG itself is empty**: `FoldToggle.toDOM()` still creates a real `<svg class="svg-icon right-triangle">` (so the Border theme's mask-image selectors have something to attach to and the click-to-fold hit area still exists) but with `width="0" height="0" viewBox="0 0 0 0"` and no `<path>` child — it draws nothing on its own. The visible "H1"/"H2"/"H3" glyph is entirely the Border theme's mask-image applied to that (CSS-sized, via `.cm-fold-indicator .svg-icon.right-triangle { width: 14px; height: 14px }`) empty box.

### Inline code vs. fenced code block styling (important)

`@lezer/markdown`'s default `styleTags` maps **both** `InlineCode` and a fenced code block's `CodeText` to the exact same `tags.monospace` tag (confirmed by inspecting `node_modules/@lezer/markdown/dist/index.js`: `"InlineCode CodeText": tags.monospace`) — there's no way to give them different treatment via `mdHighlight`'s tag-based matching alone, since CM6 can't distinguish which node produced a given tag once matched.

This mattered because the two need genuinely different visual treatment: standalone inline code (`` `text` ``) should look like a small chip (background + padding + border-radius), but applying that *same* per-character styling to a fenced block's `CodeText` — which, for a multi-line block, is one syntax node spanning several lines — rendered as a stack of visually disconnected chips instead of one block. (`Decoration.mark` ranges can't span a block boundary as a single DOM element; CM6 necessarily fragments a multi-line highlighted range into one `<span>` per visual line, and each fragment independently got the full chip styling.)

The fix, in two parts:
- `mdHighlight` gives `tags.monospace` a stable class (`cm-inline-code`) instead of inline CSS properties (same `class`-only pattern as headings). `vsTheme`'s `.cm-inline-code` rule has the chip styling, with `fontFamily: var(--code-font, var(--font-monospace, var(--vscode-editor-font-family, monospace)))` — `--code-font` is the user-configurable `obsidianLike.codeFont` setting (see "Configuration" below), empty by default so it falls through to the Obsidian theme/editor font. Font size uses the same pattern: `fontSize: var(--code-font-size, 14px)` — `--code-font-size` comes from `obsidianLike.codeFontSize` (default `14`), an absolute px size rather than the `em`-relative sizing used elsewhere, so it doesn't compound with `obsidianLike.markdownFont`'s own size. `.cm-code-block` uses the exact same `var(--code-font-size, 14px)` so inline code and fenced blocks always match.
- `livePreviewPlugin`'s `FencedCode` handling now treats a fenced code block **exactly like `Table`/```` ```tasks ```` ****: an all-or-nothing, block-wide gate, not per-line. It renders (fence lines collapsed, content lines boxed) only when *both* (a) the fence is actually closed, and (b) the cursor isn't on any line from the opening fence to the closing one, inclusive — otherwise `return false` immediately, leaving the whole block completely raw and editable (see "Why block-wide, not per-line" below for why the first version of this got both of those wrong).
  - The two fence lines (the ` ``` ` lines themselves) get the *exact* same dual treatment as `Table`'s collapsed rows / `foldPlugin`'s folded content elsewhere in this file: a full-line `Decoration.replace({})` plus a `Decoration.line({ class: 'cm-code-fence-hidden' })` (height:0, same technique as `.cm-table-row-hidden`/`.cm-fold-hidden`).
  - Every line **between** the two fence lines (the actual code) gets `cm-code-block` (`cm-code-block-first`/`-last` for the outer rounded corners/border on the first/last content line, or `cm-code-block-solo` when there's exactly one content line).
  - `vsTheme` has a plain descendant-selector override, `.cm-code-block .cm-inline-code { background: none; padding: 0; borderRadius: 0; }`, which cancels the chip look specifically for `CodeText` found inside a code-block line — ordinary CSS specificity (two classes beat one), no fighting over decoration nesting order needed.

`.cm-code-block`/`-first`/`-last`/`-solo`'s background/border/padding/radius/margin properties all carry `!important` — same defensive pattern `.cm-code-fence-hidden`/`.cm-table-row-hidden`/`.cm-fold-hidden` already use. Verified via a real `EditorView` running against the actual built `out/editor.bundle.js` in jsdom (a throwaway script, not checked in) that the decoration-building logic and generated CSS were both individually correct in isolation — the classes land on exactly the right lines, and the stylesheet CM6 injects for them is well-formed — yet the box still failed to render visibly in the real environment where this was reported. The one variable that jsdom test *didn't* have is an Obsidian theme: `theme-css` loads after CM6's own injected styles (see "Why theme CSS is sent via postMessage" above), and many themes reset background/border on generic editor-line selectors (`.cm-line { background: transparent; }` and similar) — a rule like that, arriving later in source order, doesn't need to be more *specific* than `.cm-code-block` to win the cascade if the theme also reaches for `!important`, which is common in real-world Obsidian themes. `!important` here is the same "we need this to actually stick regardless of what else is loaded" trade-off already made for the other hidden/collapsed-line classes.

**Restyled to actually look like Obsidian's own default code blocks, per a reference screenshot** — reported as looking wrong (flat solid-gray box, tight padding) compared to Obsidian's light, airy card with a faint dot-grid texture. `.cm-code-block` now layers a subtle `backgroundImage: radial-gradient(circle, ... 1px, transparent 1px)` dot pattern (11px grid) on top of the existing `--code-background`-driven base color, with wider padding (`18px` horizontal, `12px`/`14px` vertical via `-first`/`-last`/`-solo`) and a larger border-radius (`10px`, up from `6px`) for a softer card shape; border color was also lightened (`rgba(128,128,128,0.18)`, down from `0.35`) to read as a subtle outline rather than a hard line. Since each content line is still its own separate `.cm-line` element (not one shared container for the whole block — see "Why block-wide, not per-line" below for why that's the design), the dot pattern isn't pixel-perfectly continuous across a multi-line block the way a single real `<pre>` element's texture would be in Obsidian itself, but at an 11px grain the seam between lines isn't visually noticeable in practice. **A copy-to-clipboard button (visible in the reference, top-right corner of the block) was deliberately not attempted alongside this** — adding a widget at the fence-open line's position to host it would put a `Decoration.widget` at the exact same zero-length point as that line's own `hiddenLineDeco` line decoration, the identical "two decorations at one point, only one survives" `RangeSetBuilder` collision already hit (and fixed) twice elsewhere in this file — see the blank-line-when-folding and nested-heading-fold-toggle bugs, both in `foldPlugin`'s section — so it wasn't worth risking a rushed third instance of that same bug just to ship the button in the same pass as the styling fix.

**Two follow-up reports against this same restyle**: the dot pattern "se ve fatal... el fondo es gris con puntos" (reads as an unflattering gray box with dots rather than a subtle texture) — the first version's dot alpha (`0.28`, and reusing `--table-border-color` as the dot's own color, which a theme may define as a fully opaque line color never meant for a repeating fill) was simply too strong; dropped to a fixed `rgba(128,128,128,0.14)`, independent of `--table-border-color` entirely. **The second report was the more interesting bug**: "no se está usando la fuente monotype de la configuración" (the configured monospace font isn't applied at all) — a genuine, separate CSS custom-property bug, not a restyling miss. `root.style.setProperty('--code-font', init.codeFont || '')` (init) and the `font-update` handler's equivalent line always called `setProperty`, even when the value was `''` (the common case — no custom `obsidianLike.codeFont` configured). `var(--code-font, fallback)` only substitutes `fallback` when `--code-font` is **undefined** — a custom property explicitly set to an empty string still counts as "set" (to the empty token stream), so `font-family: var(--code-font, var(--font-monospace, ...))` with `--code-font: ;` doesn't fall through the chain at all: the whole `font-family` declaration becomes invalid at computed-value time and reverts to its *inherited* value instead, silently skipping every fallback including the final hardcoded `monospace`. The exact same bug affects `--md-font` (the main editor font setting), which shares the identical `|| ''` pattern — fixed alongside `--code-font` even though it wasn't the reported symptom, since it's the same bug with the same fix. **Fix**: `setFontVar(name, value)` (`webview-src/editor.js`, right above the `--md-font`/`--code-font` init lines) calls `removeProperty` instead of `setProperty('', ...)` for a falsy value, so the custom property is genuinely undefined and `var()`'s fallback chain actually runs. Used at both call sites (init and `font-update`) for both variables; the `font-update` handler's own `--md-font` branch also changed from `if (msg.font)` to `if (msg.font !== undefined)`, since the old truthy-only check meant clearing a custom font back to the default silently didn't take effect until reload.

**Third report, same thread: the dots came back up again — "¿por qué el fondo... tiene puntos? Quítalos"** (why does the background have dots, remove them) — the fainter `0.14`-alpha dot pattern from the fix above was still, on reflection, not wanted at all. Removed the `backgroundImage`/`backgroundSize` dot-grid entirely, leaving `.cm-code-block` with just the plain `--code-background`-driven flat color. In hindsight not a surprising outcome — the dot texture was always an attempt to *literally* match one reference screenshot's specific visual grain, layered on top of decorations that are individually one-`.cm-line`-per-row rather than one shared `<pre>` container, so it was never going to reproduce that texture perfectly to begin with (see the block-wide-vs-per-line design note elsewhere in this section) — simpler to just not have it.

**Fourth report, different bug this time: raw (active/being-edited) fenced code block content had "un estilo raro (se aplica un background solo al texto)"** — a per-line chip/pill background around just the text, not the reported dot-texture bug. Screenshot showed a raw block (both `` ``` `` fences visible, cursor somewhere inside — expected, per the block-wide "raw while active" design) where each content line's own text sat inside a small gray rounded-rectangle, one per line, reading as a stack of disconnected pills. Root cause: raw mode intentionally applies *no* `livePreviewPlugin` decorations at all to a fenced block while the cursor is inside it (`if (isActive) { return false; }`, before this fix) — but `mdHighlight`'s own unconditional `syntaxHighlighting()` still tags a fenced block's `CodeText` with the exact same `tags.monospace` → `cm-inline-code` class `InlineCode` gets (the same lezer quirk this whole section is about), and since a highlighted range can't span a block boundary as one DOM element, a multi-line `CodeText` node fragments into one `<span class="cm-inline-code">` per visual line — each independently getting the full chip look (background/padding/border-radius) meant for a short standalone `` `inline code` `` span. The existing `.cm-code-block .cm-inline-code` override only cancels this for the *rendered/collapsed* case (that class is never applied while raw), so it never reached this scenario.
- **Fix**: the `isActive` branch (previously a bare `return false`) now first pushes a new, minimal `Decoration.line({ class: 'cm-raw-code-line' })` over every line from the opening fence through the closing one, *then* returns false — still fully raw/unrendered otherwise, this is purely an additive marker for CSS purposes. `vsTheme` gets a matching `.cm-raw-code-line .cm-inline-code` rule with the identical cancellation as `.cm-code-block .cm-inline-code`. Deliberately a **separate** class from `.cm-code-block` rather than reusing it — `.cm-code-block` also carries the collapsed box's own background/border/padding, which raw mode must not get (confirmed by the report itself: raw mode's plain-text appearance was explicitly fine, only the per-line chip background was the complaint).
- **Placed after `if (!closeMark) return false`, not before it** — deliberately: this whole `FencedCode` branch has a documented history of freezing the editor (see "Bug 1" below) from computing a closing line via `node.to`/`doc.length` math while a fence is still *unclosed* (being actively typed, with no second `CodeMark` yet). This fix only ever runs once `closeMark` is already confirmed to exist, using the exact same `fromLine`/`toLine` the rest of this branch already trusts — it doesn't introduce any new positional computation of its own, and doesn't run at all for an unclosed fence. Verified with a real `EditorView` in jsdom (throwaway script, not checked in) against three cases: a closed fence with the cursor inside (the reported bug — correctly marks every line, no crash), a still-open/unclosed fence (correctly bails immediately, zero marker lines, no crash — confirming this didn't reintroduce the freeze), and a closed fence with the cursor entirely outside it (correctly applies no marker at all, leaving the existing `.cm-code-block` rendering path untouched).

#### Why block-wide, not per-line — two bugs from the same root cause

Two versions of this got progressively closer before landing on the current, correct design; both mistakes trace back to treating a fenced code block's rendering decision per-line instead of as one atomic unit, the way `Table`/```` ```tasks ```` already correctly do.

**Bug 1 — deriving the closing line from `node.to`/`doc.length` instead of a real `CodeMark`.** The very first version (and, it turns out, the *pre-existing* ` ```tasks ` query-block handling right next to it, which had always computed things the same way) derived "the closing fence's line" as `state.doc.lineAt(Math.max(node.from, Math.min(node.to, state.doc.length) - 1))`. This is wrong specifically **while the fence is still open** (being actively typed, not yet closed): lezer-markdown extends an unclosed `FencedCode` node all the way to end-of-document, so the instant the user presses Enter after typing content and lands on a fresh, still-empty line, `node.to` sits exactly at `doc.length` — pulling back by 1 to "stay inside the node" walks *past* that empty (but real, cursor-occupied) line and back onto the actual content line typed just before it. That content line then gets misidentified as "the closing fence" and — because it isn't the active line (the cursor is one line further down, on the line this computation skipped past) — gets collapsed to zero height. That alone is a visible bug (typed text vanishing), but the real damage: collapsing a line the cursor's neighboring navigation depends on while CM6 is mid-layout is severe enough to corrupt its own cursor/selection tracking outright — reported symptom was total input lockup (arrow keys, clicks, even Enter doing nothing) that persisted until the document was closed and reopened. Fix, part one: never derive the closing line from `node.to`/`doc.length` math — check `node.node.getChildren('CodeMark')` instead. lezer-markdown only emits a *second* `CodeMark` once a real closing ` ``` ` has been parsed (confirmed empirically: 1 mark while open, 2 once closed, regardless of how much content sits in between); `state.doc.lineAt(closeMark.from)` then gives the real closing line unambiguously.

**Bug 2 — a second version still hid the *opening* fence's marker text per-line even while the block was unclosed.** Gating the new box/collapse logic on `closeMark` (bug 1's fix) wasn't sufficient by itself: while unclosed, that new logic correctly declined to run, but the tree walk still fell through into `FencedCode`'s children afterward, and the pre-existing, unrelated generic non-active-line `CodeMark`-hiding rule (further down in the same walk, originally written for `InlineCode`'s marks) still matched the *opening* mark and blanked it the moment the cursor moved past it — even with no closing fence in sight yet. Fix, part two: make the whole node's fate — raw vs. rendered — a single up-front decision, computed once, exactly mirroring `Table`/```` ```tasks ````'s existing block-wide `isActive` scan (`for (line = fromLine; line <= toLine; line++) if (active.has(line)) isActive = true`) rather than per-line `active.has(...)` checks scattered through the fence/content handling. If the fence isn't closed yet, or the cursor sits anywhere from the opening line to the closing line inclusive, `return false` immediately and let nothing further in this walk touch the node's children at all — the entire block, opening marker included, stays fully raw until the cursor has moved completely outside a properly closed block.

### `livePreviewPlugin`

`ViewPlugin` that hides markdown syntax markers on non-active lines via syntax tree iteration. Active lines = lines containing any cursor selection anchor or head.

Before the tree walk even starts, `_build(view)` also handles the document's leading YAML frontmatter block (if any) as a single unconditional unit — see `PropertiesWidget` below — and the walk's `enter(node)` bails out (`return false`) for any node **fully contained inside** that block (`node.to <= fm.to`), so lezer's normal parsing of its content (a `---` `HorizontalRule`, `tags:` as a `Paragraph`, `  - x` as a `BulletList`/`ListItem`, ...) never also decorates it.

**This check used to compare only `node.from`'s own line against the frontmatter's closing line (`state.doc.lineAt(node.from).number <= fmCloseLine`) — a long-standing bug, not something recent, that silently disabled live-preview rendering for the *entire rest of the document* on any note with a frontmatter block.** The syntax tree's own root `Document` node always starts on line 1 — which, whenever a frontmatter exists at all, is always "<= fmCloseLine" — so `enter()` returned `false` for the *root node itself* the very first time it ran. Returning `false` stops the walk from descending into that node's children at all, meaning nothing after the frontmatter — headings, lists, fenced code blocks, tables, wiki-links, everything — was ever visited by this tree walk again, for the rest of the document. Reported as "cuando hay un frontmatter en la página, los estilos dejan de aplicarse": every heading showed its raw `#`, every list its raw `*`/`-`, every fenced code block its raw backticks, all unconditionally, on any frontmatter-containing note — confirmed with a real `EditorState` and a full syntax-tree dump (throwaway script, not checked in) whose very first line was `BAIL Document from=0 to=<wholeDocLength>`. Fixed by checking `node.to <= fm.to` instead — whether the node's *entire span* sits inside the frontmatter, not just where it starts — which correctly still bails on the frontmatter's own internal `HorizontalRule`/`Paragraph`/`BulletList` nodes (each of those is itself fully contained within `[0, fm.to]`) while leaving `Document` — and everything after the frontmatter — alone, confirmed with the same tree dump.

`_build(view)` iterates the syntax tree over the current viewport:
- **ATXHeading[1-6]** — `Decoration.line({ class: 'HyperMD-header HyperMD-header-N' })` on every heading line (active or not), enabling Obsidian theme CSS selectors. Does not `return false` so children are still visited.
- **Tables** — first line replaced by `Decoration.replace({ widget: TableWidget })` (single-line, no `block:true`). Remaining table lines replaced with `Decoration.replace({})` + `Decoration.line({ class: 'cm-table-row-hidden' })` to collapse height. Unlike every other block widget here, this is **not** gated behind `active.has(ln)` — see `TableWidget`'s own section below for why.
- **HorizontalRule** (`---`/`***`/`___` alone on a line) — on a non-active line, the whole line is replaced by `Decoration.replace({ widget: new HorizontalRuleWidget() })`, a plain `<hr class="cm-hr">` (`vsTheme`'s rule is just a themed `border-top`, no other chrome). Gated behind the same `active.has(ln)` check every other marker here uses, checked *after* it (matches the convention of everything below rather than tables' own deliberate exception). Doesn't need any special-casing against the frontmatter's own `---` delimiters — those are already fully bailed out of this whole walk above (`node.to <= fm.to`), so a `HorizontalRule` node only ever reaches this branch when it's a real thematic break in the document body.
- **HeaderMark** — `Decoration.replace({})` hides `## ` prefix (and trailing space) on non-active lines.
- **EmphasisMark, CodeMark, StrikethroughMark** — `Decoration.replace({})` hides the markers on non-active lines.
- **LinkMark, URL** — returns `false` only (no hiding); handled by `mdLinkPlugin` instead.
- **`Link` nodes shaped like a `[[wiki-link]]`'s inner bracket pair, only while that link is "activated"** — marked `cm-wiki-link-raw`; see below.

**`block: true` decorations are permanently banned** — they crash CM6's `measureVisibleLineHeights` / `coordsAt`. All multi-line hiding uses `Decoration.line({ class: '...' })` with `height: 0` CSS.

**Per-token raw/rendered switching (`isLinkActivated`)**: `getActiveLines(state)` (→ `active: Set<number>`, whole-line granularity) is still what gates most markdown-marker hiding (headings, emphasis, code, strikethrough — see above), matching Obsidian's own simplified live-preview model for those. `[[wiki-link]]`s are a deliberate exception on two axes: per-token rather than per-line (with several `[[links]]` on one line, only one should ever stay raw at a time), and gated by *edit activation* rather than mere cursor presence (see the "wiki-link activation" section under `wikiLinkPlugin` below for the full mechanism and why cursor presence alone — including a link merely passed through by `moveVerticalByLine` — was replaced). `isLinkActivated(from, to)` is used for exactly the two wiki-link-related decisions instead of `active.has(ln)`: `wikiLinkPlugin`'s own match-skip check (below) and the `cm-wiki-link-raw` detection here. Both are called with the *full* `[[...]]` span (`node.from - 1` through `node.to + 1`, since `node`/`node.to` below refer to the *inner* `[Foo]` Link node — see next paragraph).

**`[[wiki-link]]` inner-bracket coloring while editing (`.cm-wiki-link-raw`)**: `[[Foo]]` isn't real CommonMark syntax, but lezer-markdown parses its *inner* `[Foo]` as an ordinary shortcut-reference `Link` node (with its own `LinkMark` children) purely because it's indistinguishable from single-bracket link syntax — confirmed by dumping the syntax tree for `[[Foo]]`, which produces a `Link` node spanning just the inner `[Foo]` plus two `LinkMark` children, while the *outer* `[` and `]` fall completely outside any node. Since `mdHighlight` colors `tags.link`/`tags.processingInstruction` unconditionally (CM6's own `syntaxHighlighting()`, independent of and always active regardless of what `livePreviewPlugin`/`wikiLinkPlugin` decide to hide), the inner brackets ended up colored + smaller font-size while the outer ones stayed plain text color — a visible mismatch while actively editing the line (non-active lines never showed this, since `wikiLinkPlugin`'s own decorations already replace/hide the whole `[[...]]` span). Fixed by detecting a `Link` node immediately preceded by `[` and immediately followed by `]` (the signature of being the inner pair of a doubled bracket), gated by `isLinkActivated` on the link's full outer span (see above), and marking it `cm-wiki-link-raw`. Two things this deliberately does not touch: `![[Foo]]` (a transclusion) — the leading `!` makes the *outer* `Image` node wrap everything, so every character including its brackets already gets uniform `tags.link` styling with nothing to fix; detected via `node.node.parent.name !== 'Image'`. And it only applies to the currently-activated link — with several `[[links]]` on the active line, the others still get `wikiLinkPlugin`'s hidden-brackets + `cm-wiki-link` styling instead, since this decoration must not stack on top of that (the `!important` reset would cancel `wikiLinkPlugin`'s blue/underline styling on an already-resolved link).

**Why `.cm-wiki-link-raw`'s CSS also targets `*` (every descendant), not just the class itself**: CM6 renders overlapping mark decorations from *different* extensions (here: this ViewPlugin's own decoration vs. `syntaxHighlighting(mdHighlight)`'s, a separate extension) as genuinely **nested** `<span>`s, not a single flat span with combined classes — confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): `<span class="cm-wiki-link-raw"><span class="tok-link tok-processingInstruction">[</span>Foo<span class="tok-link tok-processingInstruction">]</span></span>`. The bracket/text characters live on the *inner* spans, each with their own explicit `color`/`font-size` coming straight from `mdHighlight`. A child element's own explicit CSS property value always wins over an ancestor's for that same property, `!important` or not — `!important` only affects how a rule competes against *other rules matching that same element*, it doesn't make an ancestor's value propagate past a descendant that has its own matching rule; "inherit" is strictly a fallback for when nothing else matches. So a rule of just `.cm-wiki-link-raw { color: inherit !important }` silently did nothing for the nested spans — only the outer element (which has no text of its own) ever saw it. Fixed by using `.cm-wiki-link-raw, .cm-wiki-link-raw *` as the selector, so the same reset also matches the nested spans directly, at which point `!important` correctly wins against `mdHighlight`'s plain (non-`!important`) generated classes on those same elements.

**A bare `[text]` (no `(url)` after it, not a `[[wiki-link]]`'s own inner brackets) got the exact same false-positive coloring — `.cm-plain-brackets` fixes it the same way, unconditionally.** Confirmed via a syntax tree dump: lezer-markdown parses *any* `[...]` shape as a shortcut-reference `Link` node regardless of whether a matching `[label]: url` reference definition exists anywhere in the document, so `mdHighlight`'s unconditional `tags.link` styling colors it and makes it look clickable even though (per the same dump) a shortcut-reference `Link` node with no URL has no `URL` child at all — `linkClickHandler`'s `findUrlAtPos` was never going to find anything to navigate to; the bug was purely cosmetic, but misleadingly so. Three `Link` shapes needed telling apart, all confirmed by the same dump: a genuine `[text](url)` link's node span extends through the closing `)` (`state.doc.sliceString(node.to - 1, node.to) === ')'`), swallowing the parenthesized URL into the *same* node — a bare `[text]`'s span stops right at `]`, so this check alone separates the two. A `[[wiki-link]]`'s own inner brackets (handled just above) are structurally identical to a bare `[text]` at the `Link`-node level — same span shape, no `URL` child either — so what actually tells them apart is purely the *outer* characters immediately surrounding the node (another literal `[`/`]` pair, checked via `sliceString(node.from-1, node.from)`/`sliceString(node.to, node.to+1)`), which the two checks are written to be mutually exclusive on. One more guard, `!(!activeLinkClosed && activeLinkFrom === node.from - 1)`, avoids a one-keystroke flicker while actively typing a not-yet-closed `[[note` — its momentary single-`]` parse state would otherwise transiently match "bare bracket" too, for the instant between typing the two `[` and before the matching `]]` is complete.

**Follow-up bug: a bracket inside a heading lost the heading's font-size, shrinking to the surrounding paragraph size.** Both `.cm-wiki-link-raw` and `.cm-plain-brackets` reset `font-size: inherit !important` alongside `color`/`text-decoration`/`cursor`, on `.selector, .selector *` — needed for those other properties, to beat `mdHighlight`'s own generated classes on the *nested* span (see "Why `.cm-wiki-link-raw`'s CSS also targets `*`" above). But `highlightTree` was confirmed (via a throwaway script feeding `mdHighlight` directly, not through a full `EditorView`) to combine *every* currently-active tag's classes onto **one** span rather than nesting them separately — a bracket inside an H1 gets a single span classed `cm-header cm-header-1 tok-link tok-processingInstruction`, all together. `.cm-header-1`'s own `font-size` rule (in `vsTheme`) isn't `!important`, though — so the blanket `!important` reset silently beat it too, on that same element, collapsing the heading-sized text back down to `inherit` (the paragraph default) the instant it sat inside `[...]`.
- Fixed by dropping `font-size` from that shared class rule entirely and computing the *correct* value per-instance instead, applied as an inline `style` attribute (wins regardless of stylesheet order or `!important` ties, same reasoning as the list hanging-indent fix below): `headingLevelOf(node)` walks the syntax tree *up* from the `Link` node looking for an ancestor `ATXHeading[1-6]` (confirmed via syntax tree dump: an inline node's `Link` is a genuine descendant of its enclosing heading node, so this reliably finds it), and `plainBracketFontSizeStyle(node)` returns `font-size: var(--h{level}-size, {default}) !important` when found — `HEADING_SIZE_DEFAULT` mirrors `.cm-header-1..6`'s own fallback values exactly — or `font-size: inherit !important` otherwise (the original, still-correct behavior for a bracket in a plain paragraph).

**Follow-up bug: `[SANPT] Sync Seguridad` (a heading whose text starts with a bracketed prefix) rendered the bracketed part in a visibly different, plainer typeface than the rest of the same line.** The font-size-only fix above worked for size, but `.cm-header-N`'s own rule also carries `font-weight`/`font-family`/`line-height`/`color`/`font-style` — none of which `plainBracketFontSizeStyle` restored, so a bracket sitting inside a heading fell back to the editor's plain body font/weight for everything *except* size, reading as a mismatched typeface glued onto the theme's actual (often distinctive) heading font right next to it.
- First attempted fix: widen `plainBracketFontSizeStyle` to restore *every* one of `.cm-header-N`'s properties (`HEADING_STYLE_DEFAULT` replacing the size-only `HEADING_SIZE_DEFAULT`), same inline-`style`-on-the-outer-span mechanism, just more properties.

**This introduced a second, worse regression, reported immediately: "si abro y cierro un corchete en una cabecera... los corchetes y lo que hay encerrado en ellos se ven enormes"** — opening and closing a bracket on a heading line made the brackets *and* their enclosed text render at nearly triple the heading's own size. Root-caused this time with a real `EditorView` in **jsdom** (a throwaway script this session actually got working, unlike the usual "jsdom smoke test fails on this machine's Node version" caveat elsewhere in this file — see its own note below) that loaded the real compiled `out/editor.bundle.js` against `# [Test] Heading` and dumped both the resulting DOM and every injected stylesheet's actual CSS text:
- Every one of the bracket's own inner pieces — `[`, the enclosed text, `]` — turned out to each get their *own* nested `<span class="cm-header cm-header-1 ...">` from mdHighlight's `highlightTree`: heading tagging reaches a bracket's contents exactly the same way it reaches the rest of the heading line (confirmed directly — the earlier assumption in this file that only the bracket *marks* get re-tagged inside a heading, and the enclosed text stays bare, turned out not to hold for this bundle/lezer-markdown version).
- The dumped stylesheet showed `.ͼo .cm-header-1 { font-size: var(--h1-size, 1.75em); ... }` — a **two-class** compound selector (`.ͼo` is `vsTheme`'s own generated editor-root class) — versus tags.link/tags.url/tags.processingInstruction's own auto-generated combo classes (`.ͼs`, `.ͼv`, ...), each a **single class**. By plain CSS specificity (0,2,0 beats 0,1,0), `.cm-header-1`'s font-size rule *already* wins on those inner spans, unconditionally, regardless of stylesheet injection order — meaning **every inner span was already rendering at the correct heading size on its own, with no help needed from anything wrapping it.**
- The inline style this function returns is applied to the *outer* wrapping span (`cm-wiki-link-raw`/`cm-plain-brackets`, added by `livePreviewPlugin` — a genuinely different, outer element than the inner mdHighlight-generated spans, confirmed nested not merged by the same dump — see "Why `.cm-wiki-link-raw`'s CSS also targets `*`" above). Its own font-size was *also* declared in `em`, relative to *its own* parent's font-size (the heading's `.cm-line`) — and the inner spans' `1.75em` is in turn relative to *that already-enlarged* outer span. The two multiplied together (≈1.75 × 1.75 ≈ 3×) instead of composing to the one intended heading size.
- **The original bug this whole mechanism was introduced to fix (the "shrinks to paragraph size" one, two entries up) was never actually about the *outer* span's own font-size at all** — it was about an *earlier* version of the shared reset rule applying `font-size: inherit !important` via a `.selector *` **descendant** selector, which *does* reach the inner spans directly (as a real selector match on that exact element, not "cascading down from an ancestor") and *does* beat their own non-`!important` `.cm-header-1` rule regardless of specificity, since importance always wins before specificity is even considered. That part of the fix — dropping `font-size` from the shared `.selector, .selector *` reset — was correct and is still exactly right. Restoring it a second time via the *outer* span's own inline style, on top of that, never fixed anything a real heading-wrapped bracket needed; it just added a second, compounding source of the same property.
- **Fix**: `plainBracketFontSizeStyle` now unconditionally returns `''` — no inline style at all. `headingLevelOf`/`HEADING_STYLE_DEFAULT` were removed as now-dead code. Verified with the same jsdom harness: `.cm-plain-brackets`'s own `style` attribute is empty, while its children still carry `cm-header cm-header-1` (plus whichever combo class) exactly as before, so they still resolve their own size/weight/family/color correctly via the specificity argument above — with nothing left to compound against.

**A jsdom test that actually ran, for once** — most "verified via jsdom" notes elsewhere in this file carry a caveat that the smoke test fails outright on this machine's installed Node version (`ERR_REQUIRE_ESM`/`getClientRects is not a function` from newer jsdom releases' own dependency chain). This one worked by installing an older, compatible release (`npm install --no-save jsdom@24`, never added to `package.json`/committed) and loading the *real* built bundle as an actual `<script>` tag inside a jsdom `Window` (`runScripts: 'dangerously'`, with `window.__vaultInitial`/`acquireVsCodeApi` stubbed the same way the real host page provides them) rather than trying to import internals from the ES-module source directly — CM6 still throws on a handful of layout-measurement calls jsdom can't fully back (`coordsIn`/`getClientRects`), but that only affects some *measurement* code paths, not the actual decoration-building/DOM-construction this was being used to inspect, so the relevant DOM and stylesheet content came through intact regardless.

### `TableWidget` / `renderCell(raw)`

`TableWidget` is a `WidgetType` rendered as a single-line `Decoration.replace` on the first table line. Renders a full `<table>` with `<th>` / `<td>` cells.

**Cells are directly `contentEditable`, and the table renders unconditionally — it no longer ever
falls back to raw `| pipe | source |` text.** Every other block widget in this file (headings'
markers, `[[wiki-links]]`, code fences) only renders while the cursor is *elsewhere*, on the theory
that editing requires seeing/typing the underlying markdown syntax directly — `livePreviewPlugin`'s
old `Table` branch followed that same pattern (`isActive` check, skip rendering `TableWidget`
entirely when the cursor sat on any of the table's lines). For a table that meant the *only* way to
edit a cell was via raw pipe-delimited source, which is exactly what was reported as "no way to fill
the table with data — the cursor landing on any of its lines just drops into raw markdown mode."
Fixed by giving cells their own way to accept input instead, the same way `PropertiesWidget`'s real
`<input>` fields already do for frontmatter (also rendered unconditionally, also never falls back to
raw YAML) — and once cells can be edited directly, there's no reason left to ever fall back at all.
- **`commitTableCell(view, tableFrom, isHeader, rowIndex, colIndex, value)`** writes one cell's new
  value back via `mutateTableAt(view, tableFrom + 1, ...)` — the exact same helper the row/column
  context-menu actions already use (see below), just mutating a single `t.header[i]`/`t.rows[r][i]`
  entry instead of splicing rows/columns. `tableFrom + 1` is just a stable position anchor inside
  the table for `findTableRangeAt` to re-resolve the table's *current* range from — not the cell's
  own position, which isn't needed here since the whole table is always replaced as one unit anyway.
- **Cells show *rendered* inline formatting (bold/italic/strikethrough/inline-code/`==highlight==`) while not focused, and swap to the raw markdown text on focus** (`renderTableCellDisplay`, just above `commitTableCell`) — reported as "los estilos *negrita* y `code` no se están aplicando" against an earlier version of this widget that deliberately rendered plain, unformatted text for every cell regardless of focus (a `contentEditable` region holding rendered sub-elements makes committing an edit back to markdown harder — would need an HTML→markdown round-trip instead of just reading `textContent` — so that first version traded rich rendering away for a simpler, more robust round-trip). Fixed with the same "raw while active, rendered otherwise" convention used everywhere else in this file (headings, wiki-links, ...), just applied per-cell instead of per-line: `wireCell`'s `focus` listener sets `cell.textContent` to the *raw* stored value (`t.header[colIndex]`/`t.rows[rowIndex][colIndex]`, so the user edits real markdown syntax), and its `blur` listener — after committing if the value changed — sets `cell.innerHTML = renderTableCellDisplay(value)` to restore the rendered look; the cell's own construction (`th.innerHTML`/`td.innerHTML`) uses the same function so a freshly-rendered (never-focused) table already shows formatting.
  - `renderTableCellDisplay` is a **deliberately narrower function than `renderCell`**, not a call to it: `renderCell` also renders wiki-links/`#tags`/bare-URLs as blue, clickable-*looking* spans, but a cell's own `mousedown` listener calls `e.stopPropagation()` (see below), so a click on one of those never bubbles up to `linkClickHandler`'s `[data-wiki]`/`.cm-md-link` handling — rendering them here would look interactive while doing nothing at all on click, worse than plain text. Bold/italic/strikethrough/code/highlight have no such click affordance to fake, so they're the only things this function renders.
- **Tab / Shift+Tab / Enter navigation**, all on `keydown` (`e.preventDefault()`, then commit the
  current cell if its text actually changed, then move): Tab goes to the next cell in reading order
  (header → row 0 → row 1 → ...), Shift+Tab to the previous one, Enter moves down within the *same*
  column. Tabbing past the last cell of the last row (or pressing Enter on the last row) inserts a
  new empty row first and lands in its first cell (or same column, for Enter) — matches ordinary
  spreadsheet UX for "just keep typing to grow the table," which is the main way a freshly-created
  empty table actually gets filled in. **Committing and navigating can't be two separate steps** the
  naive way (commit via `blur`, then call `.focus()` on the next cell found in the *current* DOM):
  `mutateTableAt` dispatches a document change, which `livePreviewPlugin` reacts to synchronously by
  rebuilding decorations — by the time `view.dispatch(...)` returns, `TableWidget.toDOM()` has already
  run again and the *old* cell elements (including whatever "next cell" was found before committing)
  are already detached from the document. `focusTableCell(view, tableFrom, isHeader, rowIndex,
  colIndex)` re-queries the freshly-rebuilt DOM by `data-table-from`/`data-row`/`data-col` *after* the
  commit dispatch returns, rather than holding a stale element reference across it.
- **Unparseable table text** (`parseTableSrc` returns `null` — shouldn't normally happen, since it
  only needs a header + delimiter line pair, but nothing guarantees a hand-edited table always stays
  valid) still renders as `contentEditable` plain text instead of the old fully-static fallback: on
  blur, whatever was typed is written back as-is (not re-parsed as a table), so the user always has
  *some* way to fix a broken table up from the rendered view rather than being stranded with
  unclickable, uneditable monospace text and no path back to valid markdown.
- **Follow-up bug: cells were focusable and the caret moved between them via Tab/Enter, but typing never actually added or removed anything.** `wireCell`'s `keydown` listener only called `e.preventDefault()`/`e.stopPropagation()` inside its Tab/Enter/Escape branches — a plain character key, or Backspace/Delete, fell through untouched and kept bubbling up past the cell to CM6's own `contentDOM`-level keymap (`defaultKeymap`/`historyKeymap`). Confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): dispatching a `Backspace` keydown at a nested `contentEditable` cell correctly left the *document* untouched (CM6's `deleteCharBackward` targets the widget's own single anchor position, not the cell's text, so it has nothing meaningful to do there) — but `event.defaultPrevented` was still `true` afterward, because the command ran and returned a result regardless of whether it changed anything. A prevented keydown never reaches the browser's own default action for that key, which for a focused `contentEditable` element *is* the actual character insertion/deletion — so every keystroke besides Tab/Enter/Escape silently did nothing at all. Fixed (at the time) by calling `e.stopPropagation()` unconditionally as the very first line of the listener, before the Tab/Enter/Escape branching — the same treatment `mousedown` on these cells already gets, just for the analogous keydown-level competition instead of cursor-placement-level.
- **Follow-up, two more bugs from that same blanket `e.stopPropagation()`: native copy/paste didn't work inside a cell, and — separately reported — Ctrl+S (and, by extension, any other VS Code keybinding) did nothing while the cursor was in a cell.** Both trace back to the same root cause, just two different casualties of it. CM6's `InputState` gates *all* of its own event handling — not just clicks, despite the name — behind `eventBelongsToEditor` (`@codemirror/view`): it walks from `event.target` up to `contentDOM`, and if any widget along that path has `ignoreEvent(event)` return `true`, CM6 skips the event entirely for that dispatch (no built-in command runs, and — critically — nothing calls `preventDefault()`). `TableWidget.ignoreEvent()` used to unconditionally return `false`, so CM6's own built-in `handlers.paste`/`handlers.copy`/`handlers.cut` (all real, exported behaviors of `@codemirror/view`, confirmed by reading its source) ran for a `paste`/`copy`/`cut` event bubbling up from inside a cell — each acts on *the document*, not the cell's own text, but each also calls `preventDefault()` regardless, which silently blocked the browser's native paste/copy behavior on the actual focused `contentEditable` element. Separately, the blanket `e.stopPropagation()` in `wireCell`'s `keydown` listener (the fix for the *previous* bug, above) stopped every keystroke from bubbling *at all* — including past `contentDOM` to wherever VS Code's own webview-side keybinding-forwarding listener lives (same document, above CM6, needed to relay a keydown like Ctrl+S back to the workbench's keybinding service) — so Ctrl+S, and any other chord with no cell-specific meaning, never had a chance to reach it either.
  - **Fix**: `TableWidget.ignoreEvent(event)` now returns `true` for exactly `keydown`/`paste`/`copy`/`cut` (not for `mousedown`/`click`/`contextmenu`/`dragover`/`drop`, which `tableContextMenuHandler`'s own `contextmenu` handling and the existing cursor-placement suppression still need CM6 to see — `ignoreEvent` gates *every* domEventHandlers-registered listener too, not just CM6's built-ins, so returning `true` unconditionally would have silently broken the right-click row/column menu). With CM6 now skipping keydown entirely for a cell, `wireCell`'s own `keydown` listener no longer needs a blanket `e.stopPropagation()` to defend against CM6's keymap — that line was removed, and `e.stopPropagation()` is now called only inside the Tab/Enter/Escape branches (the keys this widget still means to fully consume for cell-to-cell navigation). Everything else — plain typing, Backspace, Ctrl+C/V/X, Ctrl+S — now bubbles normally to both the browser's native `contentEditable` handling and whatever sits above CM6.
  - `PropertiesWidget`'s text/list/new-key `<input>`s had the identical blanket-`stopPropagation()` bug for the identical reason (see that section below) and got the identical fix.

`renderCell(raw, basePath?)` — inline markdown renderer for table cell content (and, via `renderTaskRow`, a tasks-query row's description — see the `basePath` param's own comment on the function): HTML-escapes, then restores a literal `<br>`/`<br/>`/`<br />` (case-insensitive) back into a real `<br>` element (see its own comment on that line — reported as "si hay un `<br>` [en una tabla], se tiene que pintar como un salto de línea": raw table-row syntax can't contain a real newline within a cell, so `<br>` is the standard way to force one, and this is the one specific tag shape let through after escaping; every other `<...>` stays inert), then applies sequential regex for `#tags` (`.cm-tasks-query-tag` pill, *in place* — not stripped out — same `(^|\s)#[^…]` pattern as the engine's own `TaskRegularExpressions.hashTags`, run early so it only ever sees plain text), bold, italic, strikethrough, `==highlight==` (`<mark class="cm-highlight">`, same class `highlightMarkPlugin` below uses in the live editor), standard `[text](url)` links **and bare `https://...`/`http://...` URLs** (one combined regex, alternation — see below), wiki-links (`data-wiki` attribute), inline code. Uses `innerHTML` so formatting renders. A `[text](url)` link renders as `<span class="cm-md-link" data-url="url">text</span>` — reusing the CM6-native `mdLinkPlugin`'s own class/attribute/CSS rather than inventing a new one, so `linkClickHandler`'s existing `.closest('.cm-md-link')` branches (mousedown guard + `open-url` click handler) pick it up with zero new wiring. Only `text` is ever visible for a real `[text](url)` — the point of rendering it at all instead of leaving `[text](url)` as literal characters is specifically so the raw URL doesn't show up alongside the link text. A bare URL (no surrounding `[]()`) gets the exact same `<span class="cm-md-link" data-url="...">` treatment, just with the URL itself as both the visible text and the `data-url` — this is what makes a link pasted straight into a task's description (a very common way to end up with one) clickable instead of sitting there as plain text, mirroring `mdLinkPlugin`'s own bare-URL handling in the main editor (see its own section below). Both branches live in **one** regex (`/\[([^\]]+)\]\(([^)\s]+)\)|(https?:\/\/[^\s)"'\]>]+)/g`) rather than two sequential passes specifically so a `[text](url)`'s own destination URL can never be re-matched by the bare-URL branch as a *separate* link — alternation means only one branch can win at a given string position, and `[text](url)`'s leading `[` always sits earlier in the string than the URL text inside its own parens, so the first branch claims it.

### Table context menu — create tables, manage rows/columns (`tableContextMenuHandler`, `TableMenuView`)

Right-clicking a rendered table (`TableWidget`'s own `<table class="cm-table">`) shows a small floating menu to add/remove the row or column under the pointer; right-clicking anywhere else in the editor's `contentDOM` offers "Crear tabla" to insert a new one. This replaces the native browser/VS Code context menu inside the editor — there's no other entry point for table editing in this UI (no ribbon/toolbar), so a context menu is the only reasonable place for it, same as Obsidian's own.

- **Parsing/serialization shared with rendering**: `parseTableRow`/`parseTableSrc`/`serializeTableRow`/`serializeTable`/`tableAligns` (just above `TableWidget`) are the same functions `TableWidget.toDOM()` itself now uses to render (refactored out of what used to be an inline `parseRow` closure) — a row/column edit and the next render always agree on exactly what a "cell" is. `parseTableSrc(src)` returns `{ header: string[], delim: string[], rows: string[][] }` or `null` if the text doesn't look like a table (fewer than 2 pipe-containing lines). `insertTableRow`/`deleteTableRow`/`insertTableColumn`/`deleteTableColumn` are plain in-place mutators on that shape (`rowIndex`/`colIndex` are 0-based, `rowIndex` excludes the header); `deleteTableColumn` refuses to remove the last remaining column rather than producing a headerless table.
  - **Escaped pipes (`\|`) inside a cell used to be misread as a column separator** — `parseTableRow`'s old implementation was a plain `line.split('|')` after stripping the leading/trailing delimiter, so a hand-typed or pasted cell containing `\|` (the standard markdown escape for a literal `|` inside a table cell) got silently split into two cells instead of kept as one. Fixed with two changes: (1) `\|` is protected (swapped for a placeholder token) before any splitting happens, and (2) a *real* separator now requires at least one whitespace character on each side — `\s\|\s` for an interior separator, `\s\|\s*$` for the row's own closing one — mirroring what `serializeTableRow` itself always writes (`"| "` between cells, `" |"` at the end), so a bare, unescaped `|` glued directly onto surrounding text isn't mistaken for a delimiter either. The escape is **not** kept in the resulting cell text (restored to a plain `|`, not `\|`) — reported directly ("tiene que verse un `|` sin el caracter de escape") after an earlier version of this fix kept the backslash visible in both the raw-edit and rendered views; the escape is purely a serialization detail of the `.md` file, not something a WYSIWYG cell should ever show. `serializeTableRow` re-escapes any literal `|` in a cell's value back to `\|` on the way out, so the round trip through the actual file stays valid regardless of what the in-memory/on-screen representation looks like.
- **`TableWidget.toDOM()`** tags its `<table>` with `class="cm-table"` (so `tableContextMenuHandler` can distinguish it from anything else in the DOM) and stamps `data-col` on every `<th>`/`<td>` and `data-row` on every `<tbody>` row — read back by the context-menu handler to know which column/row was right-clicked without needing to walk `tr.children`/`tbody.children` by hand.
- **`findTableRangeAt(state, pos)`** finds the syntax-tree `Table` node containing `pos` and returns the same `{ fromLine, toLine }` character-position range `livePreviewPlugin`'s own `Table` branch computes for `TableWidget` — kept in exact agreement so an edit always replaces precisely the span the widget was built from. **A real bug was caught here, not just theorized**: the first version wrote `found = node;` inside the tree-walk's `enter(node)` callback and read `found.from`/`found.to` only *after* `iterate()` returned. lezer reuses one mutable `SyntaxNodeRef` across an entire traversal for performance (documented lezer behavior, not specific to this codebase) — holding onto that reference past the callback and reading it later reflects whatever node the traversal visited *last* (in this case, the top-level `Document` node spanning the whole file), not the `Table` node actually matched. Confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): every table mutation was replacing the *entire document* with just the serialized table, silently deleting everything before and after it. Fixed by capturing `{ from: node.from, to: node.to }` (plain numbers) immediately inside the callback instead of the node reference itself.
- **`mutateTableAt(view, pos, mutateFn)`** re-resolves the table's range fresh via `findTableRangeAt(view.state, pos)` rather than trusting a range computed back when the context menu was first opened — `pos` itself is a position anchor captured once (via `view.posAtDOM(tableEl)`) at menu-open time and closed over by each menu item's `action()`, but the *range* is always re-derived at click time against the then-current document, so a menu item clicked a moment later still edits the table's actual current text rather than a possibly-stale span.
- **Serious follow-up bug: typing text right after a table (or a frontmatter panel) could end up spliced *into* the block's own source text instead, corrupting it.** Reported with a screen recording: after editing several table cells, clicking on the blank line just below the table and typing a sentence resulted in the typed characters appearing *inside the table's own delimiter row* moments later, breaking it back into raw, unrendered markdown — "con los frontmatters pasa algo parecido" (frontmatter has an analogous problem) came in the same report. Root cause, confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): `mutateTableAt`'s (and `PropertiesWidget.commit`'s) dispatch replaces the block's *entire* source range but never specifies an explicit `selection` — so CM6 falls back to its own default position-mapping for whatever the *current* selection happens to be. That default mapping is ambiguous for a position sitting **exactly** at the boundary of the range being replaced — which is precisely where a click "just below the table" is prone to resolve, since that boundary is visually where the widget ends and real editable content begins. The test reproduced it directly: setting the selection to a table's own `.to` position, then calling `mutateTableAt` to grow the table by one cell's worth of text, left the selection mapped to the *new* table's own `.to` — i.e. still pulled inside the (now longer) table — not past it. Since `mutateTableAt` is the *only* way a cell commit reaches the document, and every commit re-dispatches with the same unspecified selection, a cursor once caught at the boundary never escapes on its own; the next real keystroke (the user believing they're typing normal content below the block) lands inside the block's own markdown instead. Verified this compounds correctly too: a throwaway script simulating four consecutive commits with the cursor pinned at the boundary the whole time showed it never drifting inside, once fixed.
  - **Fix**: `mapSelectionOutsideReplacedRange(state, oldFrom, oldTo, insert)` (defined once, shared by both `mutateTableAt` and `PropertiesWidget.commit`) computes an explicit replacement selection for the dispatch: any range whose anchor/head sits *at or within* `[oldFrom, oldTo]` — the ambiguous case — is redirected to land exactly one position past the freshly inserted content; anything clearly outside that span maps the ordinary way (shifted by the length delta for positions after it). This makes the bug class structurally impossible rather than patching the one reported symptom — it doesn't matter *how* a stray cursor ended up near the boundary, or how many edits follow, the invariant "selection never sits inside a widget-owned range after that widget's own commit" now always holds by construction. (Correction to an earlier version of this note: it claimed `livePreviewPlugin`'s `isActive` gate keeps the CM6 selection off a table's own lines whenever `TableWidget` is rendering — that gate applied back when `TableWidget` still had a raw-markdown fallback; it renders unconditionally now regardless of cursor position, per its own comment above, so that specific justification no longer holds. The fix and its reasoning above stand regardless — see the next entry for what actually kept landing a stray selection at the table's boundary in the first place.)
  - **This fix alone did not fully resolve it — reported again, with a second recording, keyboard overlay included for correlating keystrokes to results**: typed text no longer spliced into the table's delimiter row, but it still ended up fragmented — isolated single characters landing on their own separate lines, interleaved with otherwise-correct text ("todo se vuelve loco"). The actual root cause, found by dumping the syntax tree with a real `EditorState` before and after typing a single character on the blank line right after a table (throwaway script, not checked in): a GFM `Table` syntax node does **not** terminate at the first line lacking a `|` — per spec, and confirmed as lezer-markdown's actual behavior — it keeps absorbing *any* subsequent non-blank line as a "lazy continuation" row, stopping only at a genuine blank line or EOF. The instant the blank line right after a table stops being blank (typing even one character there), that line — and everything non-blank after it, up to the next real blank line — gets pulled into the *same* Table node. Both `livePreviewPlugin`'s `Table` branch and `findTableRangeAt` derived their own notion of "where the table ends" directly from that node's `.to`, so `TableWidget`'s entire replaced range silently grew to match: `parseTableSrc` drops any line without a `|` from what it renders as a row, so the newly-typed text didn't just render wrong, it vanished from view entirely while still occupying document positions *inside* the widget's own takeover range, and the next table-editing commit's `serializeTable` call — having never parsed that text as anything — deleted it outright. Confirmed directly: typing one character on the blank line after a 5-line table grew the syntax node from 5 lines to 7, immediately swallowing a `![[...]]` embed on the following line too.
    - **Fix**: `computeTableEndLine(state, fromLine, nodeTo)` (right above `findTableRangeAt`, used by both it and `livePreviewPlugin`'s `Table` branch) never trusts the syntax node's own `.to` as the table's *effective* end. It walks forward from the header line instead, including a line only while it still contains a literal `|`, and stops at the first one that doesn't — mirroring `parseTableSrc`'s own row filter, so the range this editor treats as "the table" for rendering/editing and the range `parseTableSrc` actually turns into rows always agree, regardless of how far lezer's own (correct, spec-compliant) node extends. Verified with the same jsdom reproduction: after this fix, typing on the blank line still grows the raw syntax node just as before, but the *computed* end line stays pinned to the table's real last row throughout, leaving the typed text — and the embed after it — outside the widget's range and rendering normally.
- **`insertTableTemplate(view, pos)`** inserts a starter 2-column table (`| Columna 1 | Columna 2 |` / `| --- | --- |` / one empty data row) as its own block — on a blank line, right there; otherwise after the current line, preceded by a blank line so the table parses as its own block rather than continuing the preceding paragraph. The cursor lands right *after* the inserted table, not inside it.
  - **First version selected the "Columna 1" placeholder text instead**, so the user could immediately type over it. Reported broken: right-clicking a just-created table showed no row/column menu at all, and the table displayed as raw markdown instead of rendering. Root cause (at the time): `livePreviewPlugin`'s `Table` handling only ever built the actual `<table>` widget while the cursor sat on *none* of the table's own lines (the same "active line shows raw markdown" convention every other block-level element in this file follows) — leaving the cursor/selection inside the freshly-inserted table meant it stayed raw text until the user clicked elsewhere first, and `tableContextMenuHandler`'s `table.cm-table` detection has nothing to match against raw text. Fixed by moving the cursor past the table instead. **This exact failure mode no longer exists at all** — `TableWidget` was later changed to render unconditionally regardless of cursor position (see its own comment above) — but landing past the table is still kept as the sensible default cursor position after inserting a block. Growing beyond 2×1 is expected to happen via Tab/Enter (see `TableWidget`'s cell-navigation comment) or the row/column menu items below, not a size picker up front — there's no `window.prompt()`-style dialog available in a VS Code webview (same constraint noted on `PropertiesWidget`'s "+ Añadir propiedad" row).
- **`TableMenuView`** (`ViewPlugin.fromClass`, no decorations — a plain floating DOM element appended to `view.dom`, same convention as `WikiSuggestView`/`HoverPreviewView`) exposes `show(clientX, clientY, items)`/`hide()`. Built and positioned **synchronously**, directly from the `contextmenu` event handler — unlike `WikiSuggestView.render()`/`HoverPreviewView.render()`, which must defer their own `getBoundingClientRect()` reads through `requestMeasure` because they can be triggered from inside a `ViewPlugin.update()` cycle, a `domEventHandlers` callback runs *outside* CM6's update/measure cycle entirely, so a direct synchronous layout read here is safe — the same reasoning `linkClickHandler`'s `drop` handler already relies on for its own synchronous `posAtCoords` call. Menu items are `{ label, action }` (or `{ separator: true }`); clicking one hides the menu then calls `action()`. A capture-phase document `mousedown`/`keydown` (Escape) listener closes the menu on any outside click or Escape — registered via `setTimeout(..., 0)` rather than immediately, so the same right-click that opened the menu can't also be seen by this brand-new listener and instantly close it.
- **`tableContextMenuHandler = EditorView.domEventHandlers({ contextmenu(e, view) {...} })`**: bails out (returns `false`, native menu proceeds) if the click landed outside `view.contentDOM`, or on a real form control (`input, textarea, select` — `PropertiesWidget`'s text inputs, a ```tasks``` query's filter box, ...) which still need native cut/copy/paste/select-all. Otherwise: if `e.target.closest('table.cm-table')` finds a rendered table, builds column items (add-left/add-right/delete, available from any cell including header) and row items (add-above/add-below/delete for a data row via `tr.dataset.row`; header row only gets "add row below," since there's nothing above a header and deleting it isn't supported through this menu) and shows them; otherwise resolves `view.posAtCoords({x,y})` and offers "Crear tabla". `e.preventDefault()` is called in every branch that shows a menu, suppressing the native context menu specifically where this feature has something to offer — normal text elsewhere in the editor still falls through to native handling only when none of the above conditions match (effectively: everywhere inside `contentDOM` except real form controls, since there's always at least "Crear tabla" to offer).
  - **Reported: the menu "sometimes" didn't appear at all, native Cut/Copy/Paste showing instead.** `posAtCoords` returns `null` for a click that's within `contentDOM`'s own DOM bounds but below the last rendered line — a very easy spot to land on in a short document, or in any document once the click is below the visible text, since `.cm-content` still occupies that space even with nothing rendered there. The "not inside a rendered table" branch originally did `if (pos == null) return false`, silently falling through to the native menu for exactly that (common) case — nothing to do with tables specifically, any right-click in that blank area hit it. Fixed with `view.posAtCoords({x,y}) ?? view.state.doc.length`: a click below all content is treated as targeting the end of the document, same as clicking there normally places the cursor.
  - **Can this be made to appear *inside* VS Code's own native context menu instead of replacing it, as originally requested?** No — a `CustomTextEditorProvider`'s webview content has no menu-contribution point in `package.json` (`contributes.menus`' `editor/context` applies to real text editors, which this isn't, from VS Code's perspective) and no webview-JS API to inject an item into Electron's native/VS-Code-styled context menu; that menu is owned entirely by the host, not the page.
  - **So instead, this extension's own menu was made a real replacement, not a bare "Crear tabla" subset**: both branches now also show `Cortar`/`Copiar`/`Pegar` (`cutSelection`/`copySelection`/`pasteAtCursor`, just above `TableMenuView`) ahead of the table-specific items, separated by a `{ separator: true }` row. `Cortar`/`Copiar` render with `disabled: true` (see `TableMenuView.show()`'s `is-disabled` handling — a plain non-interactive row, no click listener attached, `.cm-table-menu-item.is-disabled` in `vsTheme` just dims it) whenever `view.state.selection.main.empty`, matching how a native menu greys out Cut/Copy with nothing selected. Each tries `document.execCommand('copy'/'cut'/'paste')` first — cheap and, critically, operates on the browser's *actual* DOM selection, which CM6 keeps in sync with its own selection model specifically so native behaviors like this keep working (same reason plain Ctrl+C/V already worked before any of this) — and for paste specifically, going through `execCommand` means it flows through CM6's own native `paste` event handling rather than a raw text insertion that bypasses it. If `execCommand` returns falsy (blocked/unsupported in the embedding context) or throws, each falls back to the async `navigator.clipboard` API (`writeText`/`readText`) instead. `cutSelection` calls `copySelection` first, then deletes the selected range via an ordinary `view.dispatch` — deliberately *not* `execCommand('cut')`'s own direct DOM mutation, which would bypass CM6's transaction system and risk desyncing it from the DOM it owns. None of this touches the existing Ctrl+C/X/V keyboard shortcuts, which keep working exactly as before regardless.

### Multi-cell selection (spreadsheet-style range select/copy/paste)

Requested: "quiero ser capaz de poder seleccionar varias celdas a la vez para copiarlas o pegar en ellas." Each table cell is its own independent `contentEditable` element (see `TableWidget`'s own opening comment) — great for single-cell editing, but dragging across several of them natively just produces an ordinary browser text selection spanning arbitrary characters, not a discrete rectangle of *cells* the way a spreadsheet selects one. This is implemented as its own tracking layer alongside `wireCell`, not through CM6's selection model at all (a range of table cells has no meaningful mapping onto a CM6 text selection).

- `tableCellSelection` (module-level — only one table can have an active range at a time, same reasoning as `activeLinkFrom` elsewhere in this file) is `{ tableFrom, anchorRow, anchorCol, focusRow, focusCol }`; row `-1` means the header row, mirroring the `-1` convention `wireCell`'s own `rowIndex` parameter already uses for it. `dragState` tracks an in-progress mouse drag before it's known whether it's a genuine range drag or just a plain single-cell click.
- **Starting a selection** (`wireCell`'s `mousedown`, extended): Shift+click on a cell, with an existing selection on the *same* table, extends that selection's own anchor to the clicked cell (matching Shift-click's usual "grow from wherever it already started" meaning) and calls `e.preventDefault()` so the click doesn't also move a text caret. A plain (non-Shift) mousedown always clears any existing range first — a click means "edit just this cell" until proven otherwise by an actual drag — and records `dragState`, plus a one-time `document`-level `mouseup` listener (added fresh per mousedown, removed on the very next mouseup, so it never accumulates) that focuses the table itself once a drag has actually moved to a different cell.
- **Extending via drag** (`table`'s own `mousemove`, added once per `toDOM()` call): fires continuously while the left button is held over the table; the *first* time the pointer lands on a *different* cell than the drag started on, `dragState.moved` flips true and `tableCellSelection` is set — that's what turns a plain click into a range. Blurs whatever cell was still focused at that moment (a cell mid-edit would otherwise keep silently holding the text cursor underneath the visible highlight).
- `applyTableSelectionHighlight(tableEl)` toggles `.cm-table-cell-selected` on every cell inside the current rectangle (or clears it from all cells if there's no active selection for *this* table) — called after every change to the selection, and once at the end of every `toDOM()` call, since `mutateTableAt` always produces a brand-new `<table>` element (the selection itself is module state, independent of whichever DOM happens to represent it at the moment).
- **Clearing on click-away**: `ensureTableSelectionOutsideHandler` (single-flight guard, same pattern as `ensureDataviewNoticeContainer`/`dvPopoverOutsideHandlerInstalled` elsewhere in this file) installs one `document`-level capture-phase `mousedown` listener that clears `tableCellSelection` whenever the click lands outside the table that currently owns it — a plain click *inside* the owning table is left to `wireCell`'s own mousedown handler, which already decides whether to keep, replace, or extend the range.
- **Copy/paste** (`table`'s own `copy`/`paste` listeners) only intervene when a genuine multi-cell (or a single-cell-but-explicitly-range-selected) selection is active for *this* table — with none, they return immediately and native per-cell copy/paste (already working via each cell's own `contentEditable` text, see `TableWidget.ignoreEvent`) proceeds unchanged. `e.clipboardData.setData`/`getData` is used rather than the async `navigator.clipboard` API, since these fire as real browser `copy`/`paste` events (native Ctrl+C/Ctrl+V, or the table menu's own `execCommand`-driven ones) — the standard, permission-free way to override clipboard content in response to one.
  - **Copy**: builds the selected rectangle's cell values straight from `t.header`/`t.rows` (the widget's own already-parsed table, not re-read from the DOM), and writes both `buildClipboardTsv` (tab-separated `text/plain`) and `buildClipboardHtmlTable` (a real `<table>` for `text/html`) — see "Table ↔ external clipboard interop" below for both.
  - **Paste**: prefers `text/html` (`parseHtmlTableToRows`) and falls back to `text/plain` (`tsvTextToRows`) if there's no HTML table on the clipboard, then writes the pasted grid into the table starting at the selection's own top-left corner via one combined `mutateTableAt` call — growing the table first (extra columns, then extra rows) if the pasted block is bigger than what's already there, the same way a spreadsheet paste extends the sheet to fit. Extends `tableCellSelection` to cover the newly-pasted extent afterward (matching spreadsheet UX), relying on the mutation's own full-widget rebuild (and the `applyTableSelectionHighlight` call at the end of the next `toDOM()`) to actually paint it.

**Follow-up: "Eliminar fila"/"Eliminar columna" always acted on just the one cell under the pointer, even with a multi-cell range selected.** Requested: with several cells selected, right-clicking should offer to delete *every* row (or column) the selection spans, not only the row/column the click happened to land on.
- `deleteTableRows(t, rowIndices)`/`deleteTableColumns(t, colIndices)` (next to `deleteTableRow`/`deleteTableColumn`) are plural mutators — dedupe + sort the given indices *descending* before splicing, so removing an earlier index doesn't shift the position of a later one still waiting in the same pass. `deleteTableColumns` still refuses to go below one remaining column, same as the singular version.
- `tableContextMenuHandler`'s `contextmenu` handler now checks whether `tableCellSelection` is active for *this* table (matched via `tableEl.dataset.tableFrom`, not `posAtDOM` — more direct, and already the exact identifier `tableCellSelection.tableFrom` itself is keyed on) and whether the *right-clicked cell itself* falls inside that selection's rectangle — a right-click outside the active selection intentionally still acts on just that one cell, same as clicking outside it already clears the selection elsewhere in this file. When it does apply and the rectangle spans more than one row, "Eliminar fila" becomes "Eliminar filas" (deletes every spanned *data* row — the header row, index `-1`, is excluded from the plural delete the same way it's excluded from the singular one, since deleting the header was never supported through this menu); more than one column does the same for "Eliminar columna" → "Eliminar columnas". Either plural action clears `tableCellSelection` *before* dispatching the delete (rather than after), so the widget's post-mutation `toDOM()` rebuild doesn't try to re-highlight now-shifted-or-gone row/column indices against stale selection state.
- **A genuinely blocking bug found while testing this, unrelated to the menu logic itself**: right-clicking a cell that was part of an active selection made the selection disappear *before* the context menu even opened, so the plural wording never had a selection left to detect by the time `contextmenu` fired. Root cause: `wireCell`'s own `mousedown` listener never checked `e.button` — a right-click's own `mousedown` (button `2`) fires before the browser's `contextmenu` event, and unconditionally fell into the same "plain click" branch a left-click would, which always clears any existing `tableCellSelection` first (see "Starting a selection" above) on the theory that a plain click means "edit just this cell." Fixed with `if (e.button !== 0) return;` as the first line of the handler (after `stopPropagation`) — a right-click's own mousedown now leaves selection state completely untouched, letting the native `contextmenu` event that follows see whatever was actually selected.
- Verified end-to-end via the real-Chrome harness (see the marker-styling "round three" entry above for how that's built/driven): dragged a 2×2 range across two rows and two columns of a test table, right-clicked a cell inside it — menu showed "Eliminar filas"/"Eliminar columnas" with the highlight still visibly intact — and confirmed each plural action removed exactly the spanned rows/columns, leaving the rest of the table's data untouched.

### "Pegar como tabla" / "Copiar como tabla" — Excel/Outlook clipboard interop

Requested: paste a range copied from Excel/Outlook as a real markdown table, and copy a markdown table so it pastes into Excel/Outlook as a real table (not visible `|` characters as plain text). Excel/Outlook (and most spreadsheet/office apps) recognize a copied range as "a table" specifically by its `text/html` clipboard payload containing a real `<table>` — plain text, even tab-separated, pastes there as one block of text instead; conversely, when *they* put something on the clipboard, it carries a `text/html` `<table>` (richer, preserves the original grid) alongside a `text/plain` tab-separated fallback.

- **Shared conversion helpers** (just above `insertTableTemplate`'s own paste/copy functions): `buildClipboardHtmlTable(rows)`/`buildClipboardTsv(rows)` (plain `string[][]` → a `<table>` string / tab-separated text; a literal newline in a cell becomes `<br>` for the HTML side, matching how `renderCell`/`renderTableCellDisplay` already render a `<br>` found in a *markdown* cell back as one, just in the other direction), `tsvTextToRows(text)` (tab/newline-split plain text → `string[][]`, deliberately no more sophisticated CSV-style parsing than that — a real spreadsheet copy always carries `text/html` too, so this fallback only needs to cover the common shape), `parseHtmlTableToRows(html)` (a `text/html` clipboard payload → `string[][]`, via `DOMParser` — runs entirely offline with no script execution, so this is safe against arbitrary clipboard HTML), and `rowsToMarkdownTable(rows)` (`string[][]`, first row as header → a markdown pipe-table's raw source, escaping any literal `|` in a cell to `\|` and any real line break to `<br>` — the *inverse* direction from `parseTableRow`'s own unescaping, needed because arbitrary external text has no reason to already be valid table markdown).
- **"Pegar como tabla"** (`pasteAsTable(view, pos)`) lives in the *generic* (not-on-a-table) right-click menu, alongside "Crear tabla" — reads the clipboard via the async Clipboard API (the same `navigator.clipboard` this file's own `copySelection`/`pasteAtCursor` already rely on as their own fallback path; `navigator.clipboard.read()` when available, for both MIME types, falling back to `readText()` for plain-text-only environments), prefers a `text/html` table and falls back to tab-separated `text/plain`, then inserts the result as a real markdown table at the click position — same placement rule as `insertTableTemplate` (own line if blank, otherwise a new block after the current line). A `DataviewNotice` toast (reused from the dataviewjs integration — see its own section — as a generic "floating message inside the webview" primitive, not anything dataview-specific) reports when the clipboard has nothing recognizable to paste.
- **"Copiar como tabla"** (`copyTableAsClipboard(view, pos)`) — **lives in a *rendered* table's own right-click menu**, next to add/remove row/column, not the generic one. First version operated on the current CM6 *text selection* (parsing whatever markdown text happened to be selected via `parseTableSrc`), which required manually selecting the table's raw source first; corrected directly ("el menú copiar como tabla tiene que estar en el menú contextual de la tabla") to instead resolve the *whole table the user right-clicked*, the same way every other item in that menu already finds it (`findTableRangeAt` via the menu's own `pos`) — no text selection needed at all. Writes both `text/plain` (TSV) and `text/html` (a real `<table>`) via `navigator.clipboard.write([new ClipboardItem({...})])`, falling back to `writeText`-only (with a toast noting the richer format isn't available) if `ClipboardItem`/`clipboard.write` don't exist in this embedding context.

### `PropertiesWidget` / YAML frontmatter → "Propiedades" panel

Obsidian's Live Preview never shows a note's leading YAML frontmatter as raw `---\n...\n---` text — it replaces the whole block with an interactive "Propiedades" panel (tags as removable pills, an "+ Añadir propiedad" row, ...), and editing happens entirely through that panel's own controls. Deliberately diverges from this codebase's usual "reveal raw markdown while the cursor/an edit is inside it" convention (headings, lists, wiki-links, tables, ```tasks``` blocks, ...) — there's no raw-YAML fallback view at all in Live Preview; the panel *is* the editing surface, matching Obsidian's own behavior (raw YAML is only ever visible in Source Mode, i.e. `toggleSourceMode`, which already disables all of `previewCompartment` including this).

- **Hand-rolled parser, not a real YAML library** — this webview bundle has no other npm dependencies, and only needs to round-trip Obsidian's own common property shapes (string, number, boolean, list), not arbitrary YAML. `parseFrontmatter(state)` requires line 1 to be exactly `---` and finds the next `---`-only line as the close; every line in between must match a plain `key:` / `key: value` shape (via `/^([^:\n]+):(.*)$/`, split on the *first* colon so keys containing spaces/accents work) or `  - item` (2-space-indented dash) for a list started by a bare `key:`. **Anything it doesn't confidently recognize — comments, nested maps, multi-line block scalars, anchors, an unclosed block — makes it return `null`**, at which point `livePreviewPlugin` just never enters this code path and the block renders as ordinary (unstyled) text, rather than risking mangling something the parser doesn't understand on the first write-back. `parseYamlScalar(raw)` classifies a scalar as `boolean` (`true`/`false`, case-insensitive), `number` (`/^-?\d+(\.\d+)?$/`), `list` (inline `[a, b]` syntax), or falls through to `string` (quotes stripped if present).
- **Serialization** (`serializeFrontmatter(properties)`) is the exact inverse shape: lists with items use the multi-line `key:` + `  - item` form (matching Obsidian's own typical output), an **empty** list serializes as `key: []` specifically so it round-trips back to `type: 'list'` rather than being misread as an empty *string* property on the next parse (a bare `key:` with no items is what `type: 'string', value: ''` reserializes to) — this asymmetry (`key:` = empty string, `key: []` = empty list) is the one deliberate, documented ambiguity-resolution in the whole scheme. `yamlScalarOut(value)` only quotes a value when leaving it bare would change how it re-parses (looks like `true`/`false`/a number/contains `:` or `#`/has leading-trailing whitespace).
- **Rendering strategy mirrors `Table`/```tasks``` blocks exactly** (`block: true` is banned — see above): line 1 (the opening `---`) becomes a single-line `Decoration.replace({ widget: new PropertiesWidget(view, fm.from, fm.to, fm.properties) })`; every remaining line through the closing `---` gets an empty `Decoration.replace({})` + `Decoration.line({ class: 'cm-table-row-hidden' })`, reusing that existing class rather than adding a redundant one. Unlike Table/```tasks```, there's **no active-line fallback to raw text** — see above for why.
- **`PropertiesWidget(view, from, to, properties)`** — `eq()` compares `from`/`to`/`JSON.stringify(properties)`, which is what makes in-progress, uncommitted local UI state (e.g. the "+ Añadir propiedad" row's own input, mid-typing a new key name) survive a decoration rebuild triggered by something *unrelated* elsewhere in the document: as long as the frontmatter's own parsed data hasn't actually changed, `eq()` returns `true` and CM6 reuses the existing DOM node instead of calling `toDOM()` again. This is also why every value edit **commits on blur/Enter, never on every keystroke** — a commit dispatches a real document change, which *does* change `properties`, which *does* force a fresh `toDOM()` call next rebuild, destroying whatever DOM (and focus) existed before; committing mid-keystroke would make a text field lose focus after every single character typed.
- **Editing model**: tag/list pills get a `×` (click removes that one item, commits immediately — atomic, no focus-loss concern); a small trailing `<input>` per list adds a new item on Enter/`,`. Boolean properties render a real `<input type="checkbox">`, committing on `change`. Everything else (the fallback for `string`/`number`) renders a plain text/number `<input>`, committing on `blur` or Enter. "+ Añadir propiedad" toggles between a label and an inline `<input>` for the new key's name (Enter commits a new empty-string property; Escape or blur cancels) — **not** `window.prompt()`, since VS Code webviews don't support native JS dialogs.
- **`commit(newProps)`** dispatches `{ changes: { from: this.from, to: this.to, insert: serializeFrontmatter(newProps) }, userEvent: 'properties.change' }` — the custom `userEvent` string is deliberate: it does *not* start with `"input"`/`"delete"`, so `wikiLinkActivationTracker`'s `isUserEvent('input')` check (keyed off wherever the document's actual text cursor happens to sit, completely unrelated to this panel's own DOM inputs) never mistakes a properties edit for the user editing inside whatever `[[wiki-link]]` the cursor happens to be parked on elsewhere in the note.
- **Scope deliberately cut, in exchange for the above staying simple**: no key renaming (keys render as plain, non-editable text), no per-property type picker (Obsidian lets you convert a property's type via a dropdown; a brand-new property added through "+ Añadir propiedad" always starts as `string` — building a `list`/`tags`-typed property from scratch still needs raw YAML, i.e. Source Mode, this once), and only 2-space list indentation / first-colon key splitting are recognized (matching Obsidian's own default YAML output, not arbitrary hand-written indentation styles).
- Interactive elements call `e.stopPropagation()`/`e.preventDefault()` on their own `mousedown` (matching the existing `TaskCheckboxWidget`/`TransclusionWidget` convention of `ignoreEvent() { return false; }` at the widget level, so clicks still reach the elements' own listeners rather than being swallowed) — importantly, this is deliberately **not** done for the text `<input>`s' own click-to-focus behavior, which needs the browser's native handling to proceed unobstructed for typing to work at all.
- **Follow-up bug: focusing a property's text input worked, but typing into it didn't — "en modo WYSIWYG no puedo editar el frontmatter."** The `mousedown` handlers above only ever covered *cursor placement/focus*; every text `<input>`'s own `keydown` listener (the one watching for `Enter` to commit-and-blur) never called `e.stopPropagation()`, so every other keystroke — Backspace, Delete, anything else CM6's own `defaultKeymap`/`historyKeymap` binds — kept bubbling up to CM6's `contentDOM`-level keymap. Exact same bug and same fix as `TableWidget`'s `wireCell` keydown handler (see that section): CM6's own bound command runs first, has nothing meaningful to do at wherever the *document* cursor happens to be, but still calls `preventDefault()` on the keydown regardless — and a prevented keydown never reaches the browser's own default action for that key, which for a focused `<input>` is the actual character deletion. Confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): the document was correctly untouched by CM6, but `event.defaultPrevented` was still `true`, meaning the input's own native Backspace never got a chance to run either. Fixed (at the time) by adding `e.stopPropagation()` to the very first line of every `keydown` listener in this widget — the text input's own, the list-value "+" add-input's, and the "+ Añadir propiedad" new-key input's — plus a small new keydown listener on the boolean checkbox purely to stop propagation there too (Space toggles a focused checkbox via the browser's own default action, same class of risk). None of this affects `mousedown`, which was already correctly handled — it's specifically the keyboard path that was missed the first time this widget's event-swallowing was written.
- **Follow-up, same root cause as `TableWidget`'s identical copy/paste + Ctrl+S bug (see that section's own entry for the full mechanism)**: the blanket `e.stopPropagation()` added above also blocked Ctrl+S and any other VS Code keybinding from ever reaching whatever listens for them above CM6, whenever focus was inside one of these `<input>`s. Fixed the same way: `PropertiesWidget.ignoreEvent(event)` now returns `true` for `keydown`/`paste`/`copy`/`cut` (previously an unconditional `false`), so CM6 skips those events for this widget entirely instead of needing `stopPropagation()` to fight off its keymap after the fact. Every `keydown` listener in this widget (text input, boolean checkbox, list-add input, new-key input) had its own `e.stopPropagation()` call removed accordingly — each still calls `e.preventDefault()` where it means to consume a specific key (Enter to commit, Escape to cancel), just no longer blocks unrelated keys from bubbling further.

**Tighter top spacing, and the cursor made fully unreachable inside it (requested together).** `.cm-properties`'s `margin` top value was changed to `-8px` (from `4px`) — pulling the panel up into `.cm-content`'s own fixed `16px` top padding, safe to do unconditionally since `PropertiesWidget` only ever renders on line 1 (`parseFrontmatter` requires it), so there's never anything above it to collide with when it exists at all.

- **`frontmatterAtomicRanges`** (`EditorView.atomicRanges.of(...)`, defined right after `foldAtomicRanges` and following the exact same mechanism/semantics) blocks every cursor position from **line 2** through the frontmatter's own closing `---` line. Requested: the cursor should only ever be able to land *below* the panel, never inside its own (raw, hidden) text — which the panel's whole design already assumed ("editing happens entirely through that panel's own controls," never the raw YAML in Live Preview), so a text cursor being placeable inside that span at all was an oversight rather than an intentional gap. The upper bound is computed the same way `computeFoldedSpans` computes a fold's own bound — one *less* than wherever the next valid content actually starts (the closing line's own `.to`, not `.to + 1`) — so a redirected cursor lands exactly at the start of the newline right after it, not before.
- **First version covered from position `0`** (i.e. line 1 too, where `PropertiesWidget`'s own `<input>`s/pills/checkboxes render) and broke every one of those controls outright — reported immediately as "no puedo editar el contenido de un frontmatter." Root cause, confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): CM6's own pointer handling resolves any click within a widget-replaced range back to that widget's single anchor position; when that position falls inside an atomic range, the click takes a different internal path than an ordinary click needing no remapping — one that calls `preventDefault()` on the mousedown (`event.defaultPrevented` was `true` with the wide range, `false` with a plain click at the same DOM node with no atomic range present). A browser only auto-focuses the element under a mousedown if its default action wasn't prevented, so the click reached the `<input>` but the input never actually gained focus, and Cortar/Copiar/Pegar-style native default actions were suppressed the same way. Fixed by starting the range at `line 1's own .to + 1` instead of `0` — line 1 needs no protection anyway, since it's already a single `Decoration.replace({widget})` spanning the whole line with no raw text exposed for a cursor to land "inside" of; the actual gap this facet exists to close is lines 2..N, which (unlike line 1) are collapsed one line at a time and do have reachable boundary positions between them.
- Registered **inside** `previewCompartment` (both in `createEditor`'s initial list and `toggleSourceMode`'s `reconfigure` call), unlike `foldAtomicRanges`, which sits outside it: `PropertiesWidget` itself only renders in Live Preview — Source Mode shows the raw YAML as ordinary, fully editable text by design (see this section's own opening paragraph) — so the atomic blocking must toggle off right along with the widget, not stay active over now-genuinely-editable text.
- **This alone does *not* cover this file's own custom `moveVerticalByLine`** (the Up/Down replacement — see its own section below), for the identical reason `foldAtomicRanges` alone didn't cover it for folded headings: `EditorView.atomicRanges` only protects CM6's *own* built-in navigation (`moveByChar`/`moveVertically`-based commands — i.e. Left/Right/Home/End, untouched by this codebase's custom keymap) and pointer-driven selection (mouse clicks/drag), not a function that computes a target line by hand and dispatches a raw selection directly, bypassing that machinery entirely. Confirmed empirically (throwaway script, not checked in): dispatching `EditorSelection.cursor(pos)` directly for a position inside the atomic range was **not** blocked or remapped by the facet at all — only CM6's own commands and pointer selection consult it. `moveVerticalByLine`'s cross-line branch therefore got the same kind of explicit check already added there for `computeFoldedSpans`: if the freshly computed `targetLineNum` would land on or before the frontmatter's closing line, it's redirected to exactly one line past it. Frontmatter is always anchored at the document's very start, so (unlike a fold, reachable from either direction) the only way to land inside it via vertical movement is pressing Up from somewhere below — there's no "approaching from above" case to handle.

### `mdLinkPlugin`

Regex-based `ViewPlugin` for standard markdown links `[text](url)` **and** bare `https://...`/`http://...` URLs with no `[text]()` around them at all. More reliable than syntax-tree approach for `[text](url)` because lezer-markdown's `Link` node structure varies depending on URL format in href; bare URLs are matched independently of the syntax tree entirely, same reasoning `findUrlAtPos`'s own regex fallback below already relies on.

- `[text](url)` regex: `/(?<!!)\[([^\[\]\n]*)\]\(([^)\n]*)\)/g` — matches `[text](url)` but NOT `![alt](url)`. For non-active lines: replaces the entire match with `MdLinkWidget` — a `<span class="cm-md-link" data-url="url">text</span>`.
- Bare-URL regex: `/https?:\/\/[^\s)"'\]>]+/g` — the exact same pattern `findUrlAtPos` uses as its own fallback (below), so "renders as a link" and "is clickable" always agree on the same span. Unlike `[text](url)`, this is a plain `Decoration.mark({ class: 'cm-md-link', attributes: { 'data-url': url } })` over the URL's own existing text, not a widget: there's no markdown syntax to hide/reveal for a bare URL (the visible text *is* the URL), so there's also no need for the active-line exclusion `[text](url)` uses — styling stays on even while the cursor is on that line, since a mark decoration doesn't remove or replace anything the way a widget replacement would. **Added specifically because a bare URL dropped into a task's description (no `[]()` around it) previously rendered as completely plain, unstyled text** — reported as "no enlace ni nada" even though `findUrlAtPos`'s regex fallback already made it *clickable*; the gap was purely that nothing gave it a visual affordance. Both regexes run over the same viewport-slice string and feed the same `all` decoration array, so the existing overlap-skip (`if (from < lastTo) continue`, after sorting by `from`) already keeps a `[text](url)`'s own destination URL from being double-matched by the bare-URL pass: the link's `[` always sorts before the URL text sitting inside its own `(...)`, so it claims that range first.
- Styled identically to wiki-links (underlined, `--link-color`).
- `linkClickHandler` detects `.cm-md-link` clicks and sends `open-url` with `dataset.url`.

### `highlightMarkPlugin` — `==highlighted text==`

`==text==` isn't real CommonMark/GFM syntax, so lezer-markdown never parses it into a syntax-tree node — unlike bold/italic/strikethrough (`EmphasisMark`/`StrikethroughMark`, handled in `livePreviewPlugin`'s own tree walk via `mdHighlight`'s tag-based styling), there's nothing to hook a tag onto here. Implemented the same way `mdLinkPlugin`/`wikiLinkPlugin` already handle their own non-tree-based syntax: a plain regex scan (`/==([^=\n]+?)==/g`) over the viewport. Unlike `mdLinkPlugin`'s whole-match widget replacement (fully raw, no styling at all, while the cursor is on that line), this mirrors bold/italic/strikethrough's actual convention instead: the highlighted *text* stays visually marked regardless of cursor position (a `Decoration.mark({ class: 'cm-highlight' })` over the inner span, not gated on `active`), and only the raw `==` markers hide on non-active lines, exactly like `**`/`*`/`~~` do for their own markers. `.cm-highlight` (`vsTheme`) is a plain background/color pair driven by `--text-highlight-bg`/`--text-highlight-fg` (Obsidian theme vars, with a warm-yellow fallback matching Obsidian's own default). Also rendered by `renderCell`/`renderTableCellDisplay` (as a real `<mark class="cm-highlight">`) for read-only/table-cell contexts, and registered in both `previewCompartment` extension lists (`createEditor`'s initial one and `toggleSourceMode`'s reconfigure) right after `mdLinkPlugin`.

### `wikiLinkPlugin`

Regex `/(?<!!)\[\[([^\]|]+?)(?:\|([^\]]*?))?\]\]/g` over viewport text. For each match, hides `[[`, `]]`, and (when alias) the `target|` part, leaving only the display text with class `cm-wiki-link` — **unless** that specific match's own `[[...]]` span is currently "activated" (`isLinkActivated(mFrom, mTo)`, checked per match, not per line), in which case that one match is left alone entirely (no decorations pushed for it) so the raw text renders as-is. This is deliberately per-token rather than per-line: with several `[[wiki-links]]` on the same line, only the activated one should stay raw — the others should still render normally even though `getActiveLines` would consider the whole line "active". (The same `isLinkActivated` check also backs the `cm-wiki-link-raw` inner-bracket-coloring fix under `livePreviewPlugin` above, for the same reason.)

#### `[[wiki-link]]` "activation" — why the cursor merely passing through no longer reveals raw markdown

Originally this used `rangeIsActive(state, from, to)` (any selection range touching `[from, to]`) — i.e. a link went raw the instant the cursor sat anywhere inside its brackets, by any means. That included pure cursor navigation, not just editing — and once `moveVerticalByLine` (see below) started landing the cursor at essentially arbitrary horizontal offsets while moving between lines, it became common for Up/Down to pass straight through a `[[link]]`'s span and flip it to raw markdown (and, worse, `WikiSuggestView`'s trigger regex doesn't distinguish "still typing an unclosed `[[`" from "cursor happens to sit before an existing link's own `]]`", so it would also pop the suggestion popup open) — pure noise from the user's point of view, since they weren't editing the link at all, just passing through it.

Replaced with an edit-driven model: a link only reveals its raw form once the user actually **edits** text (insert or delete) while the cursor is inside it; landing there via navigation alone leaves it rendered. Once activated by an edit, it *stays* raw — including through further pure navigation within the same link — until the cursor moves outside its outer brackets, then reverts to normal rendering.

- `activeLinkFrom`/`activeLinkTo` (module-level) — the currently-activated link's outer span: the first `[` through one past the last `]` for an existing `[[note]]`, or through the cursor itself for a still-unclosed `[[note` being typed. `activeLinkClosed` distinguishes the two: `true` for an existing, already-closed link being edited (only affects raw-vs-rendered display); `false` for a genuinely in-progress, unclosed `[[note` (also what gates `WikiSuggestView`'s popup — editing inside an *already-closed* link never reopens it, matching how the popup only ever targeted brand-new, unclosed links to begin with).
- `findLinkContextAt(state, pos)` — finds the `[[...]]` (closed) or `[[...` (unclosed, ending exactly at `pos`) span containing a cursor-only (non-range) selection at `pos`, mirroring the exact shapes `wikiLinkPlugin` and `WIKI_TRIGGER_RE` already recognize (a fresh copy of the closed-link regex, not the shared `wikiLinkPlugin` one, to avoid any `lastIndex` state-sharing bug between the two independent scans).
- `wikiLinkActivationTracker` — a plain side-effect `ViewPlugin` (no decorations), placed in `createEditor`'s extensions list **before** `previewCompartment` (i.e. before `livePreviewPlugin`/`wikiLinkPlugin`), so its mutation of `activeLinkFrom/To/Closed` for a given transaction is visible to their own rebuild for that *same* transaction — no separate dispatched effect needed, since ViewPlugins run in extension-registration order for each update. Its `update(u)`:
  - First re-maps an existing activated span through `u.changes` (`mapPos`) whenever `u.docChanged`, so it survives edits made elsewhere in the document (e.g. an `external-update` from autosave) without drifting.
  - If this transaction is a genuine user edit (`u.docChanged && u.transactions.some(t => t.isUserEvent('input') || t.isUserEvent('delete'))` — `isUserEvent` matches dotted subtypes too, e.g. `input.type`/`input.paste`/`delete.backward`), re-derives activation fresh from `findLinkContextAt` at the new cursor position — this is what turns "landed here via an edit" into activation, and also what lets it correctly re-activate on every keystroke while typing a new link's target text.
  - Otherwise (pure navigation, or a non-user-input doc change) it only ever *clears* an existing activation once the cursor position ends up outside `[activeLinkFrom, activeLinkTo]` — it never newly activates from navigation alone.
- `isLinkActivated(from, to)` — trivial equality check (`activeLinkFrom === from && activeLinkTo === to`) used by both `wikiLinkPlugin` and `livePreviewPlugin`'s `cm-wiki-link-raw` check in place of the old `rangeIsActive` cursor-presence test.
- `WikiSuggestView.currentContext()` additionally requires `!activeLinkClosed && activeLinkFrom === openBracketFrom` (the same position its own `WIKI_TRIGGER_RE` match computes) before returning a trigger context — since that regex alone can't tell "still typing an unclosed `[[`" apart from "cursor merely sits before an existing link's `]]`" (it only looks at text *before* the cursor), deferring to the shared activation state is what actually distinguishes the two.
- Links are inherently single-line (the regex forbids embedded newlines), so any vertical move immediately lands outside whatever was previously activated and clears it — no special multi-line handling needed there.

The `cm-wiki-link` mark always carries `attributes: { 'data-target': name }` with the raw target (including any disambiguation path), even when an alias is displayed — the visible text alone isn't enough to resolve the link once an alias hides the real target. `linkClickHandler` reads `dataset.target` (falling back to `textContent` for safety) and sends that as `open-note`'s `name`, so the host receives the full target string to resolve.

**`#section` display, no alias**: `name` (the regex's capture group, e.g. `Note#Heading`) may itself carry a `#section` suffix even with no `|alias` present. Left unhandled, this rendered the raw `Note#Heading` text verbatim — the note name and `#` were never hidden the way an alias's `target|` prefix already is. Fixed the same way alias-hiding works: when there's no alias but `name` contains `#`, the `Note#` portion gets its own `Decoration.replace({})` and only the section text is wrapped in the `cm-wiki-link` mark — still carrying the *full* `name` (including the note part) as `data-target`, since navigation still needs it.

**Missing-target styling (`cm-wiki-link-missing`)**: `noteTargetExists(rawTarget)` mirrors the host's `resolveNoteUri`/`splitDirHint` rules — strips any `#section` suffix (irrelevant to existence), then checks `noteIndex` for a note matching `rawTarget`'s name, filtered by directory-hint (last path segment) if one was given. When it returns false, `wikiLinkPlugin` adds `cm-wiki-link-missing` alongside `cm-wiki-link`; `vsTheme`'s rule for it is just `opacity: var(--link-unresolved-opacity, 0.55)` layered on top of the normal link color/underline, rather than a separate hardcoded color, so it stays theme-consistent while still reading as visibly fainter than a resolved link. Existence is evaluated against the *current* `noteIndex` at decoration-build time, but a `note-index` update (e.g. the target note gets created in another panel) doesn't itself touch this document/viewport/selection — none of the conditions `wikiLinkPlugin.update()` already watches for. `noteIndexRebuildEffect` (a bare `StateEffect`) is dispatched by the `note-index` message handler specifically to force a rebuild in that case; `wikiLinkPlugin.update()` checks for it alongside the usual `docChanged`/`selectionSet`/`viewportChanged` conditions.

### `imgPlugin`

Regex `/!\[\[([^\]]+)\]\]/g` over viewport. Parses optional `|` parameter:
- `![[file.png|400]]` or `![[file.png|400px]]` → image at 400px wide
- `![[file.png|Caption text]]` → image with `<figcaption>` below

For non-active lines with known filename in `imageMap`, replaces with `ImageWidget`. If the bracketed name's extension isn't one of `IMG_EXT`, `imgPlugin` leaves it alone — that's the signal `transclusionPlugin` (below) uses to claim it instead, since both plugins run their own regex pass over the exact same `!\[\[...\]\]` syntax.

`ImageWidget(src, alt, width, caption)` — renders `<img>` optionally wrapped in `<figure>` + `<figcaption>`.

### `.docx`/`.xlsx`/`.pdf` wiki-links and embeds → open with the OS's own default application

A `[[report.docx]]`/`[[budget.xlsx]]`/`[[manual.pdf]]` link (or a `![[...]]` embed of one) has no meaningful in-editor rendering — this isn't a note (`resolveNoteUri`/`open-note` only ever look for `<name>.md`) and isn't an image, so left alone it either silently failed to resolve (a plain link) or tried and failed a `get-transclusion` round-trip meant for markdown note text (an embed). Requested behavior: clicking one should just open the real file with whatever the OS has registered for that extension — the native Word/Excel/PDF viewer, not something this editor tries to render itself.

- `EXTERNAL_FILE_EXT = /\.(docx|xlsx|pdf)$/i` and `isExternalFileTarget(raw)` (strips any `#section`/`|alias` suffix first, mirroring `IMG_EXT`'s own filename-guess pattern) live just above `imgPlugin` — checked from three places: `linkClickHandler`'s two wiki-link click branches (`.cm-wiki-link` and table-cell `[data-wiki]`), and `transclusionPlugin`'s own `![[...]]` match loop (checked *after* the existing `IMG_EXT` check, so an actual image extension still goes through `imgPlugin`/`ImageWidget` unchanged).
- **Plain link click** (`[[report.docx]]`): `linkClickHandler` posts `{ type: 'open-external-file', name: target }` instead of `open-note` — same `dataset.target` the click already reads, just routed to a different message type based on `isExternalFileTarget(target)`. Same swap applies to a table-cell/task-row `[data-wiki]` wikilink (`renderCell`'s output), carrying `basePath` through exactly like `open-note` already does.
- **Embed** (`![[report.docx]]`): `transclusionPlugin` routes these to `ExternalFileWidget(target)` instead of `TransclusionWidget`/`get-transclusion` — a compact `div.cm-external-file` (📎 icon + filename, bordered box, `cursor: pointer`) rather than an attempt to fetch and render file content that doesn't exist as markdown text. Its click handler (wired into `linkClickHandler` the same way as `.cm-transclusion-open`) posts the same `open-external-file` message.
- `noteTargetExists(rawTarget)` (backs `cm-wiki-link-missing` dimming) returns `true` unconditionally for an external-file target — `noteIndex` only ever tracks `.md` notes, and there's no cheap client-side way to check whether a `.docx`/`.xlsx`/`.pdf` actually exists in the vault without a new round-trip, so this trades "might not dim a genuinely broken link" for "doesn't visually dim a link that in fact opens fine" (the host-side resolution at click time is what actually determines whether it works, regardless of this styling decision).
- Host side: `resolveExternalFileUri(notePart, currentDir)` (`src/extension.ts`, right after `resolveNoteUri`) is the same disambiguation shape (vault-wide `findFiles`, directory-hint tie-break, then same-directory, then first match) but searches for `notePart` *as-is* — no `.md` appended, since the target already names the real file including its own extension. A vault-wide miss shows a warning instead of creating anything, unlike `open-note`'s create-if-missing behavior — there's no sensible "create a blank .docx" fallback.
- **`openFileWithOsDefaultApp(fsPath)`** (right after `resolveExternalFileUri`) is what actually opens the resolved file — **not** `vscode.env.openExternal(Uri.file(...))`, which was the first version and is the "correct", documented API for this. Reported broken on real hardware for *both* a `.pdf` and a `.docx` target: "An error occurred opening an external program... El sistema no puede encontrar el archivo especificado (0x2)" (Windows' own ERROR_FILE_NOT_FOUND) even though the resolved path opened fine directly from Explorer — a known reliability gap in how `openExternal` hands a local `file://` URI off to the OS shell on some Windows configurations, not a bug in this extension's own path resolution (confirmed correct independently — the failure happened consistently across two different file types with two different resolved paths). Fixed by spawning the OS's own "open" mechanism directly instead: `cmd.exe /c start "" <path>` on Windows (`start` is a cmd.exe built-in, not its own executable — hence spawning `cmd.exe` itself, with `start`'s own first-quoted-argument-is-the-window-title convention accounted for via the empty `""`), `open <path>` on macOS, `xdg-open <path>` on Linux. Uses `child_process.execFile` (imported at the top of `extension.ts`), **not** `exec` — arguments are passed as an array rather than concatenated into a shell command string, so a filename containing spaces or shell-metacharacters (quotes, `&`, `%`, ...) can't corrupt the command or be misinterpreted by an intermediate shell at all.

### `transclusionPlugin` — note transclusions (`![[note]]`, `![[dir/note]]`, `![[note#section]]`)

Same `!\[\[([^\]]+)\]\]/g` regex pass as `imgPlugin`, but claims the match when the bracketed name (before any `#section` or `|param`) does **not** look like an image filename (`IMG_EXT.test(...)` false) — the two plugins' viewport passes are independent and each only emit decorations for the subset they own, same pattern `mdLinkPlugin`/`wikiLinkPlugin`/`imgPlugin` already use for their respective syntaxes.

A transclusion needs the *target* note's (possibly section-scoped) text, which the webview can't read itself — same async round-trip as `` ```tasks ``` `` query blocks: webview posts `get-transclusion` (host resolves + reads + slices), host replies `transclusion-result`, webview caches and rebuilds.

**Section boundary rule, host-side (`get-transclusion`'s own slicing, `src/extension.ts`)** — a `#section` transclusion includes everything from the matched heading's own line up to (but not including) the next heading whose level is **the same or shallower** (`headings[j].level <= headings[idx].level`), or end of file if none follows. A deeper heading (e.g. an `##`/`###` nested under a matched `#`) is *not* a stopping point — its own line and everything under it are included, same as any other content, so transcluding an H1 pulls in every nested H2/H3/etc. section beneath it, only stopping at the next heading of equal-or-higher rank. Reported as a suspected bug directly ("todo el texto... se transcluye, salvo otras cabeceras de inferior rango... tienes que dejar de trancluir cuando encuentres otra cabecera de igual rango o el final del fichero") — investigated by extracting `parseHeadings` + this exact slicing loop into a standalone script and running it against a synthetic H1/H2/H3/H2/H1 document, and separately confirming the *compiled* `out/extension.js` already installed matched the same logic byte-for-byte. Both checks showed the rule already implemented exactly as described — not a bug in this codebase's history, just previously undocumented (there was no reference for the reporter, or this file, to check the intended behavior against). Confirmed for real afterward too: a matching test note pair was created directly in the user's own vault and opened in the actual installed extension, which rendered the nested sub-sections correctly. No code changed as a result — recorded here so this exact "is this a bug?" investigation doesn't need repeating.

- `transclusionCache: Map<string, { content, title, line, error }>` keyed by the *raw* bracketed target string (e.g. `"projects/Foo#Status"`), `transclusionPending: Set<string>` dedupes in-flight requests, `transclusionRebuildEffect: StateEffect` forces a rebuild once a reply lands — all three mirror `tasksQueryCache`/`tasksQueryPending`/`tasksRebuildEffect` exactly.
- Since the source line is always a single line already (unlike a multi-line table), rendering needs no `Table`-style "collapse the remaining lines" trick: the whole `![[target]]` match is one `Decoration.replace` (not `block: true`) whose widget happens to render multi-line content — the same technique `ImageWidget`/`TableWidget`/`TasksQueryWidget` already rely on.
- `TransclusionWidget(target, data)` — `data` is whatever `transclusionCache.get(target)` held at `_build()` time: `undefined` while in flight (renders a loading placeholder), `{ error }` for `'not-found'` / `'section-not-found'` / `'error'` (renders a one-line message instead of a body), or `{ content, title, line }` on success. Rendered DOM: an outer `div.cm-transclusion` (the bordered rectangle) containing a `button.cm-transclusion-open` (absolutely positioned top-right, `↗` glyph, `data-target` = the raw target string) plus a `div.cm-transclusion-body` (an optional `div.cm-transclusion-title` showing the target's filename, then `renderMarkdownBlock(content)`).
- `renderMarkdownBlock(text)` — a small line-based block renderer (headings → `div.cm-header-N`, fenced code → `<pre><code>`, `>` blockquotes, `-`/`*`/`+` lists → `<ul>`, tables → `renderMarkdownTable` (below), a `![[...]]` embed alone on its own line → `renderEmbedBlock` (below), task checkbox lines within a list → their own branch (below), blank-line-separated paragraphs) used only for transcluded content; each block/paragraph's inline text goes through the existing `renderCell()` (bold/italic/strikethrough/code/wiki-links), which HTML-escapes first, so transcluded text can't inject markup. A *nested note transclusion* (`![[other-note]]`, no recognized extension) is still **not** re-resolved — it renders as inert escaped text, i.e. transclusions of transclusions do not recurse. Only the image/external-file case below was ever missing real rendering; recursion itself is still deliberately out of scope.
- **`renderEmbedBlock(raw)`** — reported as "si hay una imagen [en una transclusión], tiene que verse la imagen y no el `![imagen.png]`... si hay un documento, tiene que verse y poder pulsarse... y si hay tareas, tienen que aplicarse los correspondientes estilos." Before this, a `![[...]]` embed inside transcluded content had no dedicated handling at all in `renderMarkdownBlock` — it fell through to the generic paragraph case and rendered as literal escaped text (`renderCell` only understands *inline* markdown, not `![[...]]` block syntax), even though the exact same syntax renders correctly as a real `<img>`/clickable box in the note's own live editor (`imgPlugin`/`ExternalFileWidget`). Fixed by reusing those two widgets' own `toDOM()` directly rather than re-implementing image/file resolution a second time: a line matching `/^\s*!\[\[([^\]]+)\]\]\s*$/` is checked against `IMG_EXT` (same `imageMap` lookup `imgPlugin` itself uses, basename fallback included — returns `new ImageWidget(...).toDOM()`) or `isExternalFileTarget` (`new ExternalFileWidget(...).toDOM()`); anything else (an unresolved image, or a nested note transclusion) returns `null` and the caller falls back to the original plain-text rendering, unchanged.
- **Task checkbox lines** (`- [ ] .../- [x] ...`) inside a transcluded bullet list previously rendered as an ordinary `<li>` running the *whole* line — including its own literal `[ ]`/`[x]` — through `renderCell`, with no checkbox and no done styling. `renderMarkdownBlock`'s list-building loop now checks each line against `TASK_LINE_RE` first: a match gets `cm-task-line`/`cm-task-done` (mirrors the live editor's own `TaskCheckboxWidget` classes, so strikethrough-when-done matches exactly) and a **read-only** checkbox — a plain `disabled` `<input type="checkbox">` for the plain unchecked state, or a `STATUS_ICON` glyph `<span>` otherwise — same "not interactive" convention already used for a dataview `TASK` block's rows, since editing a transcluded task in place doesn't make sense (the source note is where that happens, same reasoning as the read-only transcluded table above). Only the checkbox + done-state styling were in scope here; the live editor's overdue-due-date red highlighting was deliberately not ported to this read-only rendering (would need re-deriving `renderCell`'s already-built HTML to splice a styled span into, for comparatively little value in a display-only view).
- **`renderMarkdownTable(lines, startIdx)` and the `TABLE_DELIM_RE`-gated check that calls it** were missing entirely at first — `renderMarkdownBlock` had no table branch at all, so a `| a | b |` line inside a transcluded section just fell through to the generic paragraph case, space-joining every table row into one garbled blob of pipe characters passed through `renderCell` (which itself has no table-parsing logic either, being meant for a single cell/line of inline text). Reported as "si hago una transclusión de una sección que tiene dentro una tabla, la tabla no se visualiza correctamente." Fixed by reusing `parseTableSrc`/`tableAligns` — the same functions `TableWidget` and the table context menu already share — to build a **read-only** `<table class="cm-table">` (no `contentEditable`/`wireCell` wiring at all; editing a transcluded table doesn't make sense, the source note is where that happens) from every run of consecutive pipe-containing lines. Detection (`renderMarkdownBlock`'s main loop, checked before every other block type): a candidate line contains `"|"` **and** the line right after it matches `TABLE_DELIM_RE` (`/^\s*\|?[\s:|-]+\|?\s*$/`) and contains at least one literal `-` — the delimiter-row requirement is what tells a real table apart from an ordinary paragraph line that merely happens to contain a pipe character; the `-`-required check on top of the regex specifically excludes a blank/whitespace-only line, which the character class alone would otherwise still match (whitespace is itself one of the allowed characters).
- Clicking `.cm-transclusion-open` is wired into `linkClickHandler` exactly like `.cm-md-link`/task checkboxes: sends `{ type: 'open-transclusion', target: btn.dataset.target }`. The host's `navigateToTarget` (`createIfMissing: false`) resolves it, opens the target note in the same column, scrolls to the `#section` heading if one was given, and disposes the current panel — same UX as clicking any other wiki-link in this app's single-pane navigation model.
- `scroll-to-line` (host → webview): moves the selection to `doc.line(msg.line + 1).from` and dispatches `EditorView.scrollIntoView(pos, { y: 'center' })`. Sent by the host ~350ms after `vscode.openWith` resolves, targeting whichever panel `panelsByPath` says now owns that document path (works whether the target editor was freshly created or was already open).

### `hoverPreviewPlugin` — Ctrl/Cmd+hover wiki-link preview popup (`HoverPreviewView`)

Obsidian's "page preview": holding Ctrl (Cmd on macOS) while the mouse rests over a `[[wiki-link]]` (or a table cell's `[data-wiki]` span) shows a small floating popup with the target note's content, without navigating to it. Reuses the exact same host round-trip and cache as `transclusionPlugin` above (`transclusionCache`/`requestTransclusion`/`transclusion-result`) since the data need is identical — raw target string → `{ content, title, line, error }` — which also means a target already fetched for one feature previews instantly for the other.

- Detection lives in `linkClickHandler`'s own `mousemove`/`mouseleave` handlers, not a separate DOM walk: `mousemove` locates a `.cm-wiki-link` (via the existing `isWikiLinkEl`) or `[data-wiki]` ancestor of `e.target`, reads its target string the same way the `click` handler already does (`dataset.target || textContent.trim()`, or `dataset.wiki` for table cells), and forwards `{ e, linkEl, rawTarget }` to `HoverPreviewView.onMouseMove()`. The handler always returns `false` — it only observes, never claims the event, so normal cursor placement/selection is untouched.
- **Why the Ctrl/Cmd check reads `e.ctrlKey`/`e.metaKey` off the mousemove event instead of tracking `keydown`/`keyup`**: keyboard events only fire while some element in the page has focus, and would miss the common case of "Ctrl already held, then move the mouse over a link" (e.g. focus is on the title field, or nothing in the webview has focus at all). A mousemove event's modifier flags are always accurate regardless of what has focus, so `onMouseMove` re-derives `ctrlHeld` fresh on every call instead of maintaining a separate boolean.
- `HoverPreviewView` (`hoverPreviewPlugin = ViewPlugin.fromClass(...)`) is a pure side-effect plugin managing a detached `div.cm-hover-preview` appended to `view.dom` — same shape as `WikiSuggestView`, not a CM6 decoration. `onMouseMove(e, linkEl, rawTarget)`: if Ctrl/Cmd isn't held or there's no link under the cursor, calls `leaveLink()` (hide); if `linkEl` is the same element already being tracked, does nothing (avoids restarting the delay timer on every pixel of mouse movement over the same link); otherwise starts a `HOVER_PREVIEW_DELAY` (300ms, matching Obsidian's own hover-preview delay) timer before calling `show()`.
- `show()` reads `transclusionCache.get(target)` — `undefined` (not yet fetched) triggers `requestTransclusion(target)` exactly like a transclusion widget would, and renders whatever is available immediately (a loading placeholder if `undefined`). The `'transclusion-result'` message handler, after updating the cache and dispatching `transclusionRebuildEffect` for `transclusionPlugin`, also calls `view.plugin(hoverPreviewPlugin)?.refresh()` so an open popup waiting on that exact target repaints with the real content instead of staying stuck on "Cargando…".
- `render()`/`paint()` follow the identical `requestMeasure`-deferred pattern as `WikiSuggestView.render()` (see below) rather than reading `getBoundingClientRect()` synchronously — this can be invoked from inside a `domEventHandlers` callback (`mousemove`), and CM6 forbids synchronous layout reads at arbitrary times just as it does inside a `ViewPlugin.update()`. Positioned the same way as `.cm-wikilink-suggest`: absolute offsets relative to `view.dom`'s bounding rect, anchored under the hovered link's own `getBoundingClientRect()` rather than the cursor position (there is no text cursor involved in a hover).
- Rendered body reuses `renderMarkdownBlock()` verbatim (same escaping/no-recursion guarantees as `TransclusionWidget`) — an optional `div.cm-hover-preview-title` (target filename) followed by the rendered content, or a one-line error message for `'not-found'`/`'section-not-found'`.
- **Closing**: releasing Ctrl/Cmd without moving the mouse afterward would otherwise leave the popup open until the next `mousemove` re-evaluates it — a plain mousemove-driven check can't react to a keyup with no accompanying pointer movement. A module-level `document.addEventListener('keyup', ...)` (checking `e.key === 'Control' || e.key === 'Meta'`) calls `currentView.plugin(hoverPreviewPlugin)?.leaveLink()` directly, independent of mouse position. The popup also has its own `mouseenter`/`mouseleave` tracking (`overPopup` flag) so moving the pointer off the link and onto the popup itself (to read a long preview or select its text) doesn't immediately hide it — `leaveLink()` only hides when `overPopup` is false.

### Task checkbox lines (in `livePreviewPlugin`, `ListItem` handling)

Handled entirely by plain-text regex against `state.doc.lineAt(node.from).text` inside the existing `ListItem` branch of `livePreviewPlugin`'s tree walk — **not** via a Lezer AST node, even though `markdown({ base: markdownLanguage })`'s default config was empirically verified (via a throwaway script iterating the syntax tree over `"- [ ] test"`) to already produce GFM `Task`/`TaskMarker` nodes. Regex was used anyway because it's simpler to keep in one place alongside the due-date/priority/recurrence text-scanning, which has no AST representation regardless.

- `TASK_LINE_RE = /^([\s\t>]*)([-*+]|[0-9]+[.)]) +\[(.)\] *(.*)$/` — detects the line and captures the status char (group 3). Matches `TaskRegularExpressions.taskRegex` in the sibling `angelCastro.obsidian-like-tasks` extension.
- `TASK_CHECKBOX_RE = /^([\s\t>]*)([-*+]|[0-9]+[.)]) +(\[.\])/` — narrower match used only to locate the exact `<indent><marker> [<char>]` span for the widget replacement (consumes the marker + checkbox, then at most one extra trailing space is swallowed — mirrors the existing `ListMark` → `BulletWidget` replacement).
- Status char one of `xX-` (done/cancelled) → line gets `cm-task-line cm-task-done` (line-level, via `Decoration.line`); any other char → just `cm-task-line`. Line numbers recognised as tasks are tracked in a per-build `taskLines: Set<number>` so the plain `ListMark` handler (further down in the same tree walk) can skip adding its `BulletWidget` for that line — otherwise the two replacement decorations would overlap.
- The `<marker> [<char>] ` span is replaced with `TaskCheckboxWidget(checked, line0based)` — a `WidgetType` whose `toDOM()` returns a `<span class="cm-task-widget">` wrapping the real `<input type="checkbox">` (class `cm-task-checkbox`, `data-line` set to the 0-based doc line number), or a status-icon `<span>` for non-plain states. **Unlike `BulletWidget`, this is rendered on the active/cursor line too** (the task-line branch runs before the `active.has(ln)` gate that hides other inline markers on the cursor's line), so the checkbox stays clickable while editing that line's text.
  - **`.cm-task-status-icon` box sizing**: a color-emoji glyph (🔄⏸️👤❌...) renders noticeably larger than the checkbox's own `1em` box at the same `font-size`. An earlier version gave this class `width/height: auto` specifically to let each glyph size itself, which was exactly backwards — it's what made icons of different sizes/paddings misalign against the checkbox and against each other in a list of mixed-status tasks (confirmed by rendering a real sample through this exact CSS in headless Chrome, not just by eye). Fixed *then* by giving it the *same* fixed box as `.cm-task-checkbox` plus a shrunk `font-size` and `overflow: hidden`, to clip the (still comparatively large) glyph into that box instead of letting it dictate the box. That in turn backfired the other way — reported as "los iconos de estado se ven cortados para cualquier estado que no sea To do" (a screenshot showed only a corner of the glyph surviving): a color emoji's *visual* glyph is taller than its nominal font-size box regardless of how small that font-size is, so shrinking `font-size` never stopped the clip, it just made the box (and therefore the clip) smaller. Fixed again by matching `fontSize`'s multiplier to the box's own (`* 1`, not `* 0.7`) and dropping `overflow: hidden` — the glyph is fully visible now, at the cost of occasionally overflowing the box's edges slightly rather than a guaranteed-but-broken exact fit.
  - **Every property on this rule carries `!important`, and the box/font size use `calc(var(--md-font-size, 14px) * N)` instead of a plain `Nem`** — reported with a real vault theme ("Border", set via `obsidianLike.obsidianTheme`): every one of these icons (in-progress, delegated, done, cancelled — everything except the plain unchecked checkbox, a different rule entirely) was invisible. Same root cause already documented for `.cm-code-block` below: a vault theme's CSS loads *after* this, into a later `<style>` tag (`theme-css` postMessage), and many themes reset generic inline/list styling (`display`, `font-size`, `color`) broadly enough to catch elements they were never written with in mind — normal specificity doesn't help against a theme rule that also uses `!important`. Confirmed the fix's robustness (Border's actual CSS lives in the user's vault, not this repo, so it couldn't be inspected directly) against a synthetic worst-case theme in headless Chrome: a bare `span { font-size: 0 !important }` rule. The first attempt — `!important` alone, keeping `0.7em`/`1em` — still failed that test: `em` on `font-size` resolves against the *parent's* computed font-size, so zeroing font-size on some ancestor `<span>` (e.g. `.cm-task-widget`) silently zeroed this icon's `0.7em` right along with it, `!important` or not — `!important` only decides *which* declaration wins, not what a relative unit resolves against. Switching to `calc(var(--md-font-size, 14px) * N)` sidesteps this entirely: `--md-font-size` is a custom property set once on `document.documentElement`, and custom properties aren't touched by any `font-size` declaration on an ancestor, however broad.
- For non-done tasks, the remaining text after the checkbox is scanned (still plain regex, not AST) for `TASK_DUE_RE` (`📅`/`📆`/`🗓` + `YYYY-MM-DD`), `TASK_PRIORITY_RE` (`🔺⏫🔼🔽⏬`), and `TASK_RECURRENCE_RE` (`🔁` + rule text). Only the due date gets a visual treatment: if it parses to a calendar date strictly before today, that substring gets `Decoration.mark({ class: 'cm-task-overdue' })` (red/bold, mirrors `TaskDecorations.ts`'s `overdueDecoration` in the sibling Tasks extension). Priority/recurrence are parsed for parity with that extension's signifiers but currently have no dedicated styling.
- Clicking `.cm-task-checkbox` is wired into the existing `linkClickHandler` (`mousedown` prevents default / `click` fires the action, same pattern as wiki-links and `cm-md-link`): it sends `vscode.postMessage({ type: 'toggle-task', line: Number(el.dataset.line) })`. The extension host applies the actual toggle (see "Task checkboxes" under extension-host message handlers above) and the resulting document change flows back through the normal `external-update` path, so the widget re-renders with the new state once applied — there is no local optimistic DOM update.

### ```tasks``` query blocks (also in `livePreviewPlugin`)

Unlike single-checkbox lines, a ```tasks``` query needs data from the *entire vault* (the sibling extension's in-memory task index), which the webview cannot compute from the current document's AST alone. Rendering is therefore an async round-trip: webview → this extension's host (`postMessage`) → `angelCastro.obsidian-like-tasks`'s exported API → back to the webview → render. Since `_build()` runs synchronously, results can't be awaited inline — see the cache/effect mechanism below.

- **`.cm-tasks-query` renders in `.cm-content`'s own 780px reading-width column — no break-out.** Two earlier versions tried to give a task listing (many columns: tags, id, priority, dates, backlink, edit button) more room than plain prose by breaking out of that column via a `100vw`-relative `calc()`: first a literal, uncapped `100vw` (fixed the "checkbox stuck alone on its own line above a long description" wrapping bug — see `.cm-tasks-query-item` below — but on a wide pane left the listing touching the pane's actual edges while everything else on the page kept its normal margins), then `width: min(100vw, 1200px); margin-left: calc(50% - min(50vw, 600px))` to re-cap and re-center on a wide pane. Both were reported as the listing's side margins vanishing entirely in practice (flush against the pane's edges) — the `vw`-relative math didn't reliably line up with this element's real containing block. The actual, simplest fix: don't break out at all. A normal-flow block with no explicit width naturally fills its parent `.cm-line`'s content box, which *is* `.cm-content`'s own (780px-capped, 28px-padded, auto-centred) box — the same one every paragraph already renders in — so this reads with *exactly* the same left/right margin as normal text, at any pane width, with zero special-casing to get wrong. Confirmed against the real compiled `out/editor.bundle.js` (not just a throwaway approximation): loaded it in headless Chrome with a real ` ```tasks ` block and measured the rendered DOM — a prose line and `.cm-tasks-query` land at the identical `getBoundingClientRect().left`/`.right`. Long descriptions/titles still wrap correctly at this width — that's `.cm-tasks-query-item` being plain inline flow rather than flexbox (below), unrelated to how wide this container is; the earlier width experiments were solving a "give it more room" preference that was never actually required for wrapping to work.

- Detected via the `FencedCode` node in the same tree walk as `Table` (empirically verified: `markdown({ base: markdownLanguage })`'s default GFM setup produces `FencedCode` → `CodeMark`, `CodeInfo` (the info string), `CodeText` (the full query text as one node, even when multi-line), `CodeMark`). Only blocks whose `CodeInfo` is exactly `tasks` are touched; everything else falls through to the unmodified default `FencedCode`/`CodeMark`/`CodeText` handling.
- Rendering follows the exact same non-block strategy as `Table` (`block: true` decorations are banned — see the comment above `livePreviewPlugin`): the opening ` ```tasks ` fence line becomes a single-line `Decoration.replace({ widget: TasksQueryWidget })`; every remaining line (query text + closing fence) is collapsed via an empty `Decoration.replace({})` + `Decoration.line({ class: 'cm-table-row-hidden' })`, reusing that class rather than adding a redundant one. Also mirrors `Table`'s active-line fallback: if the cursor is on any line inside the block, the raw ` ```tasks `/query text/`` ` `` is left untouched and editable.
- `tasksQueryCache: Map<string, TasksQueryResultDTO>` (keyed by trimmed query text) and `tasksQueryPending: Set<string>` (dedupes in-flight requests) are module-level. `requestTasksQuery(query)` posts `{ type: 'run-tasks-query', query }` if that text isn't already pending. `tasksRebuildEffect: StateEffect` is a no-op effect dispatched purely to force a `livePreviewPlugin` rebuild once data arrives or is invalidated — the same trick `foldEffect` uses for fold toggles; `livePreviewPlugin.update()` checks for it alongside `docChanged`/`selectionSet`/`viewportChanged`.
- `TasksQueryWidget(query, result)` — `result` is whatever `tasksQueryCache.get(query)` held at `_build()` time: `undefined` while in flight (renders a "Cargando…" placeholder) or the resolved `TasksQueryResultDTO` once available. Passing `result` into the constructor (rather than reading the cache from inside `toDOM()`) makes `eq()` correctly report "not equal" once data arrives, so CM6 actually replaces the placeholder DOM instead of reusing it.
- **`zoom factor <N>%` query line** (a ````tasks``` addition specific to this port, not part of upstream Obsidian Tasks — see `core/Query/Query.ts` in `obsidianlike_tasks`) arrives as `result.zoomFactor` on `TasksQueryResultDTO`, always a number (`100` = normal size when the query didn't specify one, never `null`/`undefined`). `renderTasksQueryResult` applies it as CSS `zoom` (not `font-size`/`transform: scale`) directly on `container` (the `.cm-tasks-query` wrapper `TasksQueryWidget.toDOM()` created) — `zoom` is non-standard but Chromium-supported, and this webview is Chromium-based, so it's safe here; it scales the *entire* rendered subtree (text, emoji/icon badges, padding, the layout box itself) as one unit, which `font-size` alone wouldn't do for anything with fixed-px padding, and `transform: scale` wouldn't do for layout at all (the box stays its original size, just visually shrunk inside it — no more content actually fits). Set to `''` (not the literal string `'100%'`) whenever the factor is 100, so a query with no `zoom factor` line renders pixel-identical to before this existed.

An element appended straight to `document.body` is a *sibling* of `.cm-editor`, never a descendant, so a `vsTheme` class rule can never match it — **any future body-appended floating element in this file needs inline styles (or to be appended inside `.cm-editor`/`view.dom` instead), not a `vsTheme` class.** `.dv-filter-popover` itself was left as-is (out of scope for this fix, not reported broken) but is flagged with a comment at its own definition — it's presumably subject to the exact same bug, just apparently unnoticed so far.

- A tasks-query checkbox carries `data-path` **and** `data-line` (a result can come from any file in the vault, not just the open one), so `linkClickHandler` checks `.cm-task-query-checkbox` *before* the plain `.cm-task-checkbox` branch (the query variant matches both selectors) and sends `{ type: 'toggle-task-at-location', path, line }` instead of the single-file `{ type: 'toggle-task', line }`.

- `ensureSubscribedToTasksChanges()` (module scope, single-flight via `subscribedToTasksChanges`, called from the top of `resolveCustomTextEditor` every time a panel opens) subscribes to the Tasks extension's `onDidChangeTasks` event and, on every fire, broadcasts `{ type: 'tasks-changed' }` to every panel in `activePanels`. If the lookup fails, it retries up to 5 times, 1.5s apart, instead of giving up for the rest of the session — a single long-lived panel opened during the cold-start race described above would otherwise never get another chance to subscribe (there's no new panel-open event to retry from if the user doesn't close and reopen it).

An earlier version cleared the cache immediately, which forced every visible ```tasks``` block to flash to its "loading" placeholder and back on every single edit; showing stale-but-correct data for the fraction of a second it takes to refetch reads as instant, not as a flicker.

Since the spread happened before that extension's own task index existed, the getter always saw `undefined` and returned a throwaway, never-fired `EventEmitter`. `ensureSubscribedToTasksChanges()` here "subscribed successfully" every time, just to the wrong emitter — nothing was ever wrong on this side. See `c:\git\obsidianlike_tasks\CLAUDE.md`'s gotchas for the fix. Diagnosed with a real `vscode.OutputChannel` on both sides (not `console.log`, which isn't visible for a normally-installed, non-debug extension).

### ```dataview```/```dql```/```dataviewjs``` query blocks (also in `livePreviewPlugin`)

Same non-block replace-and-collapse strategy, same `FencedCode`-node detection, and the same cache/pending/rebuild-effect shape as the ```tasks``` block above — deliberately copy-pasted rather than generalized into a shared helper, since the two differ in exactly one place (structured DTO + local DOM renderer for tasks, vs. a ready-made HTML string for dataview) and a shared abstraction would have to branch on that difference anyway.

- `info === 'dataview' || info === 'dql' || info === 'dataviewjs'` is checked in the same `if (n === 'FencedCode')` branch as `info === 'tasks'`, after it (so a block genuinely tagged ` ```tasks ` still gets that specific treatment, not this one) and before the generic fenced-code-block fallback. Same active-line guard: cursor anywhere inside the block leaves the raw fence/query text editable instead of rendering it.
- `dataviewQueryCache: Map<string, DataviewQueryResultDTO>` keyed by `dataviewCacheKey(lang, query) = lang + ' ' + query` (a space-joined string, not a `[lang, query]` tuple, because `Map` keys compare by reference for non-primitives — a plain string key was the simplest way to get value equality without a second lookup structure). `dataviewQueryPending: Set<string>` (same key shape) dedupes in-flight requests. `dataviewRebuildEffect: StateEffect` — a second, independent no-op effect (not reusing `tasksRebuildEffect`); `livePreviewPlugin.update()` checks `e.is(tasksRebuildEffect) || e.is(dataviewRebuildEffect)` so either one triggers a rebuild.
- `requestDataviewQuery(lang, query)` posts `{ type: 'run-dataview-query', lang, query }` — no `path`/`currentFilePath` field: the host already has `document.uri` in scope inside `resolveCustomTextEditor`'s `onDidReceiveMessage` closure (same reasoning `toggle-task`'s handler uses `document.lineAt` directly instead of the webview sending file content), so there's nothing for the webview to add there.
- `DataviewQueryWidget(lang, query, cached)` — `cached` is whatever `dataviewQueryCache.get(key)` held at `_build()` time: `undefined` while in flight (a "Cargando consulta dataview…" placeholder, class `cm-dataview-query-loading`) or the resolved `{ ok, html }` once available. `eq()` compares all three fields (`other.cached` by reference, same as `TasksQueryWidget`'s `result` check) so CM6 only re-renders once a *different* result object actually arrives.
- **`toDOM()` sets `wrap.innerHTML = this.cached.html` directly** — the one place in this file that assigns `innerHTML` from a cross-extension source rather than building DOM nodes via `document.createElement`/`textContent` (contrast `renderTaskRow`/`renderMarkdownBlock`, which never do this). Justified here because: (a) the HTML comes from `obsidianlike_dataview`'s own `render/html.ts`, which HTML-escapes every field/tag/cell value it embeds and never echoes back a `<script>` tag or an inline event-handler attribute, and (b) the webview's CSP (`script-src 'unsafe-inline'` scoped to `cspSource`, no `unsafe-eval`) wouldn't execute an injected `<script>` tag even if one slipped through — but this is trust-the-sibling-extension's-output, not a defense-in-depth guarantee, so if `render/html.ts` on the other side ever starts embedding raw user-controlled text (e.g. a note's own frontmatter string values) without escaping, this becomes a real (same-origin, low-severity — everything here is the user's own local vault content) XSS surface. Keep both sides' escaping intact if either changes.
- CSS: `.cm-dataview-query`/`.cm-dataview-query-loading` (block wrapper + loading state, mirrors `.cm-tasks-query`/`-loading`) plus a block of `.cm-dataview-query .dv-*` rules styling the *sibling extension's* own class names (`dv-error`, `dv-empty`, `dv-list`, `dv-table`/`th`/`td`, `dv-link`, `dv-task-group`, `dv-task-list`, `dv-calendar-day`) — kept in sync **manually** with `obsidianlike_dataview/src/render/html.ts`; there's no shared stylesheet or generated types between the two repos, so a class renamed on that side silently stops being styled on this one until someone notices and updates `vsTheme` here too.
- Result links use `data-wiki` (see "Dataview query blocks — soft dependency" above under the extension-host section), so `linkClickHandler`'s existing generic `[data-wiki]` handling (`mousedown` prevents default, `click` posts `open-note`) covers them with no changes to that handler.
- Message listener: `dataview-query-result` sets the cache entry, clears the pending flag, dispatches `dataviewRebuildEffect`. `dataview-changed` (sent whenever the sibling extension's vault-wide index changes) re-requests every key currently in `dataviewQueryCache` — same "don't clear first, let the stale result sit until the fresh one replaces it" reasoning as `tasks-changed` above, so edits elsewhere in the vault don't make every visible dataview block flash to its loading state.
- Task checkboxes inside a `TASK`-type dataview block render as plain `disabled` `<input type="checkbox">` (from `obsidianlike_dataview`'s own HTML renderer) — **not interactive**, unlike a ```tasks``` query row's checkbox. Wiring that up would need a new message type on both sides (something like `toggle-dataview-task-at-location`, since `obsidianlike_dataview`'s current public API has no task-mutation method at all, only read/query) — not implemented; a known gap, not an oversight.
- **A plain `TASK` query (no `GROUP BY`) renders as a flat list, no per-file heading** — confirmed against the real Obsidian Dataview docs (grouping is opt-in via an explicit `GROUP BY`, e.g. `GROUP BY file.link`), so `obsidianlike_dataview`'s engine and this file's CSS both need to handle the flat case as the *common* one, not the exception. `.cm-dataview-query .dv-task-list` uses `display: flex; flex-direction: column; gap: 2px` rather than native `<ul>`/`<li>` block flow specifically because a plain `<li>` inherits `.cm-content`'s prose `line-height: 1.75`, which reads as noticeably more vertical padding between task rows than real Obsidian — same fix `.cm-tasks-query-list`/`-item` already applies for the sibling Tasks extension's rows.
- **Gotcha**: three literal NUL (0x00) bytes were found in this file's own dataview-integration code after a concurrent edit/commit round-trip — inside the two `"lang query"` cache-key comments, and, more seriously, inside `dataviewCacheKey`'s actual separator character (silently turning the intended `lang`-space-`query` join into `lang`-NUL-`query`), which broke `dataview-changed`'s re-split (`key.indexOf(' ')` found no space, so every re-request got mis-sliced). Root cause not identified — plain-ASCII space characters became NUL bytes somewhere between this file being written and re-read, in a repo two Claude sessions were editing at once. Fixed by a byte-level NUL-to-space replacement. `grep`/`Read` render a NUL byte invisibly, so this only surfaced as `grep -n` reporting "binary file matches" on an otherwise-plain-text `.js` file — that's the tell to check for again if this class of bug resurfaces.

#### Excel-like client-side sort/filter on `TABLE` results (`enhanceDataviewTable`)

Sorting/filtering a rendered ```dataview `TABLE` is a **pure display-layer transform over the already-rendered `<table class="dv-table">`** — it reorders/hides `<tr>` elements already in the DOM and never touches the underlying DQL query, never round-trips to the host, and never asks `obsidianlike_dataview` to re-run anything. This was a deliberate scope call: "filter/sort independent of the query results" is exactly what the user asked for, and doing it purely client-side means it works instantly with no host latency and needs zero changes on the sibling extension's side.

- `enhanceDataviewTables(root)` runs once, from `DataviewQueryWidget.toDOM()` right after `wrap.innerHTML = this.cached.html`, and finds every `table.dv-table` under `root` via `enhanceDataviewTable(table)`. It is **not** re-run on every `livePreviewPlugin` rebuild — only when `toDOM()` itself runs, i.e. only when `eq()` says the widget's `(lang, query, cached)` actually changed (fresh query results replaced the table). A rebuild that reuses the same DOM node (the common case — typing elsewhere, moving the cursor, scrolling) leaves the enhanced table and its sort/filter state completely alone.
- State (`{ originalRows, sortCol, sortDir, filters: Map<col, Set<excludedValue>> }`) lives in `dvTableState`, a `WeakMap<HTMLTableElement, State>` — keyed off the table element itself rather than stored as fields on the widget, so it naturally survives as long as the DOM node does and is garbage-collected for free once the table is replaced. `originalRows` is a snapshot of `tbody.rows` taken once at enhancement time (before any filtering/sorting mutates `tbody`'s children) — every subsequent filter/sort recomputes from this snapshot rather than from `tbody`'s current (already reordered/hidden) state, so toggling a filter off always restores the exact original row order with no cumulative drift.
- **Sort**: clicking a `<th>`'s label (`.dv-th-label`, the header text wrapped in a `<span>` at enhancement time) cycles that column through none → ascending → descending → none, resetting to a fresh ascending sort if a *different* column is clicked (single active sort column, matching a plain "click column header to sort" affordance rather than Excel's separate multi-column sort dialog, which was judged out of scope for this). `dvCompareCells` numeric-compares when both cell strings parse as numbers (so `"2"` sorts before `"10"`), otherwise falls back to `localeCompare`; blank cells always sort last regardless of direction.
- **Filter**: the small `▾` button (`.dv-th-filter`) next to each header opens a checkbox-list popover (`dvOpenFilterPopover`) — a search box that narrows the visible checkbox rows (doesn't filter the table itself), a "Seleccionar todo" checkbox with correct indeterminate state, and one checkbox per unique value in that column. Checkbox state is inverted into an *excluded*-values `Set` (`state.filters.get(col)`) rather than an included-values set, so "no filter on this column" is simply "no entry in the `Map`" instead of "a set containing every possible value" — cheaper and avoids having to know the full value list just to represent "everything is shown."
- **Cascading like Excel's own AutoFilter**: the value list a column's popover offers only considers rows that already pass every *other* column's active filter (`dvRowPassesFilters(state, tr, col)` with `col` excluded from the check) — so filtering column A down to a few rows narrows what column B's dropdown even offers, not just what the table currently shows.
- Each checkbox toggle applies immediately (`dvApplyTable` runs on every `change` event) rather than requiring an "OK" button like real Excel — judged close enough to "análogo" and meaningfully simpler (no need to stage-and-commit-or-revert a temporary copy of the excluded set while the popover is open).
- The popover is appended to `document.body`, **not** as a descendant of the widget's own DOM — this lets it float above the CM6 editor (`position: fixed`, high `z-index`) without being clipped by any `overflow: hidden` ancestor inside the editor content area, and as a side effect means CM6's own event routing never sees clicks inside it at all (it isn't part of `view.dom`), so no `ignoreEvent` handling is needed for the popover itself — only for the two controls that *are* inside the widget's DOM, `.dv-th-label` and `.dv-th-filter` (see `DataviewQueryWidget.ignoreEvent` below), for the same reason `TasksQueryWidget`'s filter input needed one: without it, clicking them moved the document cursor into the block's range, which made the next rebuild treat the cursor as "inside" and swap the rendered widget back to raw source before the click could register.
- A single `document`-level `mousedown` listener (installed once, guarded by `dvPopoverOutsideHandlerInstalled`) closes the popover when the click target isn't inside `.dv-filter-popover` or `.dv-th-filter` itself — this has to live outside the widget for the same reason `ignoreEvent` doesn't need to cover the popover: it isn't part of the editor's DOM, so a click there wouldn't reach a listener scoped to `view.dom`.
- `.cm-dataview-query .dv-table th` was changed from a plain table-cell to `display: flex` (label + filter button side by side, `justify-content: space-between`) — safe in the Chromium engine VS Code webviews run on; not universally portable CSS but this codebase already targets exactly one rendering engine.
- Not implemented (known gaps, not oversights): multi-column sort, "sort by color/icon," and any persistence of sort/filter state across a rebuild that replaces the table (e.g. `dataview-changed` firing) — a fresh result set starts with a clean sort/filter state every time, mirroring "the underlying data changed, start over" rather than trying to re-apply a stale filter to different rows.

### Font/theme metrics and `requestMeasure()`

CM6 measures line-height/character metrics once during its own layout passes, using whatever font is actually resolved by the browser at that moment. Two things in this codebase change those metrics *after* CM6 has already measured and cached them, without going through CM6's own transaction system: the `theme-css` message (an Obsidian theme can define its own heading fonts/line-heights, and — per "Why theme CSS is sent via postMessage" above — it lands ~300ms after the webview's initial paint, well after CM6's first layout) and `font-update` (changes `--md-font`/`--md-font-size`, which `.cm-content` reads directly). If CM6's cached geometry goes stale relative to what's actually painted, anything computed from it — most visibly `drawSelection()`'s custom-drawn selection boxes — ends up positioned against the old metrics instead of the current ones, i.e. offset from the text it's supposed to cover. A one-time `document.fonts.ready.then(() => view.requestMeasure())` right after editor creation, plus the calls from those two message handlers, fix it.

**Confirmed fixed on real macOS hardware** — but the actual chain was more specific than "a timing race" originally suggested: `resolveCustomTextEditor` only sends `theme-css` at all when `getThemeCss()` returns non-empty (`if (themeCss) { webviewPanel.webview.postMessage(...) }`). While `getThemeCss()`'s macOS path-lookup bug (see its entry above) was making it return `''`, the `theme-css` message — and therefore the `requestMeasure()` call inside its handler — never fired *at all* on that machine, not just late. Fixing the theme lookup made both problems disappear together: the theme's own CSS started applying, and the `requestMeasure()` call attached to that same message finally got a chance to run and correct CM6's stale initial layout (which, until then, had been permanently based on `vsTheme`'s fallback font/sizing rather than the theme's actual ones — not a race that later resolved itself, but a fix that was never reached).

### `foldPlugin`

`ViewPlugin` outside `previewCompartment` (works in both live-preview and source mode) that implements collapsible headings.

- `foldedSet: Set<number>` — module-level set of `line.from` positions of folded headings.
- `foldEffect: StateEffect` — dispatched on toggle to trigger plugin rebuild.
- `collectHeadings(state)` — scans the full syntax tree for `ATXHeading[1-6]` nodes.
- For each heading in viewport: adds `FoldToggle` widget at `line.from` with `side: -1`.
- `FoldToggle.toDOM()` renders the Obsidian DOM structure: `div.cm-fold-indicator[contenteditable=false] > div.collapse-indicator.collapse-icon > svg.svg-icon.right-triangle`, but the `<svg>` is built with `width="0" height="0" viewBox="0 0 0 0"` and no `<path>` — it's kept only so the Border theme's mask-image reskin selectors (and the click-to-fold hit area) have an element to attach to; see "Fold indicator" under "Heading styling architecture" above for why it's empty, hover-only, and positioned left of the color bar rather than always-visible after it. When folded, `div.cm-fold-indicator` also gets `is-collapsed` class, which triggers the Border theme's accent-color CSS for the indicator icon.
- For each folded heading: collapses lines from heading+1 to start of next heading at same/higher level (or end of doc) using `Decoration.replace({})` + `Decoration.line({ class: 'cm-fold-hidden' })`.
- Fold positions are remapped through document changes via `u.changes.mapPos()`.
- `currentView` module-level ref is set after editor creation so `FoldToggle.toDOM()` can dispatch effects.
- **Note**: `HyperMD-header-N` line classes are added in `livePreviewPlugin`, NOT here. Adding both a widget and a line decoration at the same position (`h.lineFrom`) in one plugin causes CM6 `RangeSetBuilder` ordering issues where the line decoration is silently dropped.

**Follow-up bug: folding a heading in a long document could leave a large (reported: several hundred px) blank gap.** Root cause was CSS, not a CM6 height-estimation issue as first suspected — `.cm-fold-hidden` (and the structurally identical `.cm-table-row-hidden`/`.cm-code-fence-hidden`, used to collapse table rows/```tasks```/frontmatter lines and fenced-code fence lines respectively) zeroed `height`/`line-height`/`padding`/`min-height` with `!important`, but never touched `margin`/`border`/`border-radius`/`box-shadow`. CM6 combines `Decoration.line()` classes from *different* extensions onto the same line's `class` attribute, so a folded line commonly ends up with `cm-fold-hidden` *and* some other box-styling class at once — most concretely, a folded section containing a fenced code block, where `.cm-code-block-first`/`-last` (see "Inline code vs. fenced code block styling" above) sets non-zero `margin-top`/`margin-bottom`/`border`/`padding` of its own, *also* with `!important`. Same-specificity `!important` ties go to whichever rule is declared later in the stylesheet — `.cm-fold-hidden` and friends used to live much earlier (grouped next to the decoration logic they support), so `.cm-code-block-first`/`-last`'s margin/border/padding, declared later, silently won and leaked through. One leftover margin is a handful of px; a folded heading whose content included several such blocks (or nested folds, lists, etc.) compounded that into the reported gap.
- Fixed by consolidating all three into one rule (`.cm-table-row-hidden, .cm-code-fence-hidden, .cm-fold-hidden`) moved to the very end of `vsTheme`'s spec object — after every other rule it might need to out-cascade — and widening it to zero `margin`/`border`/`border-radius`/`box-shadow` too, not just the properties one specific bug report happened to trace.
- **Still not a guaranteed fix, and confirmed insufficient**: reported again — the blank gap persisted even after the above, on a document with no code blocks at all (just a folded heading followed by several blank-line-separated paragraphs). Root cause: moving the rule to the end of `vsTheme`'s *own* stylesheet only wins against *other rules in that same stylesheet* — an Obsidian theme's CSS loads into a wholly separate, *later* `<style>` tag (see "Why theme CSS is sent via postMessage"), so a theme rule reaching for the same property via `!important` on some more general selector (a blanket `.cm-line` rule, or something targeting line spacing generally) can still win purely because it loads after *everything* `vsTheme` produces, no matter where within `vsTheme` the rule sits. This is the exact same risk `.cm-code-block`'s own comment already calls out for its background/border — that one just accepts it ("!important + hope the theme doesn't also reach for it").
- **`hiddenLineDeco(cls)`** (just above `livePreviewPlugin`, replacing every direct `Decoration.line({ class: 'cm-table-row-hidden' | 'cm-code-fence-hidden' | 'cm-fold-hidden' })` call across the file — table rows, ```tasks```/frontmatter collapse, fence-line collapse, and this plugin's own fold collapse, 7 call sites total) closes that gap for real: it sets the *exact same* zeroing properties as an **inline `style` attribute** on the line, in addition to the class. An inline declaration beats *any* class-based rule regardless of `!important`, because CSS compares specificity before falling back to source order within the same importance tier, and inline specificity always outranks a class selector — no external stylesheet, loaded whenever, by whatever theme, can out-specificity a declaration living on the element itself. The CSS class rule stays too (harmless, redundant fallback), but correctness no longer depends on it.
- **Still reported after the inline-style fix too — the actual root cause turned out to be a completely different layer, nothing to do with CSS at all.** Screenshot evidence (a folded heading followed by several blank-line-separated paragraphs) showed the gap unchanged. Diagnosed by building a real `EditorView` against the actual fold-collapse logic in `jsdom` (throwaway script, not checked in) and inspecting each `.cm-line`'s actual rendered `class`/`style` after folding: every *non-blank* line inside the folded span correctly received `cm-fold-hidden` and its inline zeroing style — but every *blank* line inside the same span received neither. The CSS (both the class rule and the inline style) had been correct all along; it simply never reached the blank lines' DOM elements in the first place.
  - **Root cause**: every one of these 7 call sites pushes *two* decorations per hidden line into the same merge/sort/`RangeSetBuilder` pipeline — a content-hiding `Decoration.replace({ from: line.from, to: line.to })` and a box-collapsing `Decoration.line` (`hiddenLineDeco`, added as a zero-length point at `line.from`). For a line with real text, these two decorations land at different points (`(line.from, line.from)` for the line decoration vs. `(line.from, line.to)` for the replace, `line.to > line.from`), so both survive the sort/merge cleanly. For a **blank** line, `line.to === line.from`, so the replace decoration *also* degenerates to a zero-length span at exactly `(line.from, line.from)` — the identical point as the line decoration. Two decorations added to a `RangeSetBuilder` at an exact identical point silently keep only one of the pair (confirmed empirically, not from documentation); depending on which one lands last in whichever stable-sort tie-break order the merge happens to produce, the *line* decoration — the one actually carrying the height:0 CSS — is the one that gets dropped. Non-blank lines in the very same folded block collapsed correctly the whole time, which is why earlier CSS-focused fixes (both the specificity consolidation and the inline-style escalation) never moved the needle: the bug was never in what the CSS said, only in whether the decoration carrying it ever reached the DOM.
  - **Fix**: at all 7 call sites (frontmatter, `Table` remaining rows, ```tasks``` query block, `dataviewjs`, `dataview`/`dql`, the two fence lines in `livePreviewPlugin`'s `FencedCode` handling — which are never blank, so unaffected but left as-is — and `foldPlugin`'s own fold-content collapse), the `Decoration.replace({})` push is now guarded with `if (line.to > line.from)`. A zero-length replace decorates nothing anyway (there's no content to hide on an empty line), so skipping it for blank lines changes no visible behavior *except* letting the line decoration — the one actually responsible for collapsing the line to zero height — survive the merge unopposed.

**Same collision, a different culprit: collapsing an H1 that itself contains nested H2/H3 headings still left a gap, one line-height per nested heading.** Reported right after the blank-line fix above shipped, with a repro nesting `## Hijo`/`### Nieto` headings under a folded `# Padre`. `foldPlugin._build()`'s *first* loop pushes a `FoldToggle` widget (`Decoration.widget`, zero-length, at `h.lineFrom`) for **every** heading in the viewport, unconditionally — including a heading that's itself sitting inside an ancestor's already-folded content. That widget decoration and the nested heading's own `hiddenLineDeco` line decoration (pushed later, by the *second* loop) land at the exact same zero-length point (`h.lineFrom` *is* that heading's `line.from`) — the identical "two decorations at one point, only one survives" collision as the blank-line bug above, just with a widget instead of a redundant replace. Confirmed with a real `EditorView` in jsdom (throwaway script, not checked in): every nested heading's own line kept its `FoldToggle` widget and never received `cm-fold-hidden`, while its surrounding (non-heading) paragraph lines — no competing widget there — collapsed correctly. A folded section with several nested headings inside it therefore left one small visible gap per nested heading, compounding into the reported "blank space remains" regardless of what was inside (tables, line breaks, or further headings — anything whose *own line* also happened to coincide with a widget decoration from elsewhere in the same rebuild).
  - **Fix**: `foldPlugin._build()` now computes `foldedSpans = computeFoldedSpans(state, headings)` once, up front (also replacing the second loop's own redundant re-call, no behavior change there), and the `FoldToggle` widget push is skipped whenever `h.lineFrom` falls inside any of those spans (`foldedSpans.some(sp => h.lineFrom >= sp.from && h.lineFrom <= sp.to)`). A heading that's hidden inside a folded ancestor wouldn't have a usable fold toggle anyway (its own line is invisible), so this loses no behavior — it just stops seeding the exact collision that was dropping its hidden-line decoration.

**More serious follow-up bug: folded content was still fully navigable — clickable, arrow-key-reachable, selectable, copyable, and (worst) deletable without the user seeing what they were editing.** The CSS fix above only ever addressed *rendering* — `.cm-fold-hidden` makes a line's box occupy zero visual space, but says nothing to CM6's own cursor/selection model about those document positions, which remain perfectly ordinary as far as navigation is concerned. Reported and confirmed with screenshots: collapsing a heading with several blank-line-separated paragraphs left a region that *looked* empty but was still a real, selectable span — click-dragging across it visibly highlighted the hidden text.
- **`computeFoldedSpans(state, headings?)`** (factored out of `foldPlugin._build()`, which now just calls it instead of computing the same thing inline — no behavior change there) returns `{ from, to }` character-position spans for every *currently* folded heading's content. Single source of truth, now used by three separate consumers: `foldPlugin`'s own hide-decorations (unchanged), a new `atomicRanges` provider, and `moveVerticalByLine`'s own fold-skipping (both below).
- **`foldAtomicRanges = EditorView.atomicRanges.of(view => ...)`** (added to `createEditor`'s extensions, alongside `foldPlugin`, outside `previewCompartment`) registers each folded span as a genuine CM6 cursor-navigation barrier. Confirmed by reading `@codemirror/view`'s own source (`node_modules/@codemirror/view/dist/index.js`): ranges in this facet get skipped over both by `moveByChar`/`moveVertically`-based navigation (so Home/End and any arrow-key handling actually routed through CM6's *own* commands can't land inside) **and** by mouse-driven selection — `updateSelection`'s pointer-event path explicitly runs the new selection through `skipAtomsForSelection` before dispatching, confirming click/drag placement respects it too, not just keyboard commands.
- **What `atomicRanges` does *not* cover**: `moveVerticalByLine` (this file's own Up/Down replacement — see above) deliberately bypasses CM6's built-in vertical motion for cross-line moves, for the unrelated goal-column-corruption reasons documented on that function — meaning it never runs through the code path that consults `atomicRanges` at all. Its cross-line branch now does its own fold-check instead, against the same `computeFoldedSpans`: after computing the raw target line number (`curLine.number + dir`), if that line falls inside any folded span, it's redirected to one line past the far edge of that span (in the direction of travel) — landing directly on the next real heading (or whatever follows) rather than the fold's first hidden line. Verified with a throwaway script simulating exactly the reported repro (a folded heading with several blank-line-separated paragraphs): Down from the folded heading lands on the very next heading, and Up from there returns straight to the folded heading, both skipping the hidden content entirely rather than stepping into it one line at a time.
- Deliberately *not* attempted: preventing `Ctrl+A`/select-all or programmatic selection from including folded content — `atomicRanges` only governs where a selection *endpoint* can be individually navigated to, not what a `Ctrl+A`-sized range can span; matches VS Code's own native code folding, where select-all and copy still include folded-away content.

### Line indentation and hanging indent for list items (bullet + ordered)

`ListItem` handling (inside `livePreviewPlugin`'s tree walk, alongside the task-checkbox logic above) sets `padding-left`/`text-indent` as an **inline style** on each list line's `Decoration.line`, not purely via the `cm-list-depth-N` CSS classes (which still get added, and still exist in `vsTheme` as a harmless fallback, but an inline style always wins regardless of stylesheet order — see the fold-gap bug above for why that guarantee mattered enough here too).

- **The problem**: a list item's marker (bullet or number) is inline content that only ever renders on the item's *first* source line. Plain `padding-left` alone pushes every visual row of a block by the same fixed amount — so a second (or later) row, whether from `EditorView.lineWrapping` soft-wrapping a long single-source-line item, or an actual multi-line source (2-space-indented continuation, or CommonMark "lazy" continuation with no indent at all), rendered flush with the *marker's* position instead of past it, since nothing pushes those extra rows in by the marker's own width the way the marker itself implicitly does on line 1.
- **The fix**: the standard CSS hanging-indent pair. `padding-left: (nestingIndent + markerWidth)` pushes the whole block in; `text-indent: -markerWidth` (only on the line carrying the marker) pulls just that *first* line back out by the marker's width — `text-indent` by definition only ever affects a block's own first line, never wrapped continuation rows, which is exactly the asymmetry needed. `markerWidth` is `LIST_MARKER_WIDTH_EM` (a single module-level constant, `1.5em`) — see "Marker width must be a single shared constant, and the raw marker text needs it too" below for why this used to be a per-type value (`1.2em` bullets / `2em` ordered) and why that was wrong.
- **Continuation lines**: previously, only the ListItem's *first* line (`state.doc.lineAt(node.from)`) ever got the `cm-list-line`/depth class at all — a hard multi-source-line item's second+ line got none of it, not even the old flat padding. Fixed by additionally reading the item's own direct content node — `node.node.getChild('Paragraph') || node.node.getChild('Task')` (a GFM task item wraps its content in a `Task` node instead of a plain `Paragraph` — confirmed via a syntax tree dump, `- [ ] text` produces `ListItem > (ListMark, Task)`, no `Paragraph` child at all) — and decorating every line from just after the first through that content node's own end with `cm-list-continuation` (same computed indent, no `text-indent`, since there's no marker on these lines to compensate for). Reading the item's own *direct* content node specifically (not `node.to`, which would also reach into any nested sub-list that follows) means a nested sub-list's own lines are untouched here — they get their own, deeper indent when their own `ListItem` is visited separately in the same walk, not this depth's.
- **Task checkbox lines get their own, shallower indent formula** (`taskIndentEm`/`taskFirstLineStyle`/`taskContLineStyle`, computed alongside the plain-list versions above) — `(depth - 1) * 1.5 + markerW` instead of `depth * 1.5 + markerW`, i.e. the whole formula shifted left by exactly one nesting level. At the top level (`depth === 1`) this puts `taskIndentEm` at just `markerW`, and since `text-indent: -markerW` still applies, the *checkbox itself* lands at 0 — flush with `.cm-content`'s own padding, i.e. the same left edge as a plain paragraph. A checklist isn't "a sublist of the document" the way a plain bullet list is (Obsidian's own Tasks plugin renders a top-level one the same flush way), so it shouldn't read as indented relative to prose. A *nested* task (depth 2+ — a subtask under another task, or under a plain bullet) still lands one full level deeper than its parent, since only the base offset shifted, not the per-level increment; only plain (non-task) bullet/ordered lists are unaffected, still using the original `depth * 1.5 + markerW`. The task-vs-plain branch already existed for other reasons (`taskM` in the `ListItem` handler) — this only changed which precomputed style string each branch's `Decoration.line` (and its continuation lines, via `activeContLineStyle = taskM ? taskContLineStyle : contLineStyle`) picks up. Confirmed against the real compiled bundle: a top-level task's checkbox and a plain prose line's text land at the identical `getBoundingClientRect().left`, a nested subtask sits exactly one level deeper, and a plain (non-task) bullet at the same depths is unchanged from before this fix.

**Follow-up bug: numbered and bulleted list items didn't align with each other, and a bulleted list's own alignment shifted depending on whether its line was actively being edited.** Reported via screen recording (the user typed the bug report itself into a test note first, then demonstrated both lists). Root cause was that `markerW` — used to compute `text-indent`/`padding-left` above — was a *declared* reservation, not tied to what actually got rendered for the marker on any given line:

- An **inactive bullet** line's marker (`-`/`*`/`+`) was replaced by `BulletWidget`, a fixed-width `1.2em` span (`.cm-list-bullet`) — matching the old `markerW` for bullets exactly.
- An **active bullet** line (cursor on that line) left the raw `- `/`* ` text completely unstyled — the old `ListMark` handling only ran at all when `!active.has(ln)` (it sat behind the same `if (active.has(ln)) return;` gate as `HeaderMark`/emphasis marker-hiding), so on the active line the marker rendered at its own natural glyph width instead of `1.2em`.
- An **ordered** marker (`1.`, `10.`, `100.`) never matches `/^[-*+]$/`, so it never got `BulletWidget` either — active or inactive, it always fell through to `return false` with no decoration at all, rendering at its own natural, variable width instead of the old `markerW` of `2em`.

Since `text-indent: -markerW` only cancels out to `padding-left - markerW` for the *declared* `markerW`, and the actual on-screen marker occupied a *different* width in two of those three cases, the paragraph text immediately after the marker landed at a different horizontal position in each case — visibly jumping left/right as a bullet line gained/lost focus, and never lining up between a bulleted and an ordered list at the same depth to begin with.

**The fix, first version** (`LIST_MARKER_WIDTH_EM`, a single module-level `1.5` constant defined just above `vsTheme`, used both by the CSS and by the `ListItem`/`ListMark` decoration logic):
1. `markerW` in the `ListItem` handling was just `LIST_MARKER_WIDTH_EM` unconditionally — no per-type branch, so a bulleted and an ordered list's own hanging-indent math always agreed at the same depth. (This also removed `listTypeStack`, the per-nesting-level `'BulletList'`/`'OrderedList'` stack that only existed to feed the old per-type branch — nothing else read it.)
2. ### `WikiSuggestView` — wiki-link suggestion popup

Not CM6's built-in autocompletion (that was the old `wikiComplete` source, removed): a plain floating `<div class="cm-wikilink-suggest">` appended as a child of `view.dom`, positioned with absolute offsets computed from `coordsAtPos` (`view.dom`/`.cm-editor` already has `position: relative` from CM6's own base theme). It's a `ViewPlugin.fromClass(WikiSuggestView)` (`wikiSuggestPlugin`) with no decorations — a pure side-effect plugin, same shape as `foldPlugin` conceptually but managing its own detached DOM instead of CM6 decorations. Built this way (rather than `Completion.info`/`detail`) because the desired look — a directory subtext line under each note name, a persistent keybinding-hint footer, a dedicated "no results" row — needs full control over per-row markup that the Completion API doesn't expose, same reasoning as `TableWidget`/`TransclusionWidget`/`TasksQueryWidget`.

- **Trigger**: `WIKI_TRIGGER_RE = /\[\[([^\]\n]*)$/` against the text before the cursor, re-evaluated on every `docChanged`/`selectionSet` update — but `currentContext()` additionally requires the match to be the currently edit-activated, unclosed link (`!activeLinkClosed && activeLinkFrom === openBracketFrom`, see the "wiki-link activation" section under `wikiLinkPlugin`), since the raw regex match alone can't tell "still typing a new `[[`" apart from "cursor merely navigated to sit before an existing link's own `]]`". Matches whether preceded by `!` or not (fires for both `[[note]]` links and `![[note]]` transclusions) — only the `[[...]]` span (from the `[[` onward, i.e. `openBracketFrom` through the cursor) is ever replaced on accept.
- **No `#` typed yet** (`mode: 'notes'`): empty query → `noteHistory.slice(0, WIKI_SUGGEST_SCAN_MAX)` (see `note-history` below); non-empty query → `matchNotes(query)`, which filters `noteIndex` by substring match on `name` (case-insensitive) and sorts by match-index-then-name so a name *starting with* the query sorts ahead of one that merely contains it, capped to `WIKI_SUGGEST_SCAN_MAX` (50, just a sanity bound — see "Sliding window" below for how more matches than fit on screen are actually reached). Zero matches renders a "No se encontraron resultados" row instead of hiding the popup.
- **`#` typed** (`![[Note#` or `[[Note#`, `mode: 'headings'`): unchanged from the old `wikiComplete` — `requestHeadings(notePart)` posts `{ type: 'get-headings', id, note: notePart }` and resolves via the `headings-result` handler, correlated by a locally-generated `id` tracked in `pendingHeadingRequests: Map<id, resolve>` (parallel to how `tasksQueryPending`/`transclusionPending` dedupe host round-trips, but every request gets its own id here since results aren't cached/reused across queries). A `headingsToken` counter discards a stale reply if a newer keystroke has since re-triggered the request. Results are the host's `parseHeadings()` order (document order, not alphabetical), filtered by substring on `text`, capped to `WIKI_SUGGEST_SCAN_MAX`, labeled with `'#'.repeat(level) + ' '` prefix. An empty `notePart` (bare `[[#`) closes the popup rather than searching — same as before.
- **Accept** (Enter, or a mouse click on a row — the popup is a real detached DOM node so this uses plain `addEventListener`, not `linkClickHandler`): replaces `[openBracketFrom, cursorPos)` with `[[Name]]` (notes mode), `[[notePart#Heading]]` (headings mode), or — when there are zero matches — `[[<raw typed text>]]` verbatim, then places the cursor immediately after the closing `]]`. If the two characters immediately after the cursor are already `]]` (the cursor was reopened *inside* an already-closed link — e.g. clicking back between "target" and its own trailing `]]` to type `#heading`, rather than typing a brand-new link from scratch), the replacement range is extended by 2 to swallow them; otherwise the newly-inserted text's own `]]` duplicates the pre-existing one, producing `[[note#heading]]]]`.
- **Navigation**: `ArrowUp`/`ArrowDown` move `selected` with wraparound (through the *full* `this.items` list, not just the visible window) and re-render; `Escape` hides the popup and remembers the exact trigger context (`dismissedKey`) so it doesn't immediately reopen until the typed text or cursor position actually changes. All four keys, plus `Enter`, are bound via `wikiSuggestKeymap = Prec.highest(keymap.of([...]))` — highest precedence so they intercept before `defaultKeymap`'s own Enter/arrow-key handling, but only while `view.plugin(wikiSuggestPlugin).open` is true; otherwise each binding returns `false` and normal editing proceeds untouched.
- **Sliding window over `this.items`** (`paint()`): only `WIKI_SUGGEST_MAX` (5) rows are ever rendered — with a note with more headings than that (originally reported: a document with 6+ headings, where nothing could reach heading 6 onward), `this.items` itself is *not* truncated to 5 anymore (see `WIKI_SUGGEST_SCAN_MAX` above); instead `paint()` computes `windowStart = clamp(this.selected - (WIKI_SUGGEST_MAX - 1), 0, this.items.length - WIKI_SUGGEST_MAX)` and renders `this.items.slice(windowStart, windowStart + WIKI_SUGGEST_MAX)`. This one formula, recomputed fresh on every `paint()` from nothing but the current `selected` index, reproduces the whole requested behavior with no extra "which direction was I scrolling" state: while `selected` is within the first page it's always 0 (`windowStart` clamps at 0); once `selected` scrolls past row 5, the window is *always* positioned so `selected` sits at its last visible slot — so a single Down at the bottom edge reveals the next item and drops the top one, and a single Up from there (recomputing the *same* formula for the *decremented* `selected`) lands the window one slot earlier too, immediately surfacing the item above rather than just moving the highlight within an unchanged window. `row.dataset.index` (read back by both the click handler and `accept()`) is the *absolute* index into `this.items`, not the row's position within the visible slice.
- **Flip upward near the bottom edge** (`paint()`, after the row/footer DOM is built): the popup always used to draw downward from the cursor (`top: coords.bottom + 4`), which could end up partially or entirely clipped when the cursor sat near the bottom of the visible editor pane. `paint()` now reads `dom.offsetHeight` right after building the popup's content (forces a synchronous reflow of just this detached, already-appended subtree — safe from inside `write()`, unlike a `ViewPlugin.update()`, since `write()` is exactly the phase CM6's `requestMeasure` sets aside for touching the DOM) and compares it against `editorRect.bottom - coords.bottom` (space below the cursor) vs. `coords.top - editorRect.top` (space above); if the popup wouldn't fit below *and* there's more room above, it's positioned to grow upward from just above the cursor's line instead (`top: coords.top - popupHeight - 4`). No scrolling/height-capping for the case where neither direction fully fits — same "best effort, whichever side has more room" behavior as VS Code's own suggestion widget, not attempted to be more sophisticated than what was asked.
- Matched substrings are bold (`highlightMatch`): the popup builds `innerHTML` from `escapeHtml()` output plus `<b>...</b>` around the first case-insensitive occurrence of the query — safe against injection since note names/heading text only ever go through `escapeHtml` first, never raw.
- **`render()` defers the actual paint via `requestMeasure`, never reads layout synchronously**: `render()` (called from `recompute()`, which itself runs inside the `ViewPlugin`'s own `update()` on every keystroke) needs `view.coordsAtPos()` to position the popup — but CM6 throws `"Reading the editor layout isn't allowed during an update"` if that's read synchronously from inside `update()`. Worse, when a `ViewPlugin`'s `update()` throws, CM6 destroys and **permanently deactivates** that plugin for the rest of the view's lifetime (`PluginInstance.update()` catches the exception, calls `.destroy()`, then `deactivate()` sets `spec = value = null` — confirmed by reading `node_modules/@codemirror/view/dist/index.js` directly) — so the very first `[[` typed in a session crashed the plugin once, silently, and the popup never appeared for any `[[` typed afterward either, for the rest of that editor's lifetime. Fixed by having `render()` call `view.requestMeasure({ key: this, read, write })` instead of reading `coordsAtPos`/`getBoundingClientRect` directly; the actual DOM paint moved into `paint(measured)`, invoked from the `write` callback once CM6's own measure phase runs (never synchronously inside `update()`). `key: this` ties queued requests to this instance so a later `render()` call (e.g. arrow-key navigation) replaces an earlier still-pending one instead of piling up. Verified by loading the real built `out/editor.bundle.js` into a jsdom-backed `EditorView` and dispatching a `[[` keystroke transaction directly — reproduced the exact crash pre-fix, confirmed it's gone post-fix (a separate, pre-existing jsdom limitation — no `Range.getClientRects`, real Chromium has it — still throws inside the deferred `read` callback in that test environment, but CM6's `requestMeasure` catches per-request read errors in isolation and doesn't propagate them to the plugin, unlike the direct synchronous call this replaced).

### Find/replace panel (`ObsidianSearchPanel`, Ctrl+F) — built on `@codemirror/search`

Obsidian's own find/replace overlay (a small floating card, top-right, with case/whole-word/regex toggles, a match counter, and a collapsible replace row) had no equivalent in this editor at all. Rather than hand-rolling cursor iteration, match highlighting, and regex handling from scratch, this is built directly on `@codemirror/search` (added as a new dependency) — that package already gets the hard parts right (an automatic `.cm-searchMatch` decoration on every match in the viewport, `SearchQuery`/`getSearchQuery`/`setSearchQuery` state management, `findNext`/`findPrevious`/`selectMatches`/`replaceNext`/`replaceAll` commands) — and only the *panel itself* is custom, via the one documented extension point for that (`search({ createPanel })`). The library's own default panel is a plain unstyled `<form>` with English labels and no match counter, which is why a custom one was worth building at all.

- **Why Ctrl+F is a real `contributes.keybindings` command (`vaultTool.openSearchPanel`) instead of relying on `searchKeymap`'s own `Mod-f` binding reaching the webview** — same reasoning, and the same proven pattern, as `vaultTool.editTaskAtCursor`'s `Shift+Alt+E` history (see that section): a plain in-webview keymap binding for a chord this common risks losing to whatever VS Code's own webview host does with it first (a generic "find in webview" feature, or the class of coarse keybinding-table interception already documented there) before this editor's own JS ever sees it. The command, scoped `"when": "activeCustomEditorId == 'vaultTool.markdownEditor'"`, posts `{ type: 'open-search-panel' }` to the active panel; the webview's handler just calls `openSearchPanel(view)`. `searchKeymap` (`Mod-f`/`F3`/`Mod-g`/`Escape`/`Mod-Shift-l`/`Mod-Alt-g`/`Mod-d`) is still included in `createEditor`'s own `keymap.of([...])` regardless, both as a harmless fallback and because `F3`/`Mod-g`/`Escape`/`Mod-d` (next/previous/close/select-next-occurrence) are useful once the panel is already open and don't have the same "does this webview even see the keydown" risk `Mod-f` alone does.
- **Why the panel doesn't react to VS Code's native "Edit → Buscar" menu item** — a real limitation, not a bug: native top-menu items (File/Edit/Selection/...) each invoke a *fixed* built-in VS Code command directly, entirely bypassing the keybinding-table/`when`-clause resolution a real key press goes through. "Edit → Buscar" is wired to VS Code's own generic find command (built for a real `TextEditor`/Monaco instance), which has nothing to act on for a webview-based custom editor and just does nothing. There is no `contributes.menus` target for the native Edit menu — only specific submenus/context menus are extensible — so there's no supported way to reroute that particular menu item to this panel; Ctrl+F (or the Command Palette entry, "Obsidian-like: Buscar y reemplazar") remains the only way in.
- **`top: true`, and why that specific option matters here**: `search({ top: true, createPanel: ... })` puts the panel inside `.cm-panels-top`, whose `position: sticky` (from `@codemirror/view`'s own base theme) keeps it pinned to the *top of the scrolling container* as the user scrolls — `ObsidianSearchPanel`'s own `position: absolute; top: 8px; right: 8px` is anchored inside that sticky container, which is what actually keeps the floating card visually pinned near the top-right of the visible viewport rather than wherever the top of the document happens to be. `.cm-panels`/`.cm-panels-top`/`.cm-panels-bottom` themselves are neutralized in `vsTheme` (`background`/`border: none !important`) — that container's own base-theme styling is a full-width opaque bar meant for a panel that fills it, which would otherwise show as an empty colored strip above the editor now that this panel manages its own floating-card chrome instead. Nothing else in this codebase uses the Panel API (`WikiSuggestView`/`HoverPreviewView`/`TableMenuView` are all plain `ViewPlugin`s appending straight to `view.dom`), so neutralizing `.cm-panels` globally is safe.
- **Match counter ("3 de 12")**: `@codemirror/search`'s public `SearchQuery` has no built-in concept of "which match is current" — `computeMatchInfo(query, state)` iterates `query.getCursor(state)` itself, counting total matches and finding the 0-based index of whichever one (if any) has exactly the same `{from, to}` as the current selection — `findNext`/`findPrevious`/`openSearchPanel` all set the selection to precisely a match's own range, so this equality check is what "current" means here, without the library exposing that as its own concept. Capped at `MAX_COUNTED_MATCHES` (999, shown as `"999+"` past that) for the same reason `selectMatches` itself caps at 1000 internally — a common short query in a large document shouldn't make every keystroke rescan the whole thing unbounded.
- **`runScopeHandlers(view, e, 'search-panel')` inside the panel's own `keydown` listener** — mirrors exactly what `@codemirror/search`'s own default panel does, for the same reason: keydown events on the panel's `<input>`s never reach CM6's `contentDOM`-scoped keymap at all (they're siblings of `contentDOM`, not descendants), so `searchKeymap`'s entries tagged `scope: "editor search-panel"` (`F3`/`Mod-g`/`Escape`) have to be explicitly replayed by hand while focus sits in the search/replace field, or they'd only ever work while `contentDOM` itself has focus.
- **"AB" preserve-case toggle, and why it's disabled in regex mode**: `matchReplacementCase(source, replacement)` is a plain heuristic (all-caps/all-lowercase/capitalized source → same transform applied to the replacement) used by `replaceOnePreservingCase`/`replaceAllPreservingCase`, two custom functions mirroring `@codemirror/search`'s own internal `replaceNext`/`replaceAll` logic (same precise-match check, same selection-remapping-through-the-changeset pattern) plus that one transform. Deliberately **not** attempted for a regex query — `query.replace` can contain `$1`-style backreferences there, which the library's own internal (non-exported) `getReplacement()` resolves, and "preserve case" against an arbitrary regex match has no single obviously-correct meaning anyway — so the toggle is simply disabled (`disabled` attribute + dimmed) whenever the regex flag is on, falling back to the library's own plain `replaceNext`/`replaceAll` (imported as `cmReplaceNext`/`cmReplaceAll` specifically to avoid a same-named class method shadowing the import in the method body it's called from).
- Couldn't be verified in a live browser/webview before shipping the first version (the usual jsdom-backed `EditorView` smoke test this codebase's own history relies on repeatedly failed here on an unrelated Node/jsdom version mismatch on this machine) — built from reading `@codemirror/search`'s own source/type declarations directly instead, and confirmed to at least compile/bundle cleanly. Flagged to the user as needing real hands-on testing rather than claimed as verified.

### Ordered-list auto-renumbering (`orderedListRenumberPlugin`)

Requested: deleting (or adding) an item in the middle of a numbered list should shift every following sibling's own number to stay sequential — deleting item "2." from a 1/2/3 list should turn the old "3." into "2." automatically, matching Obsidian's own live-numbering behavior. lezer-markdown has no notion of "this list's numbering just became inconsistent" to react to, so this reacts the same regex-driven way `mdLinkPlugin`/`highlightMarkPlugin` already handle syntax lezer doesn't parse — but unlike those (pure rendering, scoped to `previewCompartment`), renumbering is a real edit to the document's own text, so this plugin is registered *outside* `previewCompartment`, applying identically in source mode and live preview.

- `ORDERED_MARKER_RE = /^(\s*)(\d+)([.)])(\s+)/` detects an ordered-list marker line and captures its indent/number/punctuation/trailing-space separately, so a fix-up can replace just the number digits without touching anything else on the line.
- `findOrderedListRun(doc, lineNumber)` finds the full contiguous run of same-indent ordered-list-item lines containing `lineNumber` — tolerating blank lines (allowed inside a "loose" list) and more-deeply-indented content (a nested sub-list, wrapped continuation text — skipped over without ending the run, since it belongs to whichever item precedes it) in between without breaking the run. Returns `null` if that line isn't itself part of an ordered list.
- `orderedListRenumberPlugin` (a plain side-effect `ViewPlugin`, no decorations — same shape as `wikiLinkActivationTracker`) reacts only to a genuine user edit (`u.transactions.some(t => t.isUserEvent('input') || t.isUserEvent('delete'))`) — never to its own renumbering dispatch below (tagged with a distinct `userEvent`, so this check is false for it) or an external-update/autosave reconciliation, either of which could otherwise loop or fight with an edit still in flight.
- **Dispatching a fix-up transaction from inside `update()` isn't safe** — CM6 disallows a new transaction synchronously while one is still being processed, the same reasoning `WikiSuggestView.render()`'s own comment gives for deferring its `coordsAtPos` reads through `requestMeasure` rather than reading them synchronously inside `update()`. Fixed by deferring to a microtask (`Promise.resolve().then(...)`): by the next tick, the triggering transaction has fully landed, so re-deriving everything fresh from `view.state` at that point (rather than trying to reuse anything computed during the `update()` call) is both simpler and immune to any staleness the deferral might otherwise introduce.
- Inside the microtask: scans the cursor's own line plus one neighbour on each side (covers a merged-line backspace, where the cursor now sits where the deleted line used to start, and an Enter-split insertion alike, without re-scanning the whole document on every keystroke) for the enclosing ordered-list run via `findOrderedListRun`, recomputes the *correct* sequential numbers for that run — starting from whatever number the run's own first item already has, so a list deliberately started at "5." keeps starting there — and only if any line's actual written number differs from what it should be, dispatches one combined fix-up `{ changes, userEvent: 'ordered-list.renumber' }` replacing just the mismatched number spans.

**Bug found while building the Tab-to-nest feature below: renumbering a run silently stomped a nested sub-list's own independent numbering.** `findOrderedListRun`'s own boundary-finding (`belongs()`) correctly treats a deeper-indented line as tolerated *filler* within a run's `[first, last]` range without making it a member of that run's own sequence — but the renumbering loop right below it, which walks that same `[first, last]` range to assign sequential numbers, never re-checked indent at all: it called `ORDERED_MARKER_RE.exec(line.text)` on every line in range and treated *any* match as "the run's next item," regardless of whether that line's own indent actually matched the run's. Since the regex's leading `(\s*)` group matches any amount of indentation, a nested sub-list item (itself starting with a bare `\d+[.)]` marker, sitting inside the outer run's line range purely as tolerated filler) matched too — and got its number silently overwritten to whatever the *outer* sequence expected next, immediately erasing any independent numbering the nested list was supposed to have. Manually indenting a sub-item by hand (before the Tab feature existed) would have hit this identically; it just hadn't been exercised until the Tab feature's own tests tried indenting an item under a preceding sibling and watched the number it had just set get reverted a moment later by this same plugin's own microtask. Fixed with one added condition — `if (!m || m[1].length !== run.indent) continue;` — skipping any line whose own indent doesn't match the run's before treating it as a sequence member; `findOrderedListRun`'s boundary logic already computed exactly this same equality for a different purpose, so the fix is bringing the numbering loop into agreement with it, not new logic.

### List item indent/outdent via `Tab`/`Shift-Tab` — nest into / out of a sub-list

Requested directly: "Si le doy a la tecla tabular en entre el '3. ' y el 'Subelemento' de la tercera linea, se añade una indentación, pero el número se mantiene como 3, en vez de empezar una sublista cuyo primer elemento debe ser el 1." Before this, `Tab` on a list line fell through to `indentWithTab`'s plain `indentMore` — CodeMirror's language-aware indent computation happened to add *just enough* whitespace for the line to parse as nested content of the preceding item (CommonMark itself only cares that a continuation is indented at least as far as the parent marker's own width), so the line visually shifted right, but nothing ever touched its own marker text or renumbered anything — "3." stayed "3.", and the outer list's remaining items never closed the gap it left behind. (The renumbering-loop bug documented just above compounded this once a fix was attempted: even after manually rewriting the marker to "1.", `orderedListRenumberPlugin`'s own next pass silently reverted it back to "3." — found via this feature's own testing, and fixed there rather than here.)

- `BULLET_MARKER_RE = /^(\s*)([-*+])( +)/` — the bullet-list counterpart to `ORDERED_MARKER_RE`, needed because demote/promote has to work on both list types (only the ordered case needs any renumbering afterward).
- `parseListMarkerLine(text)` tries `ORDERED_MARKER_RE` then `BULLET_MARKER_RE`, returning `{ indent, prefixLen, type, punct|bullet }` — `prefixLen` is the *whole* marker match length (indent + marker + trailing space), i.e. exactly where this line's own content starts, which doubles as the exact indent width CommonMark requires a would-be child's content to reach for it to actually nest under this line.
- `rebuildListLine(view, line, marker, newIndent)` replaces the line's leading marker with one at `newIndent` spaces, keeping the line's own marker *type* unchanged (ordered stays ordered, bullet stays bullet) but — for an ordered marker — always resetting the number to `"1"` (reusing the line's own punctuation character, `.` vs `)`). This relies entirely on `orderedListRenumberPlugin` (registered earlier in the extensions list, so it reacts to *this* same dispatch) to fix the number up afterward if it turns out to land next to an existing nested run instead of starting a fresh one — deliberately not duplicated here; the dispatch is tagged `userEvent: 'input.indent'`, a dotted subtype of `'input'`, specifically so that plugin's own `isUserEvent('input')` check picks it up. Also preserves the cursor's relative position within the line (inside the old marker → lands right after the new one; inside the content → same offset into the content, now shifted).
- `demoteListLine(view)` (bound to plain `Tab`): requires an empty selection on a recognized list-item line, then walks backward from the line above, tolerating blank lines and *more*-indented lines (nested content of whatever sibling it's looking for — same tolerance `findOrderedListRun.belongs()` already uses) until it finds a line at the *exact same* indent (the sibling to nest under) or hits something shallower/non-list first (nothing to nest under → returns `false`, falling through to `indentWithTab`'s ordinary `indentMore`). On finding the sibling, rebuilds the current line at `sibling.prefixLen` (i.e. exactly where the sibling's own content starts).
- `promoteListLine(view)` (bound to `Shift-Tab`): the inverse — walks backward for the nearest list-item line with *strictly less* indent (the current item's own parent) and rebuilds the current line at that parent's own indent, making it a sibling of the parent instead of a child. No shallower list line at all (already top-level) → `false`, falls through to `indentWithTab`'s `indentLess`.
- `listIndentKeymap = Prec.highest(keymap.of([{key:'Tab', run: demoteListLine}, {key:'Shift-Tab', run: promoteListLine}]))`, registered alongside `orderedListRenumberPlugin` — outside `previewCompartment`, since (like renumbering) this is a real edit to the document's text, not a rendering choice, so it applies identically in source mode. Precedence matters here specifically so it gets first refusal ahead of the plain `keymap.of([...indentWithTab])` further down in the same extensions array; falling through (`return false`) on every "not applicable" branch is what lets ordinary Tab-indentation still work everywhere else (a code-ish paragraph, a table cell already handled by its own keydown wiring, etc.).
- **A red herring investigated and discarded along the way**: `indentWithTab` (bare, unspread) looked suspicious next to `...defaultKeymap`/`...historyKeymap` in the same array — the working theory was that CM6's `keymap.of` silently drops any array element lacking its own `.key` (confirmed true by reading `buildKeymap` in `@codemirror/view`'s source: `for (const b of bindings)` reads `b.key`/`b[platform]` directly off each entry, `continue`s if absent), and `indentWithTab` looked like it might itself be an *array* of two bindings meant to be spread. Spreading it (`...indentWithTab`) crashed immediately (`TypeError: Id is not iterable`) — `@codemirror/commands`'s actual export is `const indentWithTab = { key: "Tab", run: indentMore, shift: indentLess }`, a single object using the `shift` property `buildKeymap` already special-cases (`if (b.shift) add(scope, "Shift-"+name, b.shift, ...)`), not an array at all. The original bare (unspread) usage was correct all along; reverted immediately once the jsdom bundle-load surfaced the crash.
- Verified end-to-end (not just compiled/bundled) against the exact reported repro, via the same real-Chrome harness described in the "round three" marker-styling entry above: typed the four-item list from the report, clicked into line 3, pressed `Tab` — line 3 nested as "1." under line 2 and line 4 renumbered from "4." to "3." automatically; pressing `Tab` again on the new line 4 joined it into the same nested run as "2."; `Shift-Tab` on that line promoted it back out, correctly renumbering both the list it left and the list it rejoined.

### Line-based vertical cursor movement (`verticalMoveKeymap`) — replaces CM6's default Up/Down

Reported symptom: in a bulleted list, pressing Down repeatedly landed on every *other* item (skipping one each press, the skip compounding the further into the list the cursor moved), and Up from past the list then jumped back multiple lines at once instead of one.

Root cause is a documented CodeMirror behavior, not something specific to this codebase (confirmed via [a discuss.codemirror.net thread](https://discuss.codemirror.net/t/moving-of-cursor-with-different-size-mark-decoration-and-replace-decoration-issues/4198), where a maintainer explains the exact mechanism and recommends the fix below). CM6's default `cursorLineDown`/`cursorLineUp` (bound by `defaultKeymap`) move by *visual pixel position*: the first key press in a vertical-move sequence captures a "goal" x-coordinate from the current line's on-screen styling, and every further press in that same sequence reuses that stale goal rather than re-deriving it — this is what lets moving down through a run of short lines land back at the same column once you reach a long one again. It breaks specifically when a line's *on-screen width changes between presses of the same sequence* — exactly what `livePreviewPlugin`'s active-line marker-hiding does: `[- * +] ` is shown raw only on the line the cursor is currently on, replaced by `BulletWidget` everywhere else. Every arrow press moves the active line, which changes decorations on both the old and new line, which invalidates the goal x-coordinate the *next* press in the sequence is about to reuse.
- Confirmed empirically (not just by matching the maintainer's description) with a throwaway script (`@codemirror/state` only, no DOM/jsdom needed — this is pure line/column arithmetic, not a layout question) reproducing the exact reported bullet-list text and asserting the resulting line after each simulated Down/Up.
- Fix, per that thread's recommendation: bypass goal-column/pixel tracking entirely and move by plain document line number instead of visual position. `moveVerticalByLine(view, dir, extend)` computes `curLine.number + dir` directly and re-anchors at the same *character column* (clamped to the target line's length) — independent of anything actually rendered, so a decoration toggling mid-sequence can't desync it.
- `vGoalCol` (module-level) reimplements just the part of CM6's own goal-column persistence worth keeping — preserving the column through a *sequence* of consecutive vertical moves (e.g. down through several short lines, then back onto a long one) — without involving any pixel/DOM measurement. `dispatchingVerticalMove` (module-level boolean, set only for the duration of `moveVerticalByLine`'s own `view.dispatch()` call) lets the existing `EditorView.updateListener` (already present for `cursor-position` reporting) tell "this selection change is a link in an ongoing vertical-move sequence" apart from any other kind of selection change (typing, click, Home/End, wiki-link navigation, ...), which should still reset `vGoalCol = null` — same as CM6's own goal-column reset on non-vertical motion.
- Bound via `verticalMoveKeymap = Prec.highest(keymap.of([ArrowDown, ArrowUp, Shift-ArrowDown, Shift-ArrowUp]))`, placed in the extensions array *after* `wikiSuggestKeymap` (also `Prec.highest`) — same precedence, but bindings at equal precedence are checked in extension-registration order, so `wikiSuggestKeymap`'s own ArrowDown/ArrowUp (which navigate the `[[` suggestion popup when it's open, and otherwise return `false` to fall through) still get first refusal before this keymap's always-`true`-returning handlers take over.
- Only handles `state.selection.main` (single range) — this editor doesn't enable `EditorState.allowMultipleSelections`, so there's never more than one range to move.

**Follow-up bug: wrapped paragraphs skipped straight to the next real line.** `EditorView.lineWrapping` is on (see `createEditor`'s extensions), so a single *document* line with no embedded newline — an ordinary long paragraph — can still span several on-screen rows. `moveVerticalByLine`'s line-number jump (above) has no concept of that: pressing Down from the paragraph's first visual row landed on the *next document line* (e.g. a blank line right after the paragraph), skipping the paragraph's own remaining visual rows entirely — the exact "natural" wrap-aware behavior CM6's default pixel-based Up/Down had, that switching to pure line-number jumps had traded away without realizing it. Reported by pasting a real multi-paragraph `.md` file into the editor and observing Down from the very first character land on the blank line separating two long paragraphs instead of the paragraph's second visual row.
- Fixed with a hybrid: `moveVerticalByLine` first tries a single, *freshly computed* step via CM6's own `view.moveVertically(EditorSelection.cursor(range.head), forward)` — passing a brand-new cursor with no persisted `goalColumn`, unlike what CM6's own `cursorLineDown`/`cursorLineUp` do internally (that persistence across presses, while decorations change in between, is exactly the earlier bug). If the resulting position is still on the *same* document line (`state.doc.lineAt(pixelCandidate.head).number === curLine.number`), that means the step only moved between wrap-rows of one line — decorations can't have changed mid-line, so there's nothing for the earlier bug to corrupt, and the pixel result is trusted directly. Only when the fresh step *would* cross into a genuinely different document line does it fall back to the line-number + `vGoalCol` character-column jump described above, which is where the original corruption actually lived.
- `vGoalCol` is deliberately left untouched by the same-line (wrap-row) branch — it's not a line-to-line jump, so it has no bearing on that column-preservation mechanism, and touching it there would overwrite a longer-line goal with whatever a mid-paragraph wrap-row happened to clamp to.

**Packaging gotcha hit while testing this fix, unrelated to the bug itself but worth remembering**: `vsce package` (part of `npm run package`) can fail with `ERROR Couldn't detect the repository... The link 'url' will be broken in README.md` and **exit non-zero without writing a `.vsix` at all** — silently leaving the previous build's `.vsix` on disk. Root cause: `vsce`'s README link-rewriter matches literal `[text](something)` sequences even *inside inline code spans* (`` `[texto](url)` ``), and — despite `--allow-missing-repository` being passed — still hard-fails trying to resolve it against a repo URL that doesn't exist for this project (never published, no `repository` field in `package.json`). `--allow-missing-repository` only suppresses a *different* missing-repository warning, not this one. Since the deploy workflow chains `code --uninstall-extension` / `--install-extension` right after `npm run package` regardless of whether packaging actually succeeded, this can silently reinstall a **stale** build with no error surfaced at the install step — always check `npm run package`'s own exit status (or the `.vsix`'s mtime) before trusting a subsequent install actually shipped what was just changed. Fix/avoidance: never write a literal `[text](url)`-shaped example in `README.md`, even inside backticks — rephrase it in prose instead.

### Drag & drop files onto the editor — status: fix attempted, not yet confirmed working

First attempt (raw `document.addEventListener('dragover'/'drop', ...)`) was manually tested and failed: VS Code's own "open the dropped file as a new editor tab" behavior still won. This looked at first like a VS Code-level architectural block (a drag-tracking overlay rendered outside the webview's iframe) — **but that theory doesn't hold up**: `microsoft/vscode#182449` confirms OS-file-drop onto a `CustomTextEditorProvider` webview does reach the webview's DOM (fixed in the June 2024 milestone; only Explorer-tree-internal drags were ever broken, and that's since been fixed too). So on a current VS Code (this repo tests against 1.126.0), the drop should reach our iframe's content just fine.

The real, confirmed-in-source culprit: **`@codemirror/view`'s `EditorView` has its own built-in `drop` handler** (`handlers.drop` in `node_modules/@codemirror/view/dist/index.cjs`) that, on seeing `event.dataTransfer.files.length > 0`, reads each file as *text* (`FileReader.readAsText`) and inserts the result into the document — garbage for a binary file like `.docx`. This built-in handler is bound directly to `view.contentDOM`, which sits *inside* `#editor` — closer to the actual drop target than a `document`-level listener, so it's reached first as the event bubbles, regardless of what a listener bound higher up the tree tries to do. Whether that alone fully explains "opens as a new tab" (as opposed to inserting garbled text) is unconfirmed; either way it's a real bug worth fixing on its own.

CM6 combines event handlers per type as `[...extension-registered domEventHandlers, ...its own built-in handlers.X]` (`computeHandlers` in `@codemirror/view`) and — per `runHandlers` — stops at the first one that returns truthy for that event, calling `preventDefault()` for it. So `dragenter`/`dragover`/`drop` are now registered as part of `linkClickHandler`'s existing `EditorView.domEventHandlers({...})` extension (same mechanism as its `mousedown`/`click` handling, not a raw DOM listener), which places them *before* CM6's own built-in `handlers.drop` in that per-type list — returning `true` there pre-empts CM6's default file-as-text behavior entirely, rather than racing against it.

- `dragenter`/`dragover` (on `linkClickHandler`) — return `true` whenever `e.dataTransfer.types.includes('Files')`; `dragover` also sets `dropEffect = 'copy'`. CM6 calls `preventDefault()` automatically for a truthy return, so the target becomes (and stays) valid for the duration of the drag.
- `drop` (on `linkClickHandler`) — computes the insertion position via `view.posAtCoords({x, y})` (falling back to the current selection head), stashes it in module-level `pendingDropPos`, reads every `File` via `readFileAsDataUrl` (`FileReader.readAsDataURL` wrapped in a `Promise`), and posts one batched `{ type: 'drop-files', files: [{ name, data }] }` once all have resolved. Returns `true`.
- A `document`-level fallback (`dragenter`/`dragover`/`drop`, sharing the same `pendingDropPos`/`readFileAsDataUrl`) still exists for drops landing outside CM6's `contentDOM` (the title/breadcrumb area above the editor, which `eventBelongsToEditor()` in `@codemirror/view` excludes from CM6's own handler scope entirely) — guarded with an `if (e.defaultPrevented) return;` at the top of each so it doesn't double-process a drop `linkClickHandler` already claimed.
- Temporary diagnostics: capture-phase `document` listeners on `dragenter`/`dragover`/`drop` log `[obsidian-like] document <type>: hasFiles=... defaultPrevented=... target=...` unconditionally (capture phase means they log even if something else stops propagation first) — check via Command Palette → "Developer: Open Webview Developer Tools" (with the note panel focused) while performing the drag, to see whether the event reaches the webview's DOM at all. Remove once this is confirmed working end-to-end.

Host-side `drop-files` handling mirrors `paste-image` (writes into `getSaveDir()`, same base64-decode-and-`fs.writeFileSync` shape, via the shared `uniqueAttachmentName(saveDir, filename)` helper) but — unlike pasted clipboard image data, which has no real filename and gets a `Pasted image YYYYMMDDHHMMSS.png` name — a dropped file's original name is already known and kept as-is, only disambiguated (`"name N.ext"`) on an actual collision. The reply (`files-dropped`) inserts one `![[filename]]` per file at `pendingDropPos`, same embed convention already used for pasted images and note transclusions.

**Not yet re-tested on real hardware after this fix.** If it still doesn't work, the next things to check (in order): (1) the diagnostic logs above — do they fire at all, and with what `hasFiles`/`defaultPrevented`; (2) whether `event.dataTransfer.files` is actually populated at `drop` time (some remote/network-share paths on macOS can behave oddly with native DnD); (3) whether VS Code really does have some outer-layer interception after all, in which case `vaultTool.insertAttachment` below remains the fallback.

### `vaultTool.insertAttachment` — the actual working way to attach a file to a note

Explorer-context-menu command (`contributes.menus.explorer/context` in `package.json`) that sidesteps the drag-and-drop problem above entirely by never depending on a drop event reaching the webview. Right-click one or more files in VS Code's Explorer → "Obsidian-like: Insertar como adjunto en la nota activa":

1. Resolves the target Obsidian-like panel: `activePanels.find(p => p.active) ?? activePanels.find(p => p.visible) ?? (exactly one panel open ? that one : none)` — `.active` will almost always be `false` here since invoking from the Explorer context menu means focus was on the Explorer, not the editor, so the `.visible` fallback (and the single-panel fallback, covering the common case of just one note open in a background tab) both matter, unlike `toggleSourceMode`'s otherwise-identical panel lookup.
2. Resolves that panel's document path via a reverse lookup through `panelsByPath` (`[...panelsByPath.entries()].find(([, p]) => p === panel)`).
3. Copies each selected file into `getSaveDir(docPath)` via `fs.copyFileSync`, name-deduplicated by the same `uniqueAttachmentName` helper `drop-files` uses.
4. Posts the exact same `files-dropped` message the `drop-files` handler sends — no webview-side changes needed at all. `pendingDropPos` is `null` in this path (no drop occurred), so the webview's existing fallback inserts at the current cursor position instead — which is exactly the right behavior: place the cursor where you want the embed, then run the command.

### `vaultTool.duplicateFile` — "Duplicar archivo"

Another Explorer-context-menu command (same `contributes.menus.explorer/context` group as `insertAttachmentCmd` above, same `clicked?: vscode.Uri, selected?: vscode.Uri[]` argument shape VS Code passes to any command invoked from there). Right-click one or more files → "Obsidian-like: Duplicar archivo": for each, copies it (`fs.copyFileSync`) alongside itself with `_copia` appended to the base filename before its extension (`Note.md` → `Note_copia.md`), reusing `uniqueAttachmentName`'s own " N" disambiguation loop (seeded from the `_copia` name instead of the original) so an existing `Note_copia.md` doesn't get silently overwritten — a second duplicate becomes `Note_copia 2.md`, etc. Not scoped to `.md` files specifically — works on any file the same way `insertAttachmentCmd` does, matching how generically "duplicate this file" is expected to behave in a file explorer.

### `vaultTool.openNoteQuickPick` — the "open note" quick switcher

Modeled directly on Obsidian's own quick switcher dialog. Deliberately implemented as a `vscode.window.createQuickPick()` rather than a webview: a webview in VS Code always occupies a fixed editor tab (there is no API for a floating/modal webview overlay), so it can't actually reproduce a floating dialog the way Obsidian's looks — `QuickPick` is the widget the Command Palette itself is built on, and already floats with a search box on top and a list below, which is what was actually being asked for. **Position is not configurable**: QuickPick always anchors near the top of the window, horizontally centered — there is no API to move it to the vertical center, regardless of how Obsidian's own dialog happens to be positioned in a reference screenshot. This isn't a gap to fix later; it's a hard constraint of the platform.

QuickPick also has no footer slot the way Obsidian's dialog shows one below the list — `qp.prompt` (rendered below the input box, *above* the list, the closest thing VS Code exposes) carries the keybinding hint text instead: `'↑↓ navegar · ↵ abrir · Ctrl+↵ nueva pestaña · Ctrl+Alt+↵ dividir a la derecha · Esc descartar'`. Deliberately not a verbatim copy of Obsidian's own footer text — there's no Shift+Enter-to-create here, since "create" is implemented as a regular, always-visible list item instead (see below), not a modifier-key gesture.

- Bound to `Ctrl+O`/`Cmd+O` (`contributes.keybindings`), but scoped with `"when": "activeCustomEditorId == 'vaultTool.markdownEditor'"` so it only overrides VS Code's native "Open File…" shortcut while a obsidian-like note is the focused editor — not globally.
- `NOTE_HISTORY_KEY` in `context.globalState` (capped at `NOTE_HISTORY_LIMIT` = 50, most-recent-first, deduplicated by moving an existing entry to the front rather than adding a second one) is the "recently opened" history — persisted per VS Code profile, survives restarts, same as Obsidian's own quick switcher history. `recordNoteOpened(fsPath)` is called from `resolveCustomTextEditor` itself, the single choke point every note passes through regardless of *how* it was opened (Explorer double-click, wiki-link click, transclusion's open button, drag-and-drop-created attachment note, or this quick pick's own selection) — so nothing else needs to remember to record anything.
- On invoke: builds `allItems` from a fresh `findFiles('**/*.md')` (label = basename, description = vault-relative directory, for disambiguating same-named notes in different folders) and `recentItems` by mapping `getNoteHistory()` through the *current* file list (filtering out any history entries whose file no longer exists — deleted/moved notes just silently drop off rather than showing a dead entry).
- Empty search box shows `recentItems` (falling back to `allItems` if there's no history yet).
- Typing switches `qp.items` to `allItems` (or `allItems` plus a synthetic "create" item — see below) and lets QuickPick's own built-in fuzzy filtering (against label/description) take over from there — no custom filtering logic needed, `matchOnDescription: true` is enough to also match on the folder path shown in each item's description.
- **Create a note if the typed text doesn't match one**: `existingRelLower` is a set of every note's vault-relative path (no extension, lowercased, `/`-separated regardless of OS) built once up front. On every keystroke, if the trimmed value doesn't exactly match an entry, a synthetic item — `{ label: '$(new-file) Crear nota "..."', alwaysShow: true, isCreate: true, createName: value }` — is appended to `allItems`. `alwaysShow: true` is what exempts it from QuickPick's own fuzzy filter (which would otherwise hide it whenever the typed text doesn't textually resemble its own label); everything else in the list still gets filtered normally against the typed value. Accepting it (`createAndOpenNote`) creates an empty `.md` at `vaultRoot/<typed path>.md` (a typed value containing `/` creates the note inside that subfolder, mkdir'd as needed — mirrors Obsidian's own quick-switcher behavior for typed paths) and opens it.
- **Ctrl+Enter (new tab) / Ctrl+Alt+Enter (split right)**: QuickPick's `onDidAccept` fires identically no matter what modifier key was held for Enter — VS Code doesn't expose that. Instead, `vaultTool._openNoteQuickPickInNewTab`/`vaultTool._openNoteQuickPickToSide` are separate, unlisted commands (no `contributes.commands` entry, so they don't clutter the Command Palette) bound directly to those chords, scoped with `"when": "vaultToolQuickPickActive"` — a context flag `openNoteQuickPickCmd` sets via `setContext` for exactly as long as its own QuickPick is showing (cleared in `onDidHide`). Using this dedicated flag rather than the built-in `inQuickOpen` context means these commands can never fire while some *other*, unrelated quick pick happens to be open elsewhere in VS Code. Both commands read the currently-active item off the module-level `currentQuickPick` (there's no other way to reach a `QuickPick` instance from outside the closure that created it) and call the same `acceptQuickPick(vaultRoot, mode)` the plain Enter handler uses, just with a different `OpenMode`.
- `openNoteFromQuickPick(fsPath, mode)` — `'replace'` (plain Enter) mirrors `navigateToTarget`'s pattern exactly: `vscode.openWith` in the current panel's column, then dispose that panel afterward (skipped if the picked note *is* the one already open — nothing to replace). `'newtab'` opens in the same column *without* disposing anything, landing as a second tab in the same group. `'side'` opens in `vscode.ViewColumn.Beside`, a new split column, also leaving the original panel untouched. The latter two are the only place in the whole extension that intentionally opens more than one obsidian-like panel side by side — everywhere else (wiki-links, transclusions) always replaces the current one — but they exist specifically because the reference UI asked for them, not as a general precedent to extend elsewhere.

### Image Toolkit (click-to-zoom images) — soft dependency on `angelCastro.obsidianlike-imagetoolkit`

Unlike the Tasks/Dataview integrations above, this sibling (repo `c:\git\obsidianlike_imageToolkit`) doesn't hand back data for this codebase to render — it owns an entire *webview script* (click-to-popup/zoom/pan/rotate/flip/invert/copy/fullscreen, Normal + Pin modes, gallery navbar), ported from the Obsidian community plugin "Image Toolkit". Two extensions can't share a webview's DOM, so that script has to be loaded into *this* extension's own editor webview — this codebase is the one side of the soft dependency that has real injection work to do, not just an API call.

1. `getImageToolkitApi()` — same lazy/cache-on-success-only pattern as `getTasksApi()`/`getDataviewApi()`, targeting `vscode.extensions.getExtension('angelCastro.obsidianlike-imagetoolkit')`.
2. `getImageToolkitAssets()` — calls the sibling's `getWebviewAssets()` (absolute fs paths to its `out/imageToolkit.bundle.js`/`out/imageToolkit.css`, since only *this* webview can mint webview URIs for them) exactly once process-wide and caches both the assets and the derived `imageToolkitAssetRoots: vscode.Uri[]` (the two parent directories) — every place `localResourceRoots` is built (the three separate `webviewPanel.webview.options = {...}` assignments: initial setup, the `attachmentsLocation`/`attachmentsFolder` config-change handler, and `injectImageToolkitIfAvailable` itself) spreads `...imageToolkitAssetRoots` in, so a panel opened *after* the first one already has the roots available synchronously instead of only after its own async injection resolves.
3. `injectImageToolkitIfAvailable(webviewPanel, docUri)` — called fire-and-forget from the top of `resolveCustomTextEditor` (not awaited: blocking the note's first paint on activating another extension isn't worth it, especially since the common case — the sibling not installed at all — resolves near-instantly anyway). Once the assets resolve, reassigns `webview.options` with the extra roots, converts both paths to webview URIs via *this* panel's own `webview.asWebviewUri()`, and posts `{ type: 'load-image-toolkit', scriptUri, styleUri, settings }`.
4. `editor.js`'s `load-image-toolkit` handler sets `window.__imageToolkitSettings` (read synchronously at the top of the sibling's own script — must be set *before* the `<script>` tag is appended) and appends real `<link rel="stylesheet">`/`<script src="...">` tags. `image-toolkit-settings` (sent later, whenever `ensureSubscribedToImageToolkitChanges`'s `onDidChangeSettings` fires) just updates the global and dispatches a `image-toolkit-settings-changed` DOM event instead — the script is already loaded by then, no need to reload it.
5. CSP note: `buildHtml()`'s `style-src` had to gain `${cspSource}` (previously just `'unsafe-inline'`) so the sibling's externally-linked stylesheet is allowed to load at all — an inline-only `style-src` blocks a real `<link href>`, unlike `<style>` blocks.
6. `ImageToolkitApi` (declared locally, not imported from the other repo — same reasoning as `TasksExtensionApi`/`DataviewExtensionApi`) is intentionally the full-and-only shape: `getWebviewAssets()`, `getSettings()`, `onDidChangeSettings`. There's no DTO/HTML-rendering method here at all, since this integration never asks the sibling to compute anything — it only asks *where its assets are* and *what the user configured*.

This is a **soft dependency**: no `extensionDependencies` entry in either `package.json`, so obsidianlike keeps working standalone (just without the image viewer) if `angelCastro.obsidianlike-imagetoolkit` isn't installed — `getImageToolkitApi()` resolves to `undefined` and `injectImageToolkitIfAvailable` is a silent no-op.

## Known issues / future work

1. **Image paste** — reported broken, not investigated.
2. **Standard markdown images** `![alt](url)` — not handled by imgPlugin (which only handles `![[file]]`). Shows as raw markdown.
3. **External file drag-and-drop onto the editor** — implemented (see "Drag & drop files onto the editor" above) but not confirmed reliable; `vaultTool.insertAttachment` (Explorer right-click) is the dependable path in the meantime.
4. **VS Code's native "Edit → Buscar" menu item does nothing** — not fixable from this extension; see "Find/replace panel" above. Use Ctrl+F, or the Command Palette ("Obsidian-like: Buscar y reemplazar"), instead.
5. **Find/replace panel's preserve-case replace, and the panel generally** — built directly from `@codemirror/search`'s own source/types, not verified against a live webview yet (see "Find/replace panel" above for why the usual jsdom smoke test couldn't run on this machine). Expect a round of visual/functional fixes once it's actually exercised.
6. **Multi-cell table selection and the Excel/Outlook clipboard interop** ("Multi-cell selection"/"Pegar como tabla"/"Copiar como tabla" above) — built and confirmed to compile/bundle cleanly, and the heading-bracket font-size fix in the same session was independently verified against a real `EditorView` in jsdom, but these specific features (mouse drag tracking, `ClipboardItem`/`DOMParser`-based clipboard interop) haven't themselves been exercised in a live webview yet. Expect a round of fixes once actually tried against real Excel/Outlook clipboard content.
